# 지식 원문 원장 — 계획 (2026-10-08, 업계 표준 방식 확정 후 MVP)

> 결정: 원문 = 기준(SoT), 청크·임베딩 = 언제든 다시 만드는 파생물(사용자 10/07). 배경: 장애 보고서
> `docs/incident/2026-10-07-knowledge-chunking-defect.md` §7. 업계: AWS Bedrock KB·Azure AI Search(원문은 저장소, 청크는 동기화 때
> 재생성), LangChain Record Manager·LlamaIndex `ref_doc_id`(청크마다 원문 ID·해시), 메달리온 Bronze 층.

## 1. 지금 실제로 막힌 일
1. **파이프라인 결함이 나면 다시 자를 원문이 없다** — 10/07 결함 보정은 저장된 청크에서 원문을 복원하는 우회로 했다. 추출 단계에서
   사라진 내용(코드 매크로 SQL 등)은 그 방법으로도 못 살린다.
2. **같은 원문 재등록 판단이 컨플루언스 페이지 ID에만 의존** — 파일·붙여넣기는 다시 올리면 옛 청크와 새 청크가 함께 남는다.
3. **청크가 어느 원문에서 왔는지 모른다** — 컨플루언스 활성 청크 56개 중 페이지 ID 0개, "Confluence 18개 페이지" 같은 묶음 이름뿐.

## 2. 하는 것 (MVP)
- **`rag_source_document`**: 파트, 원문 종류(confluence·web·file·paste), 원본 위치(페이지 ID / URL / 파일명), 제목·상위 제목, 원문 형식
  (html / text), **원문**(컨플루언스 storage HTML·웹 HTML 그대로, 파일은 추출 텍스트, 붙여넣기는 원문), 내용 해시, 원본 버전
  (컨플루언스), 상태(초안 → 사용 중 → 교체됨), 등록자·시각.
- **`rag_knowledge.source_document_id`**: 청크 → 원문 연결.
- **"같은 원본" 기준**(리뷰 반영): 위치가 확실한 컨플루언스 페이지 ID·웹 URL은 위치가 같으면 같은 원본(새 버전으로 교체), 파일·
  붙여넣기는 위치(파일명)만으론 모르니 위치+내용(해시)이 같을 때만. 초안 재사용은 종류·위치·내용이 같은 초안끼리만.
- **쓰기**: 미리보기 단계에서 원문을 초안으로 저장 → 미리보기 결과에 원문 ID → 확정(`/bulk`) 때 청크에
  연결하고 원문을 "사용 중"으로. 같은 원본 위치의 이전 원문은 "교체됨", 그 청크는 지금의 컨플루언스 교체 경로를 일반화해 폐기
  (중복 검사에서 자기 원문의 옛 청크는 빼고).
- **다시 분할**: `POST /api/knowledge/source-documents/{id}/rechunk` — 원장의 원문을 **지금 코드**로 다시 파싱·분할 → 품질 검사 →
  한꺼번에 교체(옛 청크 폐기). 같은 결과면 아무것도 안 함. 사람이 고친 청크(정정 승인 등으로 수정된 것)가 있으면 자동 교체하지 않고
  개수를 알려 멈춤(`force`로만 진행) — 사람의 수정을 조용히 덮지 않게. 삭제·반려한 조각, 등록 때 일부만 고른 원문, 조각별 업무구분
  차이도 같은 이유로 멈춤.
- **화면**: 지식 상세 "원문 위치"에 원문 정보와 [원문에서 다시 분할] 버튼(수정 권한자), 결과(청크 수·품질 경고) 안내.
- **재등록 확인(A안, 2차 리뷰 M1 — 사용자 결정 10/12)**: 같은 원본 재등록도 다시 분할과 같은 기준으로 본다. 흔적이 있으면 사유를
  보여주고 확인 후 교체, 없으면 바로 교체. `POST /api/knowledge/bulk/replace-check` + `/bulk`의 `confirm_replace`(없으면 409).
  삭제·반려 이력은 지금 사용 중인 원문에서 사용 중이 된 뒤의 것만(교체된 옛 원문의 이력이 다음 재등록마다 걸리지 않게).
- **동시 확정(M2)**: 같은 원본(파트·종류·위치)을 advisory lock으로 하나씩, 전환 트랜잭션 안에서 원문 상태·교체 대상을 다시 계산.

## 3. 안 하는 것 (다시 볼 조건)
| 항목 | 다시 볼 조건 |
|---|---|
| 파일 원본 바이트 보관(PDF 등) | 추출기 자체를 고쳐 원본에서 다시 추출해야 하는 사례가 생기면 |
| 옛 원문 버전 여러 개 보관·버전 비교 화면 | "예전 원문 기준으로 답했던 근거"를 재현해야 하는 요구가 생기면(지금은 교체됨 1단계만 남김) |
| 컨플루언스 자동 재동기화(버전 바뀌면 자동 재수집) | 원본 변경을 놓쳐 오답이 난 사례가 생기면 |
| 원본 삭제 감지·전파 | 같은 조건 |
| 미사용 초안 자동 정리 | 초안이 실제로 쌓여 용량 문제가 되면(해시 재사용으로 증가는 제한적) |
| 기존 청크 원문 역채움 | 데이터 재정제 때 컨플루언스에서 재수집 — 저장 청크로 원문을 만들지 않는다(원문이 아니므로) |

## 4. 완료 기준
- 불변식: 원장에서 다시 분할한 결과 = 같은 원문을 처음 등록했을 때 결과(같은 코드면 청크 동일 → 아무것도 안 함).
- 실서버 시나리오: 붙여넣기 등록 → 원장·연결 확인 → 같은 원문 재등록 시 옛 청크 폐기·중복 없음 → 다시 분할(코드 같으면 변화 0) →
  사람이 고친 청크가 있으면 멈춤.
- 회귀 전체 + E2E, 문서(architecture·flow·table-definition). 규모 있는 기능 — dev_0에서 완전 검증 후에만 main.
