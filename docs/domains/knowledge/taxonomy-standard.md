# 지식 분류 표준 — 정책 컬렉션 · 시스템 컬렉션 (11/02)

컬렉션을 무엇으로 나누나. 조직 개편(파트 분리·통합·이름 변경)에 흔들리지 않게 한다.
결정: 2026-11-02 사용자. 마이그레이션 #105(구분값·코드·보관함)와 #106(조직 컬렉션 폐지). 키 정리는 [collection-key-plan.md](collection-key-plan.md).

**범위 원칙**: OpsLens는 컨플을 통째로 옮기지 않는다. **IT 운영 지식만** 다룬다.
- 대상: 정책, 시스템 운영·개발 지식
- 대상 아님: 행정(법인카드 상신·결재), 친목(맛집), 개인 기록. 소스 연결에서 AI가 제외를 제안하고 사람이 확정한다.

## 1. 막힌 일
- 컬렉션이 정책서 장 기준 하나뿐이었다. 그래서 시스템 운영 지식(야간작업 이력·장애 대응·연동 사양)이 갈 곳이 없었다.
  - 실례: #85 CX 홈페이지 파트 컨플은 20묶음 중 17개가 "운영"이었다.
- 갈 곳 없는 지식이 조직 컬렉션(org:part:id)으로 몰렸다. 파트가 쪼개지거나 합쳐지면 손으로 옮겨야 하는 구조였다.
- 측정: 업무지식 질문 106개 전부에 정책 서술 10개가 붙었다. 정책을 빼면 정답 77.6→83.3%, 단정 오답 21.9→15.6%였다(#65).

## 2. 업계 근거
| 출처 | 핵심 | 우리에게 |
|---|---|---|
| Enterprise Knowledge, *What's in a name? Not your org chart* | 분류에 조직도를 쓰지 않는다(업무 기능으로). 관점이 여럿이면 축(facet)으로 나눈다 | 컬렉션 이름에 조직 금지, 축 분리 |
| Backstage 시스템 모델 | Domain › System, owner는 그룹을 가리키는 필드일 뿐 | 정책·시스템 + 담당 연결 |
| ITIL 서비스 카탈로그 | 업무 서비스를 기술 서비스가 받친다. 지식은 서비스에 연결한다 | 시스템 ↔ 관련 정책 연결 |
| KCS | 문서 유형은 일관된 분류로 관리하고, 문서마다 담당자를 둔다 | 문서 유형은 컬렉션이 아니라 표시(나중에) |

## 3. 표준
| 구분 (`ops_namespace.area`) | 무엇을 | 등록 경로 | 바뀌나 |
|---|---|---|---|
| **정책 컬렉션** (`policy`, 코드 `POL-…`) | 정책서(+ 정책 용어) | 정책서 가져오기 | 사업이 바뀔 때 |
| **시스템 컬렉션** (`system`, 코드 `SYS-…`, 최상위만) | **운영 지식 전부**: 컨플·매뉴얼·운영 이력·장애 대응·연동 사양·노하우 | 운영 지식 등록 · 소스 연결 | 시스템이 생기거나 없어질 때 |
| 담당 (팀·파트) | 연결만(`ops_namespace_owner`) | 담당 컬렉션 화면 | 조직 개편 때 연결 줄만 |

- 둘 다 `kind='domain'`이다. 그래서 검색·권한·담당·용어가 같다.
- **관련 정책**: 시스템 ↔ 정책 N:N(`ops_link relation='supports'`, `PUT /api/namespaces/{시스템}/supports`).
  - 관련 정책이 없는 시스템은 정상이다(예: 앱 시스템).
  - 관련 시스템이 없는 정책은 화면에 경고한다. 그 정책 질문에서 운영 지식을 찾을 길이 없기 때문이다.
- **업무 코드**: 불변·유일(`POL-MBR` · `SYS-HP`). 이름은 화면용이다. 시스템 화면 이름은 키에서 " 시스템"을 뗀 것이다.
- **넣는 규칙** — 사용자가 고민할 기준이 없게 한 줄:
  - 정책서는 정책 컬렉션에 넣는다. 시스템 컬렉션에 넣으려 하면 400이다.
  - 운영 지식은 시스템 컬렉션에만 넣는다. 위치 판단 AI v3의 후보는 시스템뿐이고, 정책 컬렉션 줄엔 [지식 등록 →]이 없다.
- 조직 컬렉션(`kind='org_space'`)은 폐지했다(#106). 팀·파트는 로그인·권한·담당 뼈대만 남는다.
- 시스템(11/02 사용자 지정, 화면은 [정책 | 시스템] 두 탭):
  - 스타벅스CSP팀: 딜리버스(SYS-DLV → 딜리버스) · 외부서비스(SYS-EXT → 제휴서비스) · 온라인스토어(SYS-OST → 온라인스토어)
  - 스타벅스CX팀: 홈페이지(SYS-HP → 회원) · 앱(SYS-APP, 관련 정책 없음)
- 외부 연계: 온톨로지 포털과는 "우리 시스템(코드) ↔ 그쪽 담당자" 관계만 맞춘다.

## 4. 검색 범위 (측정 → 게이트)
| 범위 | 내용 | 측정(11/02) |
|---|---|---|
| A 지금 | 고른 컬렉션만 | CX 질문 93개(회원에서 묻기): 검색 0% · 답 0% |
| **B linked** | 고른 컬렉션 + 관련 정책 연결(양방향, 하위 정책은 상위 연결 상속) | 검색 87.1% · 답 **83.3%**(게이트 #67 통과, 나빠짐 0, 단정 오답 10.8%) · 업무지식 106 검색 A = B 95.3% |
| C similar | B + 질문과 가까운 컬렉션 2개 | 검색 = B, 느림(질문마다 키워드 색인) → **채택 안 함** |

**채팅 기본 = B linked + 문맥 예산 1만 2천 자**(11/02 반영, v2.198). 정책 컬렉션 안 운영 지식을 시스템으로 옮긴 것(D)과 한 묶음 — 옮긴 뒤 linked 없이 정책에서 물으면 운영 지식 검색 0%(측정). 게이트: 업무지식 #71(정답 73.6→77.4% · 단정 오답 26.4→18.9% · 검색 101/106 그대로), 정책서 #72(84.9→86.0% · 12.0→11.5%). 측정 스크립트는 플래그 없음 = 채팅과 같음, `--scope none` · `--context-budget 0` = 끔.

## 5. 조직 개편 때
| 개편 | 할 일 | 지식 이동 |
|---|---|---|
| 이름 변경 | 없음(코드·id 기준) | 0 |
| 파트 분리 · 통합 · 팀 이동 | 담당 줄을 나누거나 합친다 | 0 |
| 시스템이 새로 생김 | 시스템 컬렉션 추가 + 관련 정책 연결 | — |

## 6. 안 하는 것 (다시 볼 조건)
| 안 하는 것 | 다시 볼 조건 |
|---|---|
| "공통" 구분(시스템에 안 딸린 팀 노하우) | 사용자 피드백·지식 공백에 같은 요구가 반복될 때. 시스템 노하우는 시스템에 둔다 |
| 문서 유형 표시 | 검색에서 유형으로 걸러야 할 때 |
| 자동 컬렉션 생성 | 팀 2~3개를 적재한 뒤에 추천만 |
| 시스템 하위 단계 | 시스템 하나에 수천 조각이 쌓일 때 |
