# 지식 분류 표준 — 업무 영역 · 시스템 (11/02)

컬렉션을 무엇으로 나누나. 조직 개편(파트 분리·통합·이름 변경)에 흔들리지 않게 한다.
결정: 2026-11-02 사용자 "조직은 로그인·권한 뼈대만, 컬렉션은 시스템 축으로". 마이그레이션 #105.

**범위 원칙(11/02 사용자)**: OpsLens는 컨플을 통째로 옮기지 않는다. **IT 운영 지식만** 다룬다.
- 대상: 업무 규칙·절차(업무 영역), 시스템 운영·개발 지식(시스템)
- 대상 아님: 행정(법인카드 상신·결재), 친목(맛집), 개인 기록. 묶음 단계에서 제외한다.

## 1. 막힌 일
- 업무 영역 14개가 정책서 장 기준 하나뿐이다. 그래서 시스템 운영 지식(야간작업 이력·장애 대응·연동 사양)이 갈 곳이 없었다.
  - 실례: #85 CX 홈페이지 파트 컨플은 20묶음 중 17개가 "운영"이었다.
- 갈 곳 없는 지식이 조직 컬렉션(org:part:id)으로 몰렸다. 그러면 파트가 쪼개지거나 합쳐질 때 손으로 옮겨야 한다.

## 2. 업계 근거
| 출처 | 핵심 | 우리에게 |
|---|---|---|
| Enterprise Knowledge, *What's in a name? Not your org chart* | 분류에 조직도를 쓰지 않는다(업무 기능으로). 관점이 여럿이면 축(facet)으로 나눈다 | 컬렉션 이름에 조직 금지, 축을 분리 |
| Backstage 시스템 모델 | Domain › System, owner는 그룹을 가리키는 필드일 뿐 | 업무 영역·시스템 + 담당 연결 |
| ITIL 서비스 카탈로그 | 업무 서비스를 기술 서비스가 받친다. 지식은 서비스에 연결한다 | 시스템 → 업무 "받침" 연결 |
| KCS | 문서 유형은 일관된 분류로 관리하고, 문서마다 담당자를 둔다 | 문서 유형은 컬렉션이 아니라 표시(나중에) |

## 3. 표준
| 축 | 형태 | 무엇을 | 언제 바뀌나 |
|---|---|---|---|
| 업무 영역 (`area=business`) | 컬렉션 | 정책 + 업무 규칙·절차 | 사업이 바뀔 때 |
| 시스템 (`area=system`) | 컬렉션(최상위만) | 운영 이력 · 장애 대응 · 모니터링 · 연동 사양 · 시스템 개발·운영 노하우 | 시스템이 생기거나 없어질 때 |
| 담당 (팀·파트) | 연결만(`ops_namespace_owner`) | — | 조직 개편 때 연결 줄만 바꾼다 |

- 시스템은 새 종류(kind)가 아니라 업무 영역의 구분값이다. 그래서 검색·권한·담당·용어가 업무 영역과 똑같이 동작한다.
- 받침 연결: `ops_link(from_type='domain' 시스템, relation='supports', to_type='domain' 업무)`.
- 조직 컬렉션(`kind='org_space'`, #83)은 없앤다. 팀·파트는 로그인·권한·담당에만 남긴다.
- 넣는 규칙(위에서부터 처음 "예"인 곳):
  1. 특정 업무의 규칙·절차인가 → 업무 영역
  2. 특정 시스템의 운영·사양·이력·노하우인가 → 시스템
  3. 둘 다 아니면 → 제외
- 첫 시스템(사용자 지정 11/02) — 화면은 [업무 | 시스템] 두 탭만(팀별 묶음 없음):
  - 스타벅스CSP팀: 딜리버스 시스템(→ 딜리버스) · 외부서비스 시스템(→ 제휴서비스) · 온라인스토어 시스템(→ 온라인스토어)
  - 스타벅스CX팀: 홈페이지 시스템(→ 회원) · 앱 시스템(받침 미정)
- 외부 연계: 온톨로지 포털과는 "우리 시스템 ↔ 그쪽 담당자" 관계만 맞춘다.

## 4. 조직 개편 때
| 개편 | 할 일 | 지식 이동 |
|---|---|---|
| 이름 변경 | 없음(id 기준) | 0 |
| 파트 분리 · 통합 · 팀 이동 | 담당 줄을 나누거나 합친다 | 0 |
| 시스템이 새로 생김 | 시스템 컬렉션 추가 + 받침 연결 | — |

## 5. 안 하는 것 (다시 볼 조건)
| 안 하는 것 | 다시 볼 조건 |
|---|---|
| 문서 유형 표시 | 검색에서 유형으로 걸러야 할 때 |
| 자동 컬렉션 생성 | 팀 2~3개를 적재한 뒤에 추천만 |
| 시스템 하위 단계 | 시스템 하나에 수천 조각이 쌓일 때 |
| 기존 제휴서비스·딜리버스 컨플 지식(업무 영역에 직접 들어감)의 재배치 | 시스템 컬렉션이 생긴 뒤 측정(D)으로 판단 |
| 세 번째 구분 "공통"(시스템에 안 딸린 팀 노하우 — 일의 종류로 이름, 예: 개발·운영 가이드) | 사용자 피드백·지식 공백에 "시스템에 안 맞는 노하우" 질문이 반복될 때. 시스템 노하우(개발환경·장애 예방 등)는 시스템에 둔다 |

행정 기록(법인카드 상신 내역 · 결재 · 개인 정보가 든 표)은 운영 지식이 아니고 민감하다 — 묶음 단계에서 **제외**한다(맛집 목록과 같은 취급).

4. 화면: 채팅 [업무 | 시스템], 컬렉션 › 시스템. 시안을 먼저 확인받는다.
