## 3. (A) 조직 공간 — 데이터 모양

**고른 안: `ops_namespace`에 종류 하나(`kind='org_space'`)와 칸 하나(`owner_team_id`)만 더한다.**
따로 표를 만들지 않는 이유: 지식·용어·원문 원장·정정·질의 로그 등 **17개 표가 `namespace_id`로 보관 위치를 가리킨다**(FK 확인).
조직 공간도 같은 id 하나면 적재·검색·승인·캐시 경로를 하나도 갈라지지 않고 그대로 쓴다. 별도 표로 만들면 17곳이 다 분기해야 한다.

| 칸 | 업무 영역 (`domain`) | 조직 공간 (`org_space`) |
|---|---|---|
| `kind` | `domain` | `org_space` (이미 `domain`·`policy_test` 값이 있어 값만 하나 늘어난다) |
| 담당 | `owner_part_id` (매핑, 조직 › 담당 업무 영역) | 파트 공간: `owner_part_id` = 그 파트 / 팀 공통: **새 칸 `owner_team_id`** = 그 팀. 둘 중 하나만 채운다(CHECK) |
| `name` (UNIQUE, 캐시 키) | 업무 이름 | **id 기반 키**(`org:team:1`, `org:part:774`). 화면 이름은 조회 때 만든다: "팀 공통 · 스타벅스CSP팀", "노하우 · 온라인서비스 파트" — 파트 이름이 바뀌어도 데이터는 그대로 |
| 담을 수 있는 유형 | 정책·지식 문서·용어·시스템 정보 | **지식 문서·용어만**. 정책·시스템 정보는 업무에 붙는 것이라 조직 공간에 두지 않는다 |
| 만들기 | 관리자 | 팀·파트를 만들 때 함께 만들고(멱등), 팀·파트를 지우면 지식이 있을 때만 막는다(`ON DELETE CASCADE`가 지식을 지우지 않게) |

옮기기: 운영 DB의 "팀 공통" 업무 영역 → `kind='org_space'`, `owner_team_id`=스타벅스CSP팀(id만 바꾸고 행은 안 옮긴다 — 지식은 그대로 이 영역 id를 가리킨다).
점검(불변식): 옮기기 전후 표마다 `namespace_id` 행 수 같음 · `kind='org_space'`인데 담당 둘 다 비었거나 둘 다 찬 행 0 · 조직 공간에 `policy_item` 0.

**채팅 범위 규칙(측정 뒤 켬):** 지식 검색 = 고른 업무 영역 + **질문한 사람의** 파트 공간 + 그 파트가 속한 팀의 팀 공통.
정책 범위(모든 정책 영역)는 그대로. 슈퍼어드민(파트 없음)은 고른 영역만. 설정 하나(`chat.org_space_scope`, 기본 꺼짐)로 켜고 끈다.
켜기 조건: §7 측정에서 기존 업무 질문 나빠짐 0 + 조직 공간 문항에서 근거 들어옴.

## 4. (B) 등록 창구 하나 — 흐름

```
[넣는 사람]  붙여넣기 · 파일 · URL(컨플)  ── 영역·유형·업무구분을 고르는 칸 없음
     │
     ▼ ① 원문 저장: 원문 원장 draft(rag_source_document, 지금 코드 그대로)
     ▼ ② AI 판단 안 (아래 출력) ── 판단은 LLM 1회 + 이웃 투표(LLM 없음)
     │      확신 → ④로 바로        확신 없음 → ③
     ▼ ③ 선택지 핑퐁 (넣는 사람에게, 최대 1번): 버튼 2~3개 + "잘 모르겠어요"
     ▼ ④ 정정 요청 대기열에 한 줄 (ops_improvement_item kind='registration', namespace_id = 정한 보관 위치)
     │
[승인하는 사람 = 그 위치의 담당 / 담당 없으면 관리자]  품질 › 정정 요청
     ├ 승인  → 기존 적재 경로로 활성(청크·태그·용어 추출·임베딩) — 원장 draft → active
     ├ 직접 수정 → 제목·본문을 고치고 승인(내용 고치기는 사람이 직접 할 수 있다)
     └ 반려(사유 한 줄) → AI가 사유를 넣어 다시 판단 → 새 안이 같은 줄에 대기(redraft 재사용) / "등록 안 함"이면 닫힘
```

**AI 판단 안의 모양** (`proposed` jsonb — 이미 있는 칸, 새 표 없음)

```json
{ "type": "knowledge_doc",                 // policy | knowledge_doc | glossary | system_info
  "location_id": 530, "location_kind": "domain",
  "confidence": "high",                    // high | low — 숫자가 아니라 규칙 결과(아래)
  "why": "딜리버스 주문 상태 코드·배차 화면 언급, 비슷한 승인 지식 5건 중 4건이 딜리버스",
  "alternatives": [{"location_id": 266, "votes": 1}, {"org_space": "team"}],
  "title": "…", "links": [{"to_type": "knowledge", "to_key": "812", "relation": "similar"}],
  "duplicates": [812], "pingpong": {"asked": true, "picked": "맞아요"},
  "fallback": null }                       // AI 실패 시 "analyzer_failed" 등 — 카드에 그대로 표시
```

- **확신 판정은 LLM의 자기 평가를 쓰지 않는다**(자기 평가 숫자는 잘 안 맞는다). 신호 둘이 맞을 때만 `high`:
  ① LLM이 고른 위치 ② 원문 임베딩과 가까운 **승인된** 지식 k=5개의 보관 위치 다수결(지금 `duplicate-matches`와 같은 검색).
  둘이 같고 다수결이 4/5 이상이면 `high`. 아니면 `low` → 핑퐁. 컨플 공간 키 → 지난 승인 위치(있으면)는 ②에 한 표로 더한다.
- **유형:** 정책서 엑셀·v0 원문 모양이면 `policy`, DB 칼럼표·코드표 모양이면 `system_info`, 짧은 "A란 B" 묶음이면 `glossary`, 나머지 `knowledge_doc`.
  **MVP는 `knowledge_doc`만 끝까지 등록**한다. 다른 유형으로 판단되면 안 카드에 "정책서로 보여요 → 정책서 올리기로" 링크를 띄우고 멈춘다
  (조용히 지식으로 넣지 않는다). 각 유형의 적재기를 창구 뒤에 붙이는 건 그 유형 개편 때.
- **연결:** 비슷한 기존 지식(중복 후보)만. `ops_link`는 승인 때 만든다(대기 중엔 연결을 만들지 않는다).
- **핑퐁 버튼 만드는 법:** `[맞아요: 1순위]` `[2순위 위치]` `[팀 공통이에요]`(또는 내 파트 공간) `[잘 모르겠어요]`. 누르면 안을 다시 만들어 대기열로.
  "잘 모르겠어요"는 1순위 그대로 `low` 표시로 보낸다 — 승인자가 본다. 채팅 되묻기(v2.133 `clarify_for`의 `{message, options}` 모양) 재사용.
- **보이는 실패·대체:** AI 판단 실패(analyzer 기본값) → `fallback` 채움 + 위치는 넣는 사람이 지금 고른 업무 영역으로 임시 + 카드 맨 위 노란 줄.
  이웃이 0건(빈 영역)이면 "비교할 지식 없음"을 이유에 적고 `low`.
- **재사용:** 원문 원장(`source_ledger.save_draft*`), 분석(`analyzer.analyze_document`), 청크(`chunker`), 태그·용어(`tagger`), 품질 점검(`quality`),
  중복 검색, 정정 대기열(`/api/corrections` 승인·반려·redraft·retarget). 새로 만드는 건 판단 함수 하나와 API 두 개
  (`POST /api/intake` 안 만들기, `POST /api/intake/{id}/pick` 핑퐁 고르기). 원장 draft의 `namespace_id`는 위치가 바뀌면 같이 바꾼다.
- **바뀌는 화면:** 지식 등록 탭(4가지 방식) → 창구 하나로 바꾸되 **입력 방식(붙여넣기·파일·URL)은 남기고 영역·업무구분 고르는 칸만 없앤다**.
  통계 지식 공백 모달·VOC 묶음 모달 → 창구를 열면서 질문·묶음 내용을 채워 넣는다. 컨플 트리 대량 가져오기(`/import/url/tree`, bulk-pages)는
  MVP에선 그대로(관리자, 영역 지정) — 한 번에 수십 장은 페이지별 승인이 오히려 부담.

## 5. (C) 사이드바 업무 영역 선택기 — 두 안

공통: 이건 **"지금 보는 범위"(context)를 고르는 칸**이지 메뉴의 부모가 아니다. 그래서 ① 메뉴와 줄로 떨어뜨리고 ② 이름을 "보는 범위"로,
③ 메뉴(지식·조직·품질…)는 범위를 바꿔도 그대로 있다. 조직 메뉴·시스템 메뉴처럼 범위와 관계없는 화면에선 칩을 흐리게 하고 툴팁 "이 화면은 범위와 관계없음".

**1안 — 그 자리에서 검색 가능한 목록(콤보박스)**
```
┌ 사이드바 ─────────────────────┐
│ 업무 영역                      │
│ ┌───────────────────────────┐ │
│ │ 딜리버스                ▾ │ │  ← 누르면 아래로 펼침
│ ├───────────────────────────┤ │
│ │ 검색: [ 쿠       ]         │ │
│ │ 최근   딜리버스 · 외부서비스│ │
│ │ 내 담당 ───────────────    │ │
│ │   딜리버스  외부서비스     │ │
│ │ 조직 공간 ─────────────    │ │
│ │   팀 공통 · 노하우(내 파트)│ │
│ │ 전체 업무 영역 ────────    │ │
│ │   쿠폰  …                  │ │
│ └───────────────────────────┘ │
│ ── 지식 ▸ 정책서 · 지식 문서 … │
```
장점: 지금 자리·동작 그대로, 고칠 곳 적음. 단점: 메뉴 바로 위라 "부모처럼 보이는" 문제가 그대로 남는다.

## 8. 하는 것 / 안 하는 것 + 다시 볼 조건

하는 것(MVP): 조직 공간(팀 공통·파트 노하우), 지식 문서 등록 창구 + 1회 핑퐁 + 정정 대기열 승인, 사이드바 범위 칩, 측정 뒤 켜는 채팅 범위.

| 안 하는 것 | 다시 볼 조건 |
|---|---|
| 업무 영역 꼬리표 0..N (DataHub 태그식) | 조직 공간 지식이 여러 업무 질문에 실제로 필요한 사례 3건 이상 → AI가 달고 사람이 고침 |
| 정책·용어·시스템 정보 유형을 창구 뒤에 붙이기 | 각 유형 화면 개편(정책서 ⑤, 용어집 개편) 때 하나씩 |
| 개인 공간, 닫힘·비공개 공간 | 열람 제한이 필요한 문서가 실제로 생길 때 |
| 컨플 트리 대량 가져오기를 창구로 | 대량 가져오기가 월 1회 이상 반복되고, 공간 키 → 위치 매핑 승인 사례가 쌓일 때(공간 단위 승인 1번) |
| 핑퐁 2회 이상, 내용 다듬기 핑퐁("단계로 나누기") | 1회 핑퐁 뒤 반려 사유가 "내용 구조"인 것이 상위일 때 |
| 확신 숫자(점수) 화면 표시 | 리플레이에서 점수와 정답률이 실제로 같이 움직일 때 |

## 9. 위험 · 검수받을 것

1. **표본이 작다**(활성 지식 73건, 영역 대부분 0건) — 빈 영역은 이웃 투표가 안 되므로 처음엔 `low`가 많다. 핑퐁이 잦아 귀찮을 수 있다 → 핑퐁률을 첫 주에 본다.
2. **`name`을 id 키로 바꾸는 것** — 화면·캐시·URL 곳곳이 영역 이름을 쓴다. 조직 공간에만 적용하고, 화면 이름은 API가 만들어 준다(`display_name`). 놓친 곳은 키가 그대로 보인다(보이는 결함이라 찾기 쉬움).
3. **승인자가 비면 대기열이 고인다** — 담당 없는 영역은 관리자에게. 대기 7일 넘으면 통계 화면에 숫자로.
4. 검수: ① 조직 공간을 `ops_namespace` 종류로 두는 것 ② 조직 공간에 지식 문서·용어만 ③ 사이드바 2안 ④ MVP를 지식 문서 유형만으로 ⑤ 채팅 범위 규칙(내 파트 + 내 팀 공통).
