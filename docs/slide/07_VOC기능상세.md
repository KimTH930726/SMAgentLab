# 슬라이드 7 — VOC 이메일 분석 채널 상세

> 슬라이드 수: 3장
> 목표: 메일이 엔진을 거쳐 Teams로 나가기까지의 흐름과, 관리자가 실제로 뭘 조정할 수 있는지를 간결하게 전달한다. 실제 시연은 이 슬라이드 뒤에 라이브 화면으로 진행(장표에는 시연 내용 없음).
> 위치: 03장(전체 시스템 개요)의 VOC 요약과는 별도 — 이 장은 VOC 단독 상세 보고용.

## [슬라이드 7-1] 전체 흐름 — 메일 한 통이 Teams 알림이 되기까지

### 제목
**수집 → 필터 → 분석 → 반복탐지 → 알림, 5단계**

### 본문 내용

```
[VOC 시스템] (기존 — 이번에 만든 범위 아님)
  담당자가 "키워드 + 수신 이메일 주소"를 미리 등록
  (예: "배달 지연" → voc-delivery@...)
        │ 등록된 키워드에 걸리는 VOC가 접수될 때마다
        │ VOC 시스템이 그 이메일 주소로 자동 발송
        ▼
[Microsoft Graph API]  ← 여기서부터 이번에 만든 5단계
  파트별 VOC 메일함을 주기 폴링
        │
        ▼
┌────────────────────────────────────────────────────────┐
│ ① 전처리 + 관련성 필터                                       │
│ 전달/회신 체인 제거(새로 쓴 내용만 추림) → 등록된 지식과의          │
│ 하이브리드 유사도 계산 → 임계치 미달이면 LLM 호출 없이 종료        │
└───────────────────────┬────────────────────────────────┘
                        │ 임계치 이상만 통과
                        ▼
┌────────────────────────────────────────────────────────┐
│ ② RAG 분석 (KnowledgeRAG 엔진 재사용)                       │
│ 민감정보 마스킹 후 LLM 전달 → 분류·심각도·오배치·해결안 초안 산출  │
└───────────────────────┬────────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────────┐
│ ③ 중복 방지                                                 │
│ 이미 처리한 메일은 재분석하지 않음                              │
└───────────────────────┬────────────────────────────────┘
                        ▼
┌────────────────────────────────────────────────────────┐
│ ④ 반복 패턴 탐지 + 발송 게이트                                 │
│ ②의 분석 호출이 함께 뽑아준 정규화 이슈요약을 임베딩(LLM 추가    │
│ 호출 없음) → 과거 VOC와 클러스터링 → "3건 이상, 그 배수(3/6/9건째)"│
│ 인 경우에만 ⑤로 진행. 그 외(단독 발생·아직 미만·배수 아님)는   │
│ 이력에만 기록하고 종료 — Teams는 나가지 않음                   │
└───────────────────────┬────────────────────────────────┘
                        │ 반복 패턴 확정(배수 지점)일 때만
                        ▼
┌────────────────────────────────────────────────────────┐
│ ⑤ 라우팅 · Teams 알림                                       │
│ 담당 파트 채널에 게시 — "N건째 발생(M건마다 감지·K번째)" +      │
│ 해결방안(있으면 LLM으로 재검증 후) 동봉, 심각도 "높음/긴급"이면  │
│ 온콜 담당자 멘션                                             │
└────────────────────────────────────────────────────────┘
```

**설계 원칙**: 모든 메일을 무조건 LLM에 태우지 않는다 — ①에서 무관한 메일(스팸·사내공지·참조메일)을 먼저 걸러 비용과 알림 피로도를 줄인다. 새 AI를 따로 만들지 않고 채팅용 KnowledgeRAG 엔진을 그대로 재사용한다. ④도 같은 원칙 — 반복 여부 판정에 LLM을 새로 태우지 않고 순수 벡터 연산만 쓴다(단, 해결방안이 있다고 뜰 때만 그 매칭이 진짜인지 LLM으로 1회 재검증). 발송 여부 자체도 ④ 하나로 통합했다 — 개별 VOC마다 매번 알림이 나가면 노이즈가 컸다는 실사용 피드백에 따라, "반복 패턴으로 확정됐을 때만" Teams로 알린다.

### 발표자 노트
> "먼저 입구부터 보면, VOC 시스템에 담당자가 키워드와 받을 이메일 주소를 미리 등록해둡니다. 그 키워드에 걸리는 VOC가 접수되면 VOC 시스템이 자동으로 그 이메일로 보내주고요 — 이건 기존에 있던 방식이고 저희가 새로 만든 부분은 아닙니다. 저희가 만든 건 그 다음부터입니다. 그렇게 날아온 메일함을 저희가 주기적으로 폴링해서 가져온 뒤, 우리 지식과 관련 있는 것만 골라 분석합니다. 여기서 중요한 포인트가, 분석된다고 다 Teams로 나가는 게 아니라는 겁니다 — 분석 단계에서 LLM이 어차피 한 번에 뽑아주는 정규화된 이슈 요약을 임베딩해서, 표현이 조금씩 달라도 같은 유형의 VOC가 반복되고 있는지 LLM 추가 호출 없이 판정하고, 그게 실제로 반복 패턴이라고 확정될 때(3건, 6건, 9건처럼 일정 건수마다)만 담당 파트 Teams로 알립니다. 단발성 문의 하나하나에 알림이 계속 뜨면 오히려 담당자가 무뎌지기 때문에, '이건 진짜 반복되고 있는 이슈다'라고 판단됐을 때만 알리는 구조로 설계했습니다. 그 알림 카드 안에는 몇 번째 발생인지, 이미 등록된 해결방안이 있는지까지 같이 붙여서 나갑니다."

## [슬라이드 7-2] 관리자 화면 — 뭘 조정할 수 있는가

### 제목
**로그인·라우팅·폴링·이력, 관리자가 직접 통제한다**

### 본문 내용

| 관리 항목 | 위치 | 조정 가능한 것 |
|---|---|---|
| **인증** | 로그인 탭 | 조직 승인용 자격증명 또는 개인 계정 위임 로그인 |
| **라우팅** | 라우팅 탭 | 담당 파트 ↔ 메일함 ↔ Teams 웹훅 ↔ **조회 대상 폴더**(전체 메일함 또는 특정 폴더로 좁혀 노이즈 원천 차단) |
| **폴링 동작** | 폴링 탭 | ON/OFF, **확인 주기**(몇 분마다 새 메일 확인할지), **재조회 기간**(며칠치를 다시 훑을지) |
| **관련성 임계치** | 폴링 탭 | 등록된 지식과의 유사도가 이 값 미만이면 LLM 호출·알림 없이 스킵 — 값을 올리면 노이즈↓ 놓치는 것↑, 내리면 반대 |
| **반복 패턴 탐지 설정** | 폴링 탭 | 유사도 임계치·판정 기간(일)·최소 발생 건수 — **Teams 발송 여부 자체가 이 조건으로 결정됨**(추가 LLM 호출 없이 기존 임베딩 재사용). 이 최소 건수를 채우기 전엔 알림이 안 나가고, 채운 뒤로는 그 배수(3/6/9건째 등)에서만 "🔁 반복 패턴 — N건째 발생(M건마다 감지·K번째 감지)"로 알림 |
| **이력 확인** | 분석 이력 탭 | 심각도·상태·오배치·키워드로 필터링, 항목 클릭 시 판단 근거·참조 지식 실제 내용까지 조회 |
| **VOC 통계** | VOC 통계 탭 | 유형·심각도 분포 도넛차트(클릭 시 하단 목록 필터링), 반복 클러스터 목록(멤버 수·대표 제목·최근 발생, 페이징), 클러스터별 해결방안 등록 여부를 LLM으로 재검증해 표시하고 그 자리에서 바로 지식 등록 |

**설계 원칙**: 개발자만 이해할 수 있는 화면이 아니라, 실사용자가 직관적으로 조정할 수 있게 — 긴 설명 대신 짧은 라벨, 실패 시 원인+재시도 버튼 안내.

### 발표자 노트
> "관리자가 손댈 수 있는 건 크게 다섯 가지입니다 — 어느 메일함·폴더를 볼지, 얼마나 자주 확인할지, 얼마나 엄격하게 관련성을 판단할지, 반복되는 유형을 어떤 기준으로 잡을지, 그리고 처리된 결과와 반복 통계를 어떻게 확인할지. 특히 관련성 임계치와 반복 패턴 임계치는 값 하나로 '놓치는 것 vs 노이즈' 사이 균형을 관리자가 직접 튜닝할 수 있게 열어뒀고, VOC 통계 탭에서는 지금 어떤 유형이 반복되고 있는지, 그 유형에 대한 해결방안이 이미 등록돼 있는지를 한눈에 보고 없으면 바로 등록까지 할 수 있습니다."

## [슬라이드 7-3] 지금 상태와 추후 확장성

### 제목
**기술은 준비됨 — 남은 건 조직 승인과 확장**

### 본문 내용

**지금 상태**
- 기술적으로 검증 완료 — 전체 파이프라인(수집→필터→분석→반복탐지→알림) 실동작 확인, 실데이터 재검증 완료
- 반복 패턴 탐지 + VOC 통계 대시보드까지 실데이터로 검증 완료 — 클러스터링과 해결방안 커버리지 판정(오탐 방지용 LLM 재검증 포함) 모두 실제 프로덕션 데이터로 재현 확인
- 남은 것: 조직 승인(현재 개인 계정 위임 로그인으로만 동작) · 실제 VOC 메일함 검증(지금까지는 개발자 개인 메일함으로 테스트) · 전용 Teams 채널 확보

**추후 확장성**
| 방향 | 내용 |
|---|---|
| **부서 확대** | 조직 승인(Application 권한) 완료 시 코드 변경 없이 설정만으로 파트별 공용 메일함 전체 확대 |
| **VOC 시스템 직접 연계** | 이메일이라는 중간 경유지 없이 VOC 시스템과 API로 직접 연동 — 상류 키워드 규칙에 의존하지 않는 전수 감지 |
| **관련성 판단 정교화** | 순수 유사도 기반 판단의 구조적 오탐(형식만 비슷한 문서 등) — VOC 반복 유형의 해결방안 판정은 LLM 재검증 게이트로 이미 보강 완료(지금 상태 참고), 채팅 전반의 지식 검색 정확도는 리랭커 도입으로 마저 보강 예정(현재 폐쇄망 이슈로 보류) |
| **다른 알림 채널로 확장** | VOC 메일링과 동일한 구조(수집→필터→분석→라우팅)를 관제 알림 등 다른 채널에도 재사용 |

### 발표자 노트
> "기술적으로는 이제 믿고 쓸 수 있는 수준입니다. 남은 건 조직 승인과 실제 VOC 메일함으로의 파일럿 적용이고요. 확장성 관점에서 보면 이 구조 자체가 VOC 메일에만 묶여있지 않습니다 — 수집·필터·분석·라우팅이라는 같은 뼈대를 관제 알림 같은 다른 채널에도 그대로 재사용할 수 있고, 장기적으로는 이메일이라는 중간 단계 없이 VOC 시스템과 직접 연동하는 것도 로드맵에 있습니다. 참고로 순수 유사도만으로 판단이 흔들리는 문제는 VOC 반복 유형의 해결방안 판정에서 실제로 발견됐었는데, 여기는 이미 LLM 재검증 단계를 추가해서 잡아둔 상태고, 채팅 전체에 걸친 검색 정확도는 리랭커가 들어오면 마저 보강할 계획입니다."
