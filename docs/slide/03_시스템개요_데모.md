## [슬라이드 3-1] KnowledgeRAG — 구조와 동작 원리

### 제목
**KnowledgeRAG — 운영 지식을 AI가 답한다**

### 본문 내용

**무엇을 하는가**
- 사내 운영 문서·절차·FAQ를 등록하면 자연어 질문으로 즉시 답변, 근거 문서까지 함께 제시
- 예: 장애 대응("쿠폰 시스템 장애 시 1차 확인 항목은?") · 운영 절차("배송 지연 처리 프로세스는?") · 도메인 용어("DS가 뭐야?") · 반복 문의("PAY_4023 원인은?")

**어떻게 동작하는가 — ① 등록 · ② 검색·답변 · ③ 개선, 3단계가 선순환 구조로 연결**

```
                [① 지식 등록]  PDF·Excel·Confluence·URL·텍스트
                      (등록 전 미리보기 — Human-in-the-loop)
                              │
                              ▼
사용자 질문
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│  Frontend  (React + nginx) — 채팅 UI · 지식 관리 어드민     │
└────────────────────────┬─────────────────────────────────┘
                         │  REST API / SSE 스트리밍
                         ▼
┌──────────────────────────────────────────────────────────┐
│  Backend  (FastAPI)                                       │
│  [② 검색·답변] 용어 매핑 → 하이브리드 검색(벡터×0.7+키워드×0.3)│◀─▶ PostgreSQL
│  → Top-K 선별 → Few-shot 병합 → LLM 답변 생성(SSE 스트리밍)  │   + pgvector
│  [③ 개선] 로그·피드백(👍/👎) 수집 → 지식 가중치 자동 조정     │   (지식·벡터·로그)
│  → 지식 공백 감지 → 어드민 대시보드 가시화                   │◀─▶ 사내 LLM
└────────────────────────┬─────────────────────────────────┘   (DevX Gateway)
                         │
                         ▼
              자연어 답변 + 근거 문서
```

### 발표자 노트
> "오늘 집중적으로 소개드릴 에이전트가 KnowledgeRAG입니다.
> 구조 자체는 프론트-백엔드-DB로 단순하지만, 핵심은 등록·검색·개선이 하나의 선순환 구조로 연결된다는 겁니다.
> 질문이 들어오면 용어 매핑과 하이브리드 검색을 거쳐 답변이 생성되고, 그 피드백이 다시 지식 품질 개선에 쓰입니다.
> 이 구조를 어떻게 만들었는지 지금부터 하나씩 살펴보겠습니다."

## [슬라이드 3-2] 시연

### 제목
**실제 동작 화면**

### 구성
- **[영상 삽입]** 녹화된 시연 영상 재생 (2~3분)

### 시연 시나리오 (영상 녹화 시 참고)
1. 사용자가 운영 이슈 관련 질문 입력
   - 예: "결제 오류 발생 시 1차 확인 항목은 무엇인가요?"
2. 실시간 스트리밍으로 답변 생성되는 모습
3. 답변 하단의 근거 문서 확인
4. 피드백 버튼(👍/👎) 클릭
5. 어드민 화면: 지식 등록 (파일 업로드 → 청크 미리보기 → 등록)

### 발표자 노트
> "이게 실제로 동작하는 화면입니다. 답변이 나오는 동시에 어떤 문서를 근거로 했는지도 표시됩니다."

## [슬라이드 3-3] 확장 — VOC 메일링, 같은 엔진의 두 번째 활용

### 제목
**KnowledgeRAG 엔진 재사용 — VOC 메일도 같은 방식으로 처리한다**

### 본문 내용

**무엇을 하는가**
- 기존 VOC 시스템에는 이미 키워드 조건에 맞는 건을 파트별 메일함으로 자동 전달하도록 걸어둔 규칙이 있음 — 이 메일함을 우리 시스템이 주기적으로 폴링(수집)해서 가져옴
- 가져온 각 메일을 KnowledgeRAG와 **동일한 검색·분석 엔진**으로 분류·심각도 판정하고 담당 파트 Teams 채널에 자동 알림
- 새 AI를 따로 만든 게 아니라, 채팅에서 검증한 용어 매핑·하이브리드 검색·LLM 판단 로직을 **그대로 재사용** — 기존 VOC 시스템의 1차 키워드 필터링 위에, RAG 기반 2차 지능형 분석·라우팅 레이어를 얹은 구조

**전체 흐름**

```
[VOC 시스템]  키워드 조건 매칭 시 파트별 메일함으로 자동 전달 (기존 설정)
        │
        ▼
[파트별 VOC 메일함]  (voc-payment@, voc-network@ ...)
        │  주기적 폴링 (Microsoft Graph API) — 메일 도착 즉시 다음 폴링 주기에 감지
        ▼
┌──────────────────────────────────────────────────────────┐
│  ① 관련지식 사전 필터                                        │
│  메일 내용과 등록된 지식의 최고 유사도 계산                    │
│  임계치 미달 → LLM 호출 없이 종료(스팸·사내공지 등 무관 메일)   │
└────────────────────────┬─────────────────────────────────┘
                         │ 임계치 이상만 통과
                         ▼
┌──────────────────────────────────────────────────────────┐
│  ② RAG 분석  (KnowledgeRAG와 동일 엔진 재사용)                │
│  용어 매핑 → 하이브리드 검색 → LLM이 분류·심각도·오배치·해결안 판단│
└────────────────────────┬─────────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────────┐
│  ③ 라우팅 · 알림                                             │
│  담당 파트 Teams 채널에 자동 게시 (긴급 시 온콜 담당자 멘션)     │
└──────────────────────────────────────────────────────────┘
```

**지금 어디까지 와 있는가** — 이 흐름 전체가 이미 구현·검증 완료 상태입니다. 개인 계정(Delegated 권한) 기준으로 ①~③ 전 구간을 실제로 동작시켜 확인했고, 남은 건 회사 조직 승인(Microsoft 365 보안성 검토)뿐입니다 — 승인되면 코드 변경 없이 설정만으로 파트별 공용 메일함 전체로 확대됩니다(슬라이드 6 참고).

**지금 버전의 한계 — 솔직하게 짚고 갑니다**
- "선제적 감지"는 **메일함에 도착한 것을 기준**입니다. 상류의 VOC 시스템 키워드 규칙이 놓친 건은 저희도 알 수 없습니다 — 완벽한 전수 커버리지가 아니라, 이미 존재하던 키워드 필터링 경로를 자동화·지능화한 것입니다.
- **한 번도 등록된 적 없는 완전히 새로운 유형의 버그·이슈**는 등록된 지식과 유사도가 낮게 나와 관련지식 사전 필터에서 걸러지거나(관련지식 부족으로 스킵), 통과하더라도 참고할 지식이 없어 분석 품질이 떨어질 수 있습니다 — 이 시스템은 "이미 아는 유형의 문제"를 더 빠르게 감지·전파하는 데 강점이 있는 것이지, 전혀 새로운 유형의 문제까지 알아서 완벽히 잡아내는 건 아닙니다. (지식이 쌓일수록 이 맹점은 줄어드는 구조 — 슬라이드 4의 선순환 참고)
- 장기적으로는 VOC 시스템과 **직접 연계(API)**해서 키워드 필터링이라는 중간 손실 구간 자체를 없애는 게 더 정확한 방향입니다. 지금은 그 전 단계로, 이미 존재하는 이메일 채널을 활용해 빠르게 가치를 검증한 실용적 중간 형태입니다.

**왜 이게 중요한가**
- 슬라이드 4에서 볼 3가지 차별점(등록·이해 / 선순환 / 대시보드)이 **채팅 UI 밖에서도 그대로 통한다**는 걸 증명하는 사례
- 하나의 지식 베이스가 "사람이 질문할 때"와 "메일이 도착할 때" 두 경로 모두에서 근거로 쓰임 — 지식을 두 번 등록할 필요 없음

**실 운영에 적용하면 무엇이 달라지는가 — 핵심은 "선제적 감지"**

기존에는 VOC 시스템의 키워드 규칙에 따라 메일이 우리 메일함에 전달돼도, 누군가 그 메일함을 열어봐야 비로소 문제를 인지할 수 있었습니다 — 메일은 이미 와 있어도 "인지" 자체는 사람이 열어보는 시점에 달려있어 수동적·사후적이었습니다. VOC 메일링 적용 후에는 메일이 도착하는 순간 시스템이 먼저 감지·분류·심각도 판정까지 끝내둡니다 — 사람이 메일함을 열기도 전에 이미 담당자에게 알림이 가 있는, **선제적 대응 체계**로 바뀝니다.

| | 기존 (메일은 와 있어도, 사람이 열어봐야 인지) | VOC 메일링 적용 후 (시스템이 선제 감지) |
|---|---|---|
| 인지 시점 | 메일은 도착해 있지만, 누군가 우연히/뒤늦게 열어봐야 인지 | 메일 도착과 동시에 시스템이 먼저 감지 |
| 분류·전달 | 사람이 읽고 판단해서 담당 파트에 전달 | 도착 즉시 자동 분류 + 심각도 판정 + Teams 알림 |
| 긴급 대응 | 담당자가 메일을 읽어야 비로소 긴급도를 인지 | 심각도 "높음/긴급"이면 온콜 담당자 자동 멘션 — 사람이 열어보기 전에 이미 신호가 감 |
| 오배치 메일 | 잘못 온 메일이 열어보기 전까진 방치됨 | "이 파트로 온 게 맞는지" 자동 판정해 오배치 의심 표시 |
| 무관한 메일(스팸·공지) | 사람이 일일이 열어서 걸러내야 함 | 관련지식 임계치 미만이면 자동 스킵 — LLM 비용·알림 피로도 방지 |

### 발표자 노트
> "기존 VOC 시스템에는 이미 키워드 조건에 맞는 건을 저희 메일함으로 자동 전달하도록 걸어둔 규칙이 있었습니다. 문제는 그 메일이 와 있어도, 누군가 직접 열어봐야 비로소 '아, 이런 문의가 왔구나' 하고 인지했다는 겁니다.
> 지금까지 보신 KnowledgeRAG를 채팅창 밖으로 꺼내면 뭐가 될까 고민하다가, 바로 이 지점에 적용해봤습니다 — 메일함을 우리 시스템이 주기적으로 폴링해서, 사람이 열어보기 전에 먼저 감지하고 분류·심각도 판정까지 끝내두는 겁니다.
> 핵심은 새로운 AI를 또 만든 게 아니라는 겁니다 — 앞서 보여드린 용어 매핑, 하이브리드 검색, LLM 판단 로직을 그대로 가져다 썼습니다. 지식을 한 번만 등록해두면 채팅으로 물어봐도, 메일로 들어와도 같은 지식이 근거가 됩니다.
> 실제 업무 관점에서 보면, 담당자가 메일함을 일일이 열어보지 않아도 되고, 긴급한 건은 사람이 인지하기도 전에 온콜 담당자한테 알림이 갑니다 — '사람이 발견'하는 구조에서 '시스템이 선제 감지'하는 구조로 바뀌는 겁니다.
> 다만 이게 만능은 아니라는 것도 솔직히 말씀드리고 싶습니다. 저희가 감지하는 건 어디까지나 상류 VOC 시스템의 키워드 규칙에 걸려서 메일함까지 온 것들이고, 등록된 지식과 비슷한 게 하나도 없는 완전히 새로운 유형의 이슈는 저희 필터에서도 놓칠 수 있습니다. 지금 이 버전을 '전수 커버'라고 말씀드리면 나중에 신뢰를 잃을 수 있어서, 지금은 '아는 유형의 문제를 더 빠르게 잡아내는 것'까지가 정확한 범위라고 말씀드리겠습니다. 장기적으로는 VOC 시스템과 직접 연계해서 이 중간 손실 구간 자체를 줄여나가는 게 다음 목표입니다."

## [슬라이드 3-4] VOC 메일링 시연 + 비용·노이즈 통제

### 제목
**실제 동작 화면 — 수집부터 Teams 알림까지**

### 구성
- **[영상 삽입]** 녹화된 시연 영상 재생 (관리자 화면에서 폴링 ON → 실제 Teams 채널에 알림 도착까지)

### 시연 시나리오 (영상 녹화 시 참고)
1. 관리자 화면 "VOC 이메일" 탭 — 파트별 메일함 라우팅 등록 화면 확인
2. "폴링 자동화 ON" 토글 (또는 기간 지정 후 "지금 실행")
3. 실시간 상태 카드에 "지금 수집 중..." 표시
4. 처리 완료 후 결과: 수집/분석/관련지식부족(스킵)/발송 건수 표시
5. 실제 Teams 채널에 도착한 알림 카드 확인 (분류·심각도·해결안 초안·온콜 멘션)
6. 관리자 화면 "이력" 탭에서 건별 처리 결과(원본 메일·분류 근거·발송 성공여부) 재확인

**관련지식 임계치로 비용·노이즈를 통제한다**
- 모든 메일을 무조건 LLM에 태우지 않는다 — 등록된 지식과 무관한 메일(스팸, 사내 공지, 참조 메일 등)은 관리자가 정한 임계치 미만이면 LLM 호출·Teams 발송 없이 이력에만 "관련지식 부족" 기록
- 임계치는 관리자 화면에서 실시간 조정 가능 — 우리 데이터에 맞게 튜닝하며 오탐/노이즈를 관리

### 발표자 노트
> "폴링을 켜두면 이후로는 사람이 개입할 일이 없습니다. 메일이 오면 자동으로 분석되고, 관련 있는 것만 골라서 담당 팀 Teams로 바로 알림이 갑니다.
> 여기서 중요한 설계 포인트가 하나 있는데, 모든 메일을 다 LLM한테 보내지 않는다는 겁니다. 우리 지식과 관련 없는 메일까지 분석하면 비용도 낭비고 알림 노이즈만 늘어나거든요. 그래서 등록된 지식과의 유사도를 먼저 계산하고, 임계치를 넘는 것만 실제 분석·알림까지 이어지게 만들었습니다."
