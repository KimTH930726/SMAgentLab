# OpsLens 정확도 구조 개선 — 적용 기술·전후 비교·방법 (2026-10, v2.133~v2.138)

사내 소개용 기술 정리. 각 항목은 **막힌 일(전) → 적용 기술(업계 출처) → 우리 방식(덜어낸 것) → 결과(후) → 한계**로 적는다.
수치는 모두 골든셋 88문항(정책서 3개 파트, 유형 4종: 파라미터 23 · 서술 23 · 탐색 24 · 조건 18) + 답 없는 질문 60개 기준.

## 1. 평가 체계 — "개선됐다"를 말할 수 있는 근거 (v2.137)

**막힌 일.** 88문항을 한 번 돌린 정답률(예: 82%)만 있었다. 같은 설정으로 다시 돌리면 몇 %p씩 흔들렸고(LLM 생성 흔들림),
채점기(로컬 LLM)가 사람과 얼마나 맞는지 잰 적이 없었다. 그래서 "+3%p"가 개선인지 흔들림인지 판단할 수 없었다.

**적용 기술(업계).**
- 오차 범위: Anthropic, Evan Miller, *Adding Error Bars to Evals* (arXiv:2411.00640, 2024). 같은 원문에서 나온 문항끼리 묶어
  군집 표준오차를 쓰고(문항이 서로 독립이 아니므로), 두 설정 비교는 **같은 문항끼리의 차이**로 잰다(짝 비교 — 분산이 크게 준다).
- 반복 측정: 같은 문항을 N번 생성해 문항별 평균(같은 논문의 분산 줄이기 권고 — 문항 안 흔들림을 평균으로 제거).
- 검색 비교: McNemar 정확 검정(같은 문항의 맞음/틀림 짝, 1947).
- 채점기 보정: LLM-as-a-judge(Zheng et al., *Judging LLM-as-a-Judge*, NeurIPS 2023)의 권고대로 사람 라벨과의 일치를 Cohen's kappa로
  (0.6 이상 운영 가능·0.8 이상 우수, Landis & Koch 1977). 사람이 채점기 라벨을 보고 따라가지 않게 **블라인드** 라벨 화면.

**우리 방식.** 표준 라이브러리만으로 `trustkit.eval.stats(libs/trustkit)`(t 분포 임계값, 군집 표준오차, 짝 차이, 카파). 리포트가 자동으로
"정답률 82% (95% 구간 75–89%)", "차이 +2.3%p (−8.9~+13.4) → 오차 안"처럼 판정한다. 채점 기준(rubric)에 판 번호를 달아
다른 기준·다른 날 채점끼리 비교하면 경고(같은 답도 날이 바뀌면 채점이 달라지는 것을 실측 — 기준선은 같은 날 다시 채점).
실서버 시나리오 6개(원장 재등록·동시 확정·컨플루언스 실경로·재질문·후속 질문 캐시·멀티턴)를 저장소에 두고 실행 잠금을 건다.

**결과.** 88문항 1회 측정의 구간 폭이 **±8~10%p**라는 것이 드러났다 — 이보다 작은 개선은 1회 측정으로 주장할 수 없다.
그래서 이후 모든 비교를 "반복 2회 + 같은 날 채점 + 짝 비교"로 한다. 채점기 기준 v3을 사람 판정 6건과 대조해 4건 일치 + 1건은
골든셋 정답 자체의 문제로 확인.

**측정 도구 자체의 결함도 이 과정에서 잡았다.** `--reuse`(바뀐 문맥만 다시 생성)가 반복 측정의 1회차는 문맥이 같아도 매번 새로 생성해,
비용이 두 배이고 안 바꾼 문항에도 흔들림이 섞였다 → 회차별 재사용으로 수정·테스트.

**한계(운영하며 채울 것).** 채점기-사람 카파 실측(블라인드 라벨 필요), 실제 사용자 질문 기반 문항·holdout, 근거 충실도 지표.

## 2. 검색 ① — 조각에 정책명·분류 머리 붙여 임베딩 (R1)

**막힌 일.** 정책서는 LLM이 정책 하나를 의미 조각으로 나눠 조각마다 임베딩한다. 조각은 짧고(중앙값 28자, 예: "최대 20개")
정책명이 들어 있는 조각은 35%뿐이라, 벡터에 "무엇에 대한 값인지"가 없었다. 반면 서술이 없는 항목은 머리를 붙여 임베딩해
한 색인에 두 방식이 섞여 있었다.

**적용 기술.** Contextual chunk header / Contextual Retrieval (Anthropic, *Introducing Contextual Retrieval*, 2024 — 조각에 문서 맥락을
붙여 임베딩하면 검색 실패가 줄어든다). Anthropic 방식은 LLM이 조각마다 맥락 문장을 생성한다.

**우리 방식(덜어냄).** LLM 없이 결정적으로 `"정책명 (분류 > 하위분류): 조각"`. 저장 텍스트·답 문맥은 조각 그대로(임베딩 입력만 바뀜).
가져오기·편집·미분류 편입·정정 승인 네 경로가 같은 함수(`chunk_embed_text`)를 쓴다. 규칙에 판 번호(`CHUNK_EMBED_VERSION`)를 달아,
운영 DB에서 첫 기동 때 기존 조각을 자동으로 한 번 다시 임베딩한다(토큰 0, 그사이 편집된 조각은 덮지 않음).

**결과.** Recall@10 88.6% → 92.0%, 나빠진 문항 0.

## 3. 검색 ② — 정책 항목 단위로 묶기 (R2)

**막힌 일.** 조각 단위 상위 10개를 그대로 쓰면 한 정책의 조각 3개가 3자리를 차지해, 실제로 보는 정책은 10개보다 적었다.

**적용 기술.** 문서 단위 집계(MaxP — 문서 점수 = 가장 가까운 조각 점수, Dai & Callan 2019 *Deeper Text Understanding for IR*;
LangChain ParentDocumentRetriever와 같은 발상).

**우리 방식.** 조각 후보를 3배 가져와 정책 항목마다 최고 조각 하나만 남긴 뒤 상위 10개.

## 4. 검색 ③ — BM25 키워드 채널 + 구제 방식 융합 (R3)

**막힌 일.** 정책 서술은 벡터 검색만 있었다. 드문 고유명사·조건어("투고백에만")는 원문에 글자 그대로 있어도 벡터 순위 71개 중 36위,
금액 표기("3만 원" ↔ "30,000원")는 벡터로도 기존 키워드로도 안 맞았다. 기존 키워드 검색(PostgreSQL `ts_rank`)은 IDF가 없어
드문 단어와 흔한 단어("정책")의 무게가 같다.

**적용 기술.** BM25(Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond*, 2009) + 벡터 하이브리드,
순위 융합 RRF(Cormack et al., SIGIR 2009). Anthropic Contextual Retrieval도 임베딩 + BM25 조합을 쓴다.

**우리 방식.**
- 파트당 정책 수백 건이라 **메모리 BM25**(확장 설치 없음 — 폐쇄망). 표준값 k1=1.2, b=0.75. 정책이 바뀌면 색인을 비운다.
- 한국어 처리: 조사·어미 제거 2회("투고백에만" → "투고백"), 금액 정규화(만·천·쉼표 → 숫자). 데이터에 맞춘 규칙이 아니라 숫자 표기 일반 처리.
- **융합은 RRF가 아니라 "구제" 방식**: 표준 RRF(같은 무게)를 먼저 재 보니 키워드 1위가 벡터 1위를 밀어내 서술형 Top-1이 91% → 65%로
  떨어졌다. 그래서 벡터 순서는 그대로 두고, 벡터 상위 10에 없는 키워드 상위 항목만 아래 3자리에 채운다(1위는 늘 벡터).

**결과(R1~R3 합계).** Recall@10 **88.6% → 95.5%**, Top-1 60.2% → 62.5%. 맞힌 문항 78 → 84(좋아짐 6 · 나빠짐 0, McNemar p=0.031 —
통계적으로 의미 있음). 유형별 Recall: 조건형 83 → 94%, 탐색형 75 → 92%. 답 없는 질문 쪽 신호는 변화 없음.
답 정답률 측면: 검색이 바뀐 19문항만 구제 끔/켬으로 각 2회 생성 A/B → 58% → 76%.

**한계.** 전체 88문항 답 정답률은 2회 평균 77% vs 이전 82%(짝 차이 −4.5%p, 구간 −9.7~+0.6 → 오차 안). 즉 **검색은 확실히 좋아졌지만
답 정답률로는 아직 안 드러남** — 병목이 검색에서 답 생성으로 옮겨갔다(§6).

## 5. 근거 없음 즉시 판정 재보정

**막힌 일.** 근거가 약하면 LLM을 부르지 않고 "관련 지식을 찾지 못했습니다"로 답한다(지어내기 방지). 임계값이 옛 임베딩 기준이었다.

**적용 기술.** Sufficient Context(Joren et al., Google, ICLR 2025 — 문맥이 답하기에 충분한지 판단해 답/보류를 고른다). 우리는 LLM 판정 대신
검색 신호(서술 최고점·파라미터 순위·지식 채택 수)로 싸게 한다.

**결과.** 새 임베딩에서 다시 잼: (0.50, 0.0) → 정답 질문 거짓 거절 **0/88**, 답 없는 질문 즉시 차단 **36/60**.
0.05로 두면 차단 40/60이지만 정답 1건을 거절 — 거짓 거절을 더 나쁜 실패로 보고 0.0.

## 6. 답 생성 — 탐색형·조건형 (v2.138)

진단: 검색 개선 후 실패의 대부분이 "정답 근거가 문맥에 있는데 답이 틀림"(84문항 중 25건).

### 6-1. 탐색형("○○ 정책 전부 보여줘") — 목록 밖 정책을 문맥에서 뺌 + 번호

**막힌 일.** 분류 목록(DB에서 그 분류 정책 전부)은 정답과 개수까지 맞는데(탐색형 24문항 진단), 같은 문맥에 함께 실린 검색 결과(다른 분류
정책 최대 10개)를 LLM이 목록에 섞었다 — 탐색형 오답·부분의 대부분이 "다른 분류 섞임"(q069는 25개 덧붙임). 긴 목록(20개)은 중간을 건너뜀.

**적용 기술.** 메타데이터로 범위가 정해진 질문은 그 범위만 문맥에 둔다(self-query / metadata filtering — LangChain SelfQueryRetriever,
LlamaIndex auto-retrieval). 긴 문맥 중간 누락(Liu et al., *Lost in the Middle*, TACL 2024)은 번호 목록으로 개수를 명시해 줄인다.

**우리 방식.** "전부·목록" 신호(또는 재질문에서 범위 선택) + 분류 목록이 있을 때, 정책 검색 결과 중 **첫 목록 안 정책보다 아래에 섞여 든
목록 밖 정책만** 뺀다. 첫 판은 목록 밖을 전부 뺐는데, 독립 리뷰가 "전체 취소하면 쿠폰은 복원되나요?"처럼 "전체·모든"이 단어로만 든 구체 질문도
목록 답으로 잡혀 1위 정답이 빠지는 결함을 찾아 순위 기준으로 바꿨다(실사고 "문맥을 줄였더니 정답이 통째로 빠짐"과 같은 유형). 인용 카드·근거 판정은
원래 결과. 목록 줄에 1. 2. … 번호.

**결과.** 탐색형 정답률 62% → **75%** (2회 반복 평균, 좋아진 문항 6 · 나빠진 문항 2, 짝 비교 95% 구간 +2.5 ~ +22.5%p — 의미 있는 차이).

### 6-2. 조건형("X에만 따로 적용되는 규정?") — 답 구조 지시

**막힌 일.** 근거가 문맥에 있는데도 "X 전용 규정"이 따로 안 보이면 "관련 지식을 찾지 못했습니다"로 통째로 거절(18문항 중 최대 6),
또는 일반 규정을 X 전용처럼 섞어 답했다.

**적용 기술.** 질문 유형별 지시(query-aware prompting) + 부분 문맥에서 "있는 것·없는 것"을 나눠 답하기(Sufficient Context의 권고 방향).

**우리 방식.** 한국어 한정 표현("에만", "○만 따로/해당/적용/별도", "때만", "경우에만", "전용")이면 문맥 앞에 답 구조:
그 조건에 적용되는 내용(조건이 적힌 규정, 그 조건 값에 해당하는 기준 — 금액 구간·유형 코드·대상 상품)을 먼저, 함께 적용되는 일반 규정은
"공통 적용"으로 구분, 문서에 있는 내용을 두고 "따로 정한 규정이 없다"고 단정하지 않음. 골든 88에서 판별: 조건형 18/18, 다른 유형 1/70
(q006 "판매될 때만" — 실제로 조건 질문). "3만 적용", "전용계좌" 같은 오탐은 규칙에서 뺐다.

**시행착오(이것도 결과다).** 첫 판은 "② 조건 전용 규정이 없으면 없다고 밝혀라"였다. 거절은 6 → 0으로 사라졌지만 오답이 1 → 4로 늘었다 —
"3만 원 넘을 때만?"에 문서의 "30,000원 이상 무료배달"을 두고 "3만 원 초과에만 따로 정한 규정은 없다"고 단정(조건을 글자 그대로 읽음).
"없다" 지시를 빼고 "해당 내용 찾기"로 바꿔 다시 쟀다.

**결과.** 조건형 정답률 58% → **78%**, 거절 8 → 3, 오답 3 → 0 (2회 반복, 좋아진 문항 8 · 나빠진 문항 4).

### 6-3. 통계적으로 말할 수 있는 것 · 없는 것

| | 전 | 후 | 차이 | 95% 구간(짝 비교) |
|---|---|---|---|---|
| 조건형(18문항×2) | 58% | 78% | +19.4%p | 0을 품음(원문 묶음 5개라 넓음) |
| 탐색형(24문항×2) | 62% | 75% | +12.5%p | **+2.5 ~ +22.5 (의미 있음)** |
| 서술형(바꾸지 않음) | 85% | 85% | 0 | −11.0 ~ +11.0 |
| 전체(88문항×2) | 77% | 84% | +6.8%p | −3.6 ~ +17.2 |

- **말할 수 있는 것:** 탐색형 답 개선은 통계적으로 의미 있다(+12.5%p, 구간이 0을 안 품음). 검색 개선(§4)도 의미 있다(p=0.031).
  조건형은 같은 방향으로 크게 좋아졌고 겨냥한 원인 지표(거절 8→3, 오답 3→0)가 줄었다.
- **말할 수 없는 것:** 조건형·전체 정답률 개선이 통계적으로 의미 있다는 것. 조건형 18문항이 원문 5묶음에서 나와 구간이 넓다.
  같은 날 중간 판에선 바꾸지 않은 서술형도 생성 흔들림만으로 85 → 80%까지 움직였다 — 단일 측정 수치를 그대로 믿지 않는 이유.
- **확정하려면:** 반복 횟수 5회 이상, 또는 조건형·탐색형 문항 확충(운영 질의 기록에서 — 사람 검수 필요).

**한계.** 골든셋 조건형 질문이 한 가지 틀이라 실제 질문에선 판별 재현율이 낮을 수 있다(못 잡으면 지금처럼 답할 뿐 — 해가 없는 방향).

## 7. 이번 주기 앞선 변경 (v2.133~v2.136, 요약)

- 탐색형 답 형식 "정책명 — 한 줄 요약"(사용자 결정), 같은 이름 여러 업무면 업무별 묶음.
- 재질문: 주제만 말한 질문 + 정책 20개 초과 → LLM 없이 ①②③ 선택지(Claude Code의 선택형 되묻기와 같은 방식), 대화 맥락은 유지.
- 의미 캐시는 대화 첫 질문만 — 후속 질문에 다른 대화의 답이 나가던 결함.
- 시스템 프롬프트 전수 점검(23개): 과잉 거절 방지 문구(88문항 A/B: 74% → 82%), 요약·분류 전용 프롬프트, 안 쓰는 프롬프트 11개 삭제.
