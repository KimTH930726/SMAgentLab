## 1. 왜 지금(선제적으로) 정리하나

3가지 다 "지금 당장 장애"는 아니지만, 데이터가 쌓일수록/사용자가 늘수록 나중에 손대는
비용이 커지는 유형이다. 특히 접근권한은 스키마 자체를 바꿔야 해서 사용자가 늘고 나서 손대면
마이그레이션 비용이 커진다 — 지금 설계만 고정해두면 나중에 실제 요청이 왔을 때 "처음부터
분석"이 아니라 "이미 정해둔 안 중 하나를 적용"으로 끝난다.

## 2. 현재 상태 실측

### 2-1. 질의응답 감사로그 — "누가 언제 뭘 물었고 뭘 근거로 답했는지"

| 필요한 것 | 현재 상태 | 근거 |
|---|---|---|
| 누가(user_id) | **없음** — `ops_query_log`에 `user_id` 컬럼 자체가 없음 | `init/01-init.sql` (ops_query_log 정의), `backend/main.py:538,545` |
| 언제 | 있음 — `created_at` | `ops_query_log.created_at` |
| 무엇을 물었나/답했나 | 있음 — `question`/`answer` | `ops_query_log` |
| 무엇을 근거로 답했나 | **부분적** — `ops_message.metadata`(JSONB)에 `policy_citations` 등이 남지만 **메시지 단위**일 뿐 사용자와 조인 불가 | `backend/agents/knowledge_rag/agent.py:162,249,295` |
| 사용자 ↔ 질의 연결 | **불가능** — `ops_conversation`은 `user_id`를 갖지만(`init/01-init.sql:142`), `ops_message`엔 `user_id`가 없고 `ops_query_log`도 `conversation_id`/`message_id`로 조인해도 최종적으로 user까지 안 이어짐(경로 불완전) | `ops_message` 스키마, `ops_query_log` 스키마 |

**결론**: "질의응답 감사로그가 저장 안 됨"은 정확한 진단이다. 조각(질문/답변/시각/근거)은
여기저기 있지만, 사용자 한 명을 축으로 "이 사람이 이 시각에 이걸 물었고 이 근거로 이 답을
받았다"를 재구성할 조인 경로 자체가 끊겨 있다.

### 2-2. 접근권한 세분화 — "AI Read/Write 계정 분리까지만, 사용자·부서별 조회범위 제한 없음"

- 실제 역할은 `admin` / `user` 단 2단계뿐(`ops_user.role`, `backend/main.py:85`). 그 사이 단계(예:
  조회만 가능한 뷰어, 특정 파트만 보는 매니저) 없음.
- 스코핑은 **파트(part) 단위**로만 존재한다 — `check_namespace_ownership()`/`check_part_ownership()`
  (`backend/core/dependencies.py:76-113`)가 `namespace.owner_part_id`와 사용자의 `part_id`를
  비교해 "같은 파트=쓰기 가능, 다른 파트=읽기만, 공용 네임스페이스=전체 열람"을 결정한다.
  프론트 `useNamespaceAccess`(`frontend-react/src/utils/useNamespaceAccess.ts:42-43`)도 동일
  규칙을 그대로 반영할 뿐 별도 세분화가 없다.
- **"AI Read/Write 계정 분리"는 실제로 존재하지 않는다** — 전체 백엔드가 단일 DB 자격증명
  (`DATABASE_URL`, 기본 `ops`/`ops1234`)을 쓴다(`docker-compose.yml:9-10,43`, `core/database.py`).
  읽기 전용 DB 계정 자체가 없다. TODO 문구의 "AI Read/Write 계정 분리까지만"은 실제로는
  아직 그 단계에도 못 미친 상태 — **현재는 파트 단위 애플리케이션 레벨 권한만 있고, DB
  레벨 권한 분리는 전무**로 정정.
- 파트 **내부**에서 사용자별로 더 세분화할 방법이 없다 — 같은 파트 소속이면 그 파트가 소유한
  모든 네임스페이스에 전원이 동일한 쓰기 권한을 갖는다.

### 2-3. 데이터 보존·삭제 정책 — "챗 로그 민감정보 보존기간 미정"

| 테이블 | 현재 삭제/보존 규칙 | 근거 |
|---|---|---|
| `ops_query_log` | `status='resolved'`이고 90일 지난 것만 삭제(`cleanup_resolved_query_logs()`) — `unresolved`/`no_knowledge`/`pending`은 영구 보존 | `backend/service/chat/helpers.py:22,135-144` |
| `ops_message`/`ops_conversation` | 시간 기준 보존정책 **없음**. 네임스페이스당 메시지 100건 초과 시 오래된 것부터 잘라내는(`cleanup_old_messages()`) 저장용량 캡만 있음(`trimmed=TRUE` 표시) | `helpers.py:21,99-132` |
| 둘 다 | 정리 자체가 크론이 아니라 채팅 요청에 5% 확률로 얹혀 실행(`CLEANUP_SAMPLE_RATE=0.05`) — "스케줄러 인프라가 없어서"라고 코드에 명시 | `helpers.py:23` |
| 원문 저장 형태 | `ops_message.content`는 평문 TEXT, 만료 없이 영구 저장(위 100건 캡 외엔 삭제 트리거 없음) | `init/01-init.sql:157` |

참고로 **VOC 이메일 도메인에는 이미 진짜 보존정책이 있다** — `service/email_voc/retention.py`
(`RETENTION_DAYS=30`)가 `scheduler.py`의 실제 타이머로 주기 실행된다(`backend/main.py:1209,1212`).
즉 "스케줄 기반 보존정책"을 프로젝트가 모르는 개념이 아니라, **채팅/질의 로그 도메인에만
아직 적용을 안 한 것** — 새로 발명할 필요 없이 기존 패턴을 재사용하면 된다.

**결론**: "챗 로그 민감정보 보존기간 미정"은 정확하다 — 답변에 포함될 수 있는 정책 원문
(민감할 수 있는 사내 데이터)이 시간 제한 없이 평문으로 쌓인다.

## 3. 설계 옵션

### 3-1. 감사로그

**A안(최소, 스키마 변경 작게)**: `ops_query_log`에 `user_id INT REFERENCES ops_user(id)` 컬럼만
추가하고, 질의 처리 시점(`chat/helpers.py`의 `create_query_log()` 호출부)에 현재 인증된
`user["id"]`를 같이 저장. `ops_message.metadata`의 `policy_citations`/`results`는 이미 있으니
새로 안 만들어도 됨 — `message_id`로 조인해서 "이 사용자가 이 시각에 이 질문을, 이 근거로
받았다"를 재구성 가능해짐. 코드 변경 지점이 정확히 한 곳(`create_query_log()` 호출부에 인자
하나 추가)이라 리스크가 작다.

**B안(뷰까지)**: A안 + `ops_query_log ⋈ ops_message.metadata ⋈ ops_user` 조인을 미리 SQL 뷰나
관리자 API 하나로 고정해서, 나중에 거버넌스팀이 "이력 좀 보여달라"고 할 때 즉시 응답 가능한
형태로 준비. A안 없이는 만들 수 없어서 순서상 A안이 선행.

**권장**: A안 먼저(비용 작고 나머지 전부의 전제조건), B안은 실제 요청 시점에.

### 3-2. 접근권한 세분화

현재 "파트=권한 단위"는 나쁜 설계가 아니다(조직 구조와 일치, `owner_part_id` 하나로 단순).
문제는 **파트 내부에서 더 좁힐 방법이 없다는 것** — 같은 파트원 전체가 항상 동일 권한.

- **A안(역할 추가, 스키마 작게)**: `ops_user.role`에 제3의 값(예: `viewer`) 추가 — 같은 파트
  소속이어도 조회만 가능한 사람을 만들 수 있게. `dependencies.py`의 이진 `admin` 체크를
  3단계 체크로 확장.
- **B안(네임스페이스별 개인 권한 테이블)**: `ops_namespace_user_access`(namespace_id, user_id,
  level) 같은 조인 테이블을 신설해 "이 사람만 이 네임스페이스 제외/포함" 수준까지 세분화.
  현재 실 사용자 수·요청 빈도로는 과설계 가능성 — **실제 요청(예: 특정 파트 내 특정 인원만
  민감 네임스페이스 보게 해달라)이 나온 뒤 착수**를 권장(이 프로젝트의 기존 YAGNI 원칙과
  일치).
- **DB 레벨 read-only 계정**: 애플리케이션 권한과 별개로, 백엔드가 쓰는 DB 계정 자체를
  read-only/read-write 두 개로 나눠서 "애초에 실수로 쓰기 안 되는" 레이어 하나를 더 두는 안.
  지금은 이것도 전무 — 인프라 변경(compose 파일에 계정 2개 추가, 라우터별 커넥션 풀 분리)이
  필요해 규모가 있음. 거버넌스팀이 "DB 레벨 통제"를 구체적으로 요구할 때 착수.

**권장**: 지금은 A안만 최소 스캐폴딩(role enum에 값 추가 정도), B안/DB 레벨 분리는 실 요청
전까지 보류.

### 3-3. 보존·삭제 정책

기존 `email_voc/retention.py` + `scheduler.py` 패턴을 그대로 재사용(새 스케줄러 프레임워크
불필요):

- `ops_message`/`ops_conversation`에 `RETENTION_DAYS` 상수 도입(민감도 감안해 VOC의 30일보다
  길게 잡을지, 챗봇 답변 특성상 90일(`ops_query_log`의 기존 90일 기준과 통일)로 맞출지는
  거버넌스팀 확인 필요 — 임의로 정하지 않음).
  하지만 이걸 `ops_query_log`처럼 "확률적으로 요청에 얹어" 처리할지, VOC처럼 진짜 스케줄러로
  뺄지는 선택 필요.
- `ops_query_log`의 `unresolved`/`no_knowledge`/`pending` 상태도 지금은 영구 보존인데, 이것도
  "미해결로 남아 계속 참고해야 하는 데이터"라 보존과 삭제 기준이 다르게 필요(해결 안 된
  질문은 오래 남겨야 지식 공백 파악에 쓸 수 있음 — 무조건 짧게 자르면 안 됨, 이 문서 §2-3과
  [[project_common_platform_roadmap]]의 지식 공백 논의가 여기서 만남).

**권장**: 보존기간 숫자 자체는 이 문서에서 확정하지 않는다 — 실제 민감도 판단은 거버넌스팀
몫. 대신 "숫자만 정해지면 바로 꽂을 수 있는 재사용 가능한 스케줄러 패턴이 이미 있다"는 것과
"상태별로 보존 기준이 달라야 한다(해결됨 vs 미해결)"는 설계 원칙만 여기 고정해둔다.
