# 관리자 화면 구조 — 도메인 경계(DDD)대로 다시 나누기 (설계안, 2026-10-20, 검수 대기)

> 상태: **검수 완료(10/21) — 단계별로 만든다.** 검수 결과: 메뉴 순서 업무 영역 → 지식, 정정 요청은 품질로, 담당은 파트별 체크(1:N),
> 다른 파트 지식도 조회 가능, 품질에 검증(정확도 측정·골든셋)까지, 순서 §5대로.
> 처음 상태: **설계안 — 화면은 사용자 검수 뒤에 만든다.** 계기: 기준정보관리 한 화면에 업무 영역 목록·업무구분·상위 묶음·담당 매핑이 섞였고,
> 검수 없이 넣은 선택 칸을 클릭 한 번에 바꿔 쿠폰이 다른 묶음으로 옮겨졌다(사용자 10/20 "기준정보관리에 너무 다 때려박아놨어").

## 1. 지금 막힌 일

| 지금 화면 | 섞여 있는 것 | 문제 |
|---|---|---|
| 기준 정보 관리 | 업무 영역 목록 + 업무구분(지식 하위 분류) + (v2.142에 넣었다 뺀) 상위 영역·담당 파트 칸 | 영역 16개 중 13개는 업무구분이 비어 있음. "어떤 영역이 있나"와 "지식을 어떻게 나누나"와 "누가 맡나"가 한 줄에 |
| 지식 베이스 | 지식 목록·등록·검토 + **정정 검토**(정책 정정까지) | 정정은 지식·정책 공통인데 지식 탭 안에 있음 |
| 용어집 | 영역별 용어 | 정책서 용어(712)와 사람 등록 용어가 구분만 되고 위치는 같음 — 괜찮음 |
| 정책 | 항목·미분류 집계·올리기(엑셀/붙여넣기) | v0(통째 원문) 기준이 아님 — 참고표·개요·원문 확인 없음, 엑셀 경로는 v0 영역에서 막힘 |
| 통계 / 평가 게이트 / VOC / 시스템 설정 / 캐시 / 사용자 관리 | 각자 | 사용자 관리에 파트 CRUD가 같이 있음, 담당 매핑 자리 없음 |

## 2. 원칙

1. **메뉴 하나 = 도메인 경계(bounded context) 하나.** 한 화면에서 다른 경계의 데이터를 고치지 않는다(보여 주는 건 링크로).
2. **경계 사이 연결(담당 매핑 같은)은 "주인" 쪽에 둔다** — 담당은 사람 조직의 책임이라 조직 쪽(사용자 10/20).
3. **유형별 화면은 같은 업무 영역 선택기를 쓴다**(A안 유지) — 고르는 기준은 하나, 할 일은 유형마다.
4. **사람이 고르는 칸 없음 — 사람은 최종 승인만**(§5-2). 업무구분은 없앤다(P2 결정, 정확도 게이트로 전·후 확인).
5. **설정을 바꾸는 칸은 이름표·확인 필수, 즉시 저장 금지**(10/20 사고).
6. 업계 기능 목록을 옮기지 않는다 — 지금 실제로 쓰는 것만(MVP), 나머지는 "다시 볼 조건".

## 3. 경계와 메뉴 (제안)

```
관리자   (순서 = 일하는 흐름: 업무 영역을 고르면 → 그 영역의 지식이 세팅된다)
├ 업무 영역 ─────── (업무 영역 목록: 무엇이 있나) — 여기서 고른 영역이 지식 화면의 기본 선택으로 이어진다
│     영역 만들기·이름·삭제(관리자) · 영역별 유형 개수(정책 n · 지식 n · 용어 n — 누르면 그 유형 화면으로)   ops_namespace
│     P2: 하위 업무(외부서비스 > 배민·쿠팡)를 트리 단계로 — 실사용(하위 포함 검색) 생길 때
├ 지식 ─────────── (지식 자산: 업무 영역 선택기 공통, 조회는 누구나·수정은 담당 파트)
│  ├ 정책서        정책 · 참고표 · 개요 · 원문 확인(담당자 질문) · 검토 대기       policy_item·ref_table·policy_doc_overview·ops_link
│  ├ 지식 문서     목록 · 등록(컨플루언스 등) · 검토 대기                          rag_source_document·rag_knowledge
│  ├ 용어집        용어 · 동의어 (출처 표시: 정책서/사람/AI)                         rag_glossary·rag_glossary_synonym
│  └ 시스템 정보   DB 칼럼 · 공통코드 (P2에서 업무구분 "DB·공통코드" 흡수)          ref_db_column·ref_common_code
├ 조직 ─────────── (사람과 책임: 누가 맡나)
│  ├ 사용자        목록 · 가입 승인 · 역할 · 소속 파트                              ops_user
│  ├ 팀·파트       팀 > 파트 만들기·이름 (팀 편집은 조직 확정 때)                  ops_team·ops_part
│  └ 담당 업무 영역 파트별 담당 영역(1:N) — [변경] → 영역 체크 + "이 파트가 수정하게 됩니다" 확인    ops_namespace.owner_part_id  ✅ ①(10/21, 지금은 사용자 관리 탭 안)
├ 품질 ─────────── (결과 보고 바로잡기 + 검증)
│     통계(질의·지식 공백) · 정정 요청(지식·정책 공통, 지금은 지식 탭 안) · 평가 게이트 · 정확도 측정(골든셋)    ops_query_log·ops_improvement_item·eval_*
├ VOC 이메일 ────── (수집 채널 — 따로 도는 파이프라인)
└ 시스템 ───────── LLM(사내/로컬) · 프롬프트 · 검색 기준값 · 캐시                     관리자
```

## 5. 순서 (작게 나눠서, 단계마다 검수)

1. ✅(v2.144) **조직 > 담당 업무 영역** — 지금 담당을 바꿀 화면이 없어 가장 먼저(API는 있음: `PATCH /api/namespaces/{name}/settings`).
2. ✅(v2.145) **메뉴 묶기만** — 화면 내용은 그대로 두고 위 트리로 자리만 옮김(정정 요청 분리 포함). 문구 "파트"→"업무 영역"(데이터 화면).
   모양: 왼쪽 아코디언(사용자 10/21 — 항목 15개쯤이라 위 탭 두 줄보다 위치가 잘 보이고, 비어 있던 사이드바를 쓰고, 업무 영역 선택기를 메뉴 바로 위에).
   하위 하나인 묶음은 바로 이동, 지금 묶음은 늘 펼침, 펼친 상태 기억. 화면 안 업무 영역 선택기는 남겨 둠(값은 공용) — ③에서 정리.
3. ✅(v2.146) **업무 영역** 화면(목록 + 유형 개수) — 기준 정보 관리 대체. 화면 안 선택기 제거(사이드바 하나).
4. **업무구분 폐지**(P2) — 골든셋으로 전·후 측정 뒤.
5. **정책서** 화면 v0 기준(참고표·개요·원문 확인).

## 5-1. 지식의 보관 위치 — 업무 영역 + 조직 공간 (결정 10/21, 설계안은 따로)

컨플루언스 운영 노하우(배포 방법·장애 대응 등)는 업무 영역 하나에 안 맞고, 팀·파트 단위 노하우도 있다(사용자 10/21). 업계는 "보관·책임은
하나, 주제 꼬리표는 0개 이상"으로 나눈다 — Confluence(팀 공간 + 공용 참고 공간, 라벨), DataHub(도메인 1 + 태그·용어 N), Backstage(ownedBy 그룹),
Guru(묶음 책임자·검증자).
- 보관 위치 두 종류: **업무 영역**(그 업무 지식, 담당 = 매핑된 파트) / **조직 공간**(팀 공통·파트 노하우, 담당 = 그 팀·파트 자신)
- 채팅: 고른 업무 영역 + 내 팀·파트의 조직 공간 — 검색이 바뀌므로 골든셋 전·후 측정 뒤에 켠다
- 등록: 보관 위치는 AI가 정하고 사람은 승인만(§5-2). 컨플루언스 공간 → 보관 위치 매핑은 AI 판단의 단서
- 보류: 업무 영역 꼬리표 0..N(사람이 달면 나빠짐 — 사례가 쌓이면 AI가 달고 사람이 고침)
- 지금 "팀 공통"이 업무 영역인 척 쓰이는 것이 이 문제의 증상 — 조직 공간으로 옮긴다
- 실사용 후 볼 것: 등록 분포(한쪽 쏠림?), 채팅 근거에 조직 공간이 실제로 쓰이는지

## 5-2. 등록은 창구 하나 — AI가 정하고, 사람은 최종 승인만 (원칙 10/21, 전체 기능 공통)

사람의 선택을 믿지 않는다 — 사람은 최종 승인만 한다(사용자 10/20·21). 지식은 유형별 메뉴로 나눠 들어가 등록하지 않고 **한 창구**로 넣는다
→ AI가 유형(정책·지식 문서·용어·시스템 정보)·보관 위치(업무 영역/조직 공간)·연결까지 **한 안**으로 정한다 → 사람은 **승인 / 반려**만.
반려하면 사유 한 줄 → AI가 다시 판단해 새 안. 사람이 후보를 고르거나 칸을 직접 고치는 단계는 두지 않는다.
정정 요청(답변 틀림 한 줄 → AI 분석 → 승인)이 이미 이 모양이고, 용어·연결·담당자 질문도 같은 모양으로 설계한다. 지금 지식 화면 안의
"지식 등록"(영역을 먼저 고르고 넣음)은 이 창구로 바뀔 자리 — 조직 공간 설계와 묶어 설계안을 먼저 보인다.

- **선택지 핑퐁**(사용자 10/21, 최적화할 수 있는 곳에만): AI가 버튼 선택지를 내고 누를 때마다 다시 다듬는다 — 예: "딜리버스 업무 같아요 —
  [맞아요] [외부서비스예요] [팀 공통이에요]", "이렇게 다듬으면 검색이 더 잘 돼요 — [제목 바꾸기] [단계로 나누기] [그대로]" → 최종안 → 승인.
  사람은 입력·검색 없이 누르기만(귀찮으면 안 쓴다). AI가 확신하면 바로 승인 단계로. 채팅 되묻기(v2.133 clarify) 장치를 재사용한다.

## 5-3. 지금 화면 중 원칙(§5-2)과 맞지 않는 곳 — 단계별로 바꾼다 (점검 10/21)

| 화면 | 지금 사람이 하는 일 | 바뀔 모양 | 단계 |
|---|---|---|---|
| 지식 등록 | 업무 영역·업무구분을 고르고 넣기 | 단일 창구 → AI가 유형·보관 위치를 정한 안 → 승인 | 조직 공간 설계와 함께 |
| 지식 수정 | 업무구분 고르기·본문 직접 고치기 | 업무구분 칸 없앰, 본문은 수정 제안 → AI 정리 → 승인(정책과 같은 방식) | ④ + 이후 |
| 지식 일괄 수정·업무구분 관리 | 업무구분 바꾸기·만들기 | 없어짐 | ④ |
| 용어 등록 | 용어·설명 직접 입력 | AI가 뽑은 용어 안 → 승인(자동 추출은 이미 있음) | 용어집 개편 |
| 정책서 붙여넣기 | 업무 영역·정책서·시트 고르기 | v0 영역에선 막힘 — 정책서 화면에서 정리 | ⑤ |

사람이 정하는 게 맞는 곳(그대로): 담당 업무 영역 매핑·팀·파트·사용자 승인·VOC 메일함·시스템 설정 — AI 판단 대상이 아니라 조직·운영이 정하는 사실.
업무구분은 검색 분기(`_KEYWORD_ONLY_CATEGORIES` — DB·공통코드는 키워드만)가 쓰고 있어 골든셋 전·후 측정 뒤에 없앤다.

## 6. 안 하는 것 + 다시 볼 조건

- 상위 묶음(혜택·주문 등) — 실사용·관리 주체 없음(10/20 뺌). 다시 볼 조건: 영역이 많아져 목록 탐색이 실제로 불편하거나 묶음 단위 채팅 범위가 필요할 때.
- 팀 편집 화면 — 팀 1개. 조직 확정(인프라 이관) 때.
- 출처 → 영역 자동 매핑(예: 컨플루언스 공간) — 반복 등록 사례가 쌓이면.
- 담당 상속(상위 담당이 하위도) — 하위 업무 트리(P2)가 생길 때 같이.
