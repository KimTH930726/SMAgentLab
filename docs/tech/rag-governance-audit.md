## 1. 한 줄 결론

검색·저장 계층(RRF 하이브리드, PG+pgvector 단일 스토어, INSERT-only 버전관리)은 프로젝트
규모에 비해 탄탄하지만, "누가 이 지식을 볼 수 있는가"가 쓰기 경로에만 답이 있고 읽기(채팅)
경로에는 없었다 — 유일한 P0.

## 3. P0~P3

- **P0**: 채팅 경로 네임스페이스 읽기 ACL 부재 → §5-③ 로그온리로 1차 대응, 강제 전환은 실측 후.
- **P1**: 판정 계층 부재, 클레임 검증 부재, 미검토(pending_review) 정책 콘텐츠 무필터, 외부 API 민감데이터 통제 부재.
- **P2**: 검색 재시도 없음, 골든셋 단순(적대적 케이스 없음), 평가지표 검색뿐, 배포 게이트 없음, 문서충돌 탐지 없음, 감사로그 provider/latency 없음.
- **P3**: UserContext 추상화 부재, Provider 인터페이스 분리 미흡, 부모/인접 문맥 확장 없음.

## 4. 레드팀 검토 — 원래 계획의 맹점

1. **"미검토 정책 필터링"은 저비용이 아니다.** `policy_item`은 `active`/`approved` 상태 자체가 코드 어디서도 부여되지 않음 — 필터링을 그대로 걸면 정책 검색 결과가 100% 사라짐. 승인 워크플로우 신설이 먼저 필요(별도 프로젝트급).
2. **읽기 ACL을 강제모드로 바로 켜면 안 된다.** 실제 정당한 cross-part 사용 패턴이 있을 수 있어, `_KEYWORD_ONLY_CATEGORIES` 때처럼 로그온리 → 실측 → 강제 전환 순서를 지켜야 함.
3. **ACL만 고치면 "누가"는 막아도 "틀린 답"은 그대로 나간다.** 판정 계층과 별개 문제.
4. **판정 계층/클레임 검증을 서둘러 조악하게 만들면 신뢰를 깎는다.** 이 프로젝트엔 마찰 있는 기능이 방치된 실증 사례(few-shot 큐)가 있음 — 반드시 골든셋 파일럿 선행.
5. **오늘 만든 `viewer` 역할을 "하네스 대비"로 오해하면 안 된다.** 액션 레이어가 붙으면 권한 모델 축 자체가 바뀜 — 오늘 것은 오늘 문제를 푼 것일 뿐.

## 5. 우선순위 재조정 + 일정

| 순서 | 작업 | 축 | 상태 |
|---|---|---|---|
| 1 | category_path LLM 컨텍스트 포함, 임베딩 staleness 감지 | B | **완료(v2.95)** |
| 2 | 읽기 ACL 로그온리 → 실측 → 강제 전환 | A | 로그온리 **완료(v2.95)**, 강제 전환은 실측 후 |
| 3 | 정책 최소 승인 워크플로우 신설 | B | 미착수 |
| 4 | ABSTAIN 임계값 오프라인 파일럿 → 실사용 노출 | C | 파일럿 **완료(v2.95, 0.4가 안전 후보)**, 실사용 노출은 미착수 |
| 보류 | 인젝션 방어 고도화, Provider 라우팅, Release Manifest, 배포 게이트 | C 일부, D | 실 수요 시 |

**제외 결정**: `rag_knowledge.supersedes_id` 연결은 착수 전 재검토 결과 제외 — 컨플루언스 재수집이 페이지 단위 배치(구버전 N개 deprecate, 신버전 M개 삽입, N≠M 가능)라 단일값 FK로 1:1 계보를 안전하게 만들 방법이 없음. 검색 정확성은 이미 `status='deprecated'`로 보장되고 있어 급하지 않음 — B축 항목으로 재분류.

## 6. 명확히 좋아지는 지점 vs 트레이드오프 있는 지점

**부작용 없이 좋아짐(오늘 실행)**: category_path 포함, 임베딩 staleness 감지, 읽기 ACL 로그온리, ABSTAIN 오프라인 파일럿.

**좋아지지만 대가 있음(단계적 진행 필요)**: 읽기 ACL 강제 전환(정당한 cross-part 사용 차단 위험), 정책 승인 워크플로우(검토 마찰 → 방치 위험), ABSTAIN 실사용 노출(과도하면 신뢰 하락).

**해봐야 아는 것(지금 판단 근거 없음)**: Provider 데이터등급 라우팅(분류 기준 자체가 없음), 인젝션 방어 엄격도(정상 운영문서 오탐 가능성 실측 필요).
