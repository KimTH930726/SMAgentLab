## 2. 용어 (10/22 확정)

| 말 | 뜻 | 코드·DB 이름(그대로 둠) |
|---|---|---|
| **컬렉션** | 지식을 두는 곳. 지식 하나는 컬렉션 **하나**에만 있다 | `ops_namespace` |
| **업무 컬렉션** | 그 업무·시스템에 대한 지식(옛 "업무 영역"). 상위 › 하위 1단 트리 | `kind='domain'`, `parent_id` |
| **조직 컬렉션** | 어느 업무에도 안 묶이는 팀·파트의 노하우(옛 설계명 "조직 공간"). 팀 공통 / 파트 | `kind='org_space'`, `owner_team_id` / `owner_part_id` |
| **보는 컬렉션** | 사이드바에서 지금 고른 것(채팅·화면 범위) | `useNamespace` |

기각한 말: 공간(추상적)·저장소(지식 종류와 겹침·git)·팀 공간(파트까지 부르기엔 넓음)·지식 베이스(에이전트 이름)·묶음(VOC 묶음과 겹침).
화면 문구만 바꾼다. 업계 용례: Guru Collections, Microsoft Purview Collections(둘 다 "지식·자산의 집합 + 책임자").

**담을 수 있는 것**: 업무 컬렉션 = 정책·지식 문서·용어·시스템 정보 / 조직 컬렉션 = **지식 문서·용어만**(정책·시스템 정보는 업무에 붙는 것).

## 3. 메뉴 구조

```
관리자 메뉴
 ├ 지식      (정책서 · 지식 문서 · 용어 · 시스템 정보)   ← 보는 컬렉션 범위가 적용됨
 ├ 컬렉션 ▸ 업무   (트리 표: 상위 › 하위, 담당 파트, 유형별 개수)
 │        ▸ 조직   (팀 공통 · 파트별, 개수)            ← 담당 = 그 팀·파트 자신(매핑 불필요)
 ├ 조직      (사람 · 팀·파트 · 담당 업무 매핑)        ← 사람·권한만. 지식 없음
 ├ 품질 · VOC · 시스템
```
업무·조직은 **메뉴(화면)로 나눈다**(한 표에 필터로 섞지 않음 — 다루는 칸이 다르다: 업무는 담당 매핑·하위, 조직은 팀·파트에서 자동 생성).

## 4. 판정 기준 — 이 지식은 어느 컬렉션인가 (10/22 확정)

**기준 하나: "무엇에 대한 지식인가."** 쓴 사람·쓰는 팀이 아니다.

**바꿔 넣기 시험**
1. 본문의 업무·시스템 이름을 **다른 업무 이름으로 바꿔 넣는다.**
   - 그래도 맞으면 → **조직 컬렉션**(그 업무 고유 지식이 아님)
   - 틀려지면 → **그 업무 컬렉션**(노하우·절차여도 특정 시스템 절차면 업무)
2. 조직이면, 파트 이름을 다른 파트로 바꿔 넣는다. 그래도 맞으면 **팀 공통**, 틀려지면 **그 파트**.
3. 업무면, 하위가 있고 하위 이름을 바꿔 넣으면 틀려질 때만 **그 하위**. 아니면 상위.

**여러 업무에 걸침** = 가장 많이 다루는 **주 업무 하나** + 나머지는 연결(`ops_link`, `knowledge → domain`, relation `also_about`). 복사하지 않는다.
**두 파트만 공통**(같은 팀) = 팀 공통에 둔다(2단계 시험에서 "두 파트 이상에 맞으면 팀 공통"). 조회는 원래 다 열려 있어 다른 파트에 보여도 손해가 없다.
**연결의 지금 상태(10/22 확인)**: `ops_link`는 종류 무관 범용 표라 저장은 지금도 된다(정책→용어 2062건 등). 하지만 **지식→컬렉션 연결은 0건이고,
채팅 검색은 연결을 읽지 않는다** — 연결만 걸면 다른 컬렉션에서 물었을 때 안 나온다. 그래서 규칙을 정한다: 연결된 지식은 연결된 컬렉션 검색에도 포함한다.
구현은 실제 연결 사례가 생길 때(지금 0건) — 검색이 바뀌므로 전·후 게이트.
**애매하면** 넣는 사람에게 **한 번만** 묻는다(버튼). 그래도 모르면 1순위로 두고 "애매" 표시 → 승인자가 본다.

**관리 — 기준이 두 군데서 어긋나지 않게**
- 기준 본문은 이 절과 등록 AI 프롬프트 **한 곳**에만 둔다(프롬프트가 이 절을 그대로 쓴다).
- **경계 사례 판정 예시**(아래 20개, 가상)는 프롬프트 예시 겸 측정 문항. 사람이 바로잡은 실제 사례를 계속 더한다.
- 두 위치가 다 필요한 실제 사례가 3건 넘게 쌓이면 꼬리표(0..N)를 다시 본다(§9).

**경계 사례 판정 예시 (가상 — 실제 문서 아님)**

| # | 지식(제목 수준) | 판정 | 왜 |

## 5. 하위 컬렉션 — "뭔가 달라질 때만" (10/22 확정, 숫자는 추천값)

하위는 검색 정확도를 올리지 않는다(§1). 그래서 **관리가 실제로 달라질 때만** 만든다.

| 규칙 | 내용 |
|---|---|
| 기본 | **하위 없음**, 깊이 1(하위의 하위 없음) |
| 만들 자격(모두) | ① 원천 구조가 있다(컨플 상위 페이지·정책서 1단 묶음 등) ② 거기 사용 중 지식 **20건 이상** ③ 담당이 다르거나, 그것만 묻는 질문이 실제로 있다 |
| 상한 | 상위 하나에 하위 **5개** |
| 합치기 | 하위가 **5건 미만으로 30일** → 상위로 합치기 제안 |
| 등록 때 | **이미 있는** 컬렉션에 배치만. 맞는 하위가 없으면 상위. 컨플 상위 페이지명은 출처로 기록만 — **등록 때 하위 생성·생성 제안 없음** |
| 생성 경로 | **하나뿐**: 정기 점검(월 1회)이 원천 구조별로 세어 자격 충족 시 제안 1건 → 관리자 승인 |
| 관리자 수정 | 수정 창의 "상위" 칸은 보정용(평소에 쓰는 칸 아님) |

지금 자격 충족: 제휴서비스 › **배달의민족 · 쿠팡이츠**뿐(활성 24·22). 땡겨요·네이버·카페이는 지식 0이라 미달 → 상위에 둔다.
**고칠 곳**: category-removal-design §3 "등록자가 하위 영역을 골라 넣는다" → 위 "등록 때" 줄로 바꾼다.

## 6. 선택기 — 보는 컬렉션

**모양** = org-space-design §5 **2안**(사이드바 맨 위 칩 + 고르는 창, 검수 완료). 묶음: 최근 · 내 담당 · 조직 · 전체(하위는 상위 아래 들여쓰기).

**규칙**
| # | 규칙 | 상태 |
|---|---|---|
| S1 | 업무 상위를 고르면 하위까지 검색. 하위를 고르면 그 하위만 | 확정(C1 구현됨) |
| S2 | 채팅 지식 범위 = 고른 업무 컬렉션 + **질문한 사람의** 조직 컬렉션(내 파트 + 내 팀 공통). 내 파트가 담당하는 업무 **전부는 아님** | 확정. 설정 `chat.org_space_scope` 기본 꺼짐, 측정 뒤 켬 |
| S3 | 정책 범위는 지금처럼 정책 있는 업무 전부(`policy/scope.py`) | 그대로 |
| S4 | **처음 들어왔을 때 기본 = 내 담당 업무 자동 선택**(담당 여러 개면 지식 많은 것, 없으면 첫 업무). 전체 검색은 하지 않는다(§1 표) | **결정 대기** |
| S5 | 고른 값은 새로고침해도 유지(브라우저 저장, 실패해도 S4 기본으로) | 제안(지금은 새로고침하면 사라짐 — 결함) |
| S6 | 테스트용 컬렉션(`kind='policy_test'` 등)은 선택기·채팅·목록에 안 보임. 평가 스크립트가 만드는 임시 컬렉션도 이 종류로 | 제안(10/22 TrackA 임시 컬렉션이 최대 오염원이었음 — 지금은 삭제됨, 재발 막기) |
| S7 | 범위와 상관없는 화면(조직·시스템)에선 칩을 흐리게 + 툴팁 | 확정(org-space §5) |
| S8 | 슈퍼어드민(파트 없음)은 고른 업무만 | 확정 |

선택기 전수 조사(10/22): 고르는 곳은 사이드바 하나뿐, 프론트는 `kind`·`parent_id`를 안 씀(테스트 영역 노출), 평가 게이트 즉석 검색에 범위 표시 빠짐 → C2 화면 때 같이.

## 7. 등록 — AI는 초안, 사람은 [등록] (10/22, org-space §4를 고침)

```
[넣는 사람] 붙여넣기 · 파일 · URL      ← 위치·종류 고르는 칸 없음
   ▼ AI 초안: 제목 · 내용 정리 · 종류 · 위치 + 이유(§4 시험 결과 한 줄)
   ▼ (애매할 때만) 한 번 묻기 — 버튼 2~3개 + [잘 모르겠어요]
   ▼ [등록]  또는  [직접 고치기 → 등록]        ← 정책서 수정 모달과 같은 모양
   ├ 넣는 사람이 그 위치 담당 → 바로 반영(기록 남김)          ← 결정 대기
   └ 담당 아님 → 정정 요청 대기열 → 위치 담당이 승인 / 직접 고쳐 승인 / 반려(사유 → AI 다시)
```
- 확신 판정은 LLM 자기 평가를 쓰지 않는다: **LLM이 고른 위치 = 비슷한 승인 지식 5건 다수결(4/5 이상)** 일 때만 확신(org-space §4 그대로).
- AI 실패·이웃 0건은 카드 맨 위에 노란 줄로 보인다(대체 처리 표시).
- MVP는 지식 문서만. 다른 종류로 보이면 "정책서로 보여요 → 정책서 올리기" 링크를 띄우고 멈춘다.

## 8. 선순환 — AI가 스스로 보고·판단·리포트 (10/22 확정)

| 단계 | 하는 것 | 숫자(근거) |
|---|---|---|
| ① 관찰(정기) | 컬렉션마다 센다 | 크기 · 5건 미만 하위 · 이웃 다수결과 다른 위치의 지식 · 원천 구조별 양 · **A를 골랐는데 B 지식으로 답한 비율** · 신고된 근거의 위치 |
| ② 판단 | 규칙 + AI 요약 | 옮기기 / 합치기 / 하위 만들기 제안 + 근거 숫자 |
| ③ 리포트 | 품질 › 컬렉션 점검 화면 + 정정 요청 "컬렉션 변경" | 사람은 승인만 |
| ④ 적용 | 백업 + 전·후 게이트 | 나빠지면 되돌림 |
| ⑤ 학습 | 효과 확인, 반려 사유는 §4 판정 예시에 추가 | |

순서: **수동 1회 스크립트 → 화면 + 정정 연결 → 정기 실행 + 효과 추적**(등록 창구 뒤).
안 함: 승인 없는 자동 적용. 다시 볼 조건: 3개월 승인률 90% 이상이면 "옮기기"만 자동 검토.

**A. 가상 예시 20**: 이름만 줌 **19/20**(틀린 1 = 땡겨요 → 비슷한 이름 "제휴 주문 서비스"). 정책 묶음 이름으로 "다루는 것"을 붙이면 17/20으로 오히려 나빠짐
(정책 묶음 이름을 하위로 착각) → 설명 붙이기는 안 한다.

**B. 사용 중 지식 73건 — 글만 보고 판정**
| 지금 위치 | 같게 판정 | 다르게 |
|---|---|---|
| 제휴서비스 49(컨플) | 46 | 팀 공통 2 · 온라인스토어 1 |
| 딜리버스 24(직접 입력 17·컨플 7) | 10 | 14 — 주문 서비스·POS·배민 등으로 흩어짐 |

딜리버스 불일치 14건 중 13건은 **본문에 어느 업무 이름도 안 나오는 짧은 글**(54~581자)이었다 — 글만으로는 어느 업무인지 알 수 없다. 위치는 "어디서 넣었나"에만 들어 있었다.
→ **AI가 글만 보고 배치하면 짧은 메모는 틀린다.** 이웃 투표가 필요하다는 org-space §4 설계가 맞았다.

**확신 규칙(LLM 위치 = 비슷한 지식 5건 중 4건 이상 같은 위치)을 실데이터에 적용**
| | 확신(자동 반영 후보) | 확신 없음(사람 확인) | 확신인데 틀림 |
|---|---|---|---|
| 제휴서비스 49 | 45 | 4 | 0 |
| 딜리버스 24 | 6 | 18 | 0 |
| 합계 73 | **51 (70%)** | **22 (30%)** | **0** |
이웃 투표만으로는 68/73(93%)이 지금 위치와 같았다. 주의: 지식이 있는 업무가 둘뿐이라 투표가 쉬운 조건이다 — 업무가 늘면 다시 잰다(§8 선순환의 관찰 숫자).

**C. 하위가 필요한가 — 제휴서비스를 하위 없이 검색(지식 질문 92)**
| 질문 대상 | 정답 찾음 | 채택 조각 중 다른 제휴사 것 | 1등이 다른 제휴사 | 질문에 제휴사 이름 있음 |
|---|---|---|---|---|
| 배달의민족 44 | 42 (95%) | 50/126 (40%) | 9 | 10 |
| 쿠팡이츠 42 | 39 (93%) | 42/125 (34%) | 13 | 13 |
정답은 하위 없이도 찾는다. 대신 **문맥의 3분의 1이 다른 제휴사 것**이다. 하위가 있어도 사용자가 하위를 **직접 골라야만** 이 섞임이 사라진다 — 사용자는 안 고른다(최악 입력 가정).
그래서 섞임은 하위 컬렉션이 아니라 **답 단계**에서 푼다: 근거가 여러 제휴사로 갈리고 질문에 대상이 없으면 되묻기(v2.133 clarify 재사용), 근거마다 상위 페이지(배민/쿠팡) 표시.
이게 실제 답을 틀리게 하는지는 아직 모른다(검색만 쟀음) → 정확도 단계에서 답 채점으로 잰다.

**사용자 질문 답(10/22 밤)**
- 하위는 정확도 때문에 만든 게 아니다(검색 결과 같음) — 화면·담당용이었고, 배민·쿠팡은 담당도 같다(온라인서비스 파트). **만들 이유가 없다.**
- 질문 의도로 업무 컬렉션을 알아서 찾는 기능은 **지금 없다.** 범위 = 사이드바 선택(기본 = 내 담당 업무, S4). 정확도의 근거는 §1 표(고른 업무 95.3%).
  자동 선택은 "엉뚱한 업무를 골랐는데 답한 비율"을 §8 관찰 숫자로 먼저 쌓고 본다.

## 16. AI 판단 원장 — 사람이 고친 것을 남기고, 왜 틀렸는지 스스로 리포트 (사용자 10/22 "이게 핵심")

**왜**: "AI가 정하고 사람은 위험한 것만" 구조는 AI가 틀리는 걸 알아챌 장치가 없으면 조용히 정확도가 샌다. 사람이 고친 기록이 곧 AI의 오답 신고이고, 선순환의 입력이다.

**① 남기는 것 (판단 1건 = 1줄)**: 종류(위치·지식 종류·VOC 묶음·정책 위험도 …) · 대상(종류+id) · AI 값 · 확신 여부 · 근거 신호(이웃 투표 n/5, 유사도, 출처 단서) ·
프롬프트/모델 버전 · 시각. 나중에 사람이 그 값을 바꾸면 같은 줄에: 바꾼 값 · 누가 · 언제 · **"원래 AI 판단이 틀렸나요?"** 답.
- 바꿀 때 묻는 것(한 번, 버튼): [AI가 틀렸어요 — 이유: 업무 이름 없음 / 비슷한 다른 업무와 헷갈림 / 종류가 다름 / 기타 한 줄] · [AI는 맞았는데 상황이 바뀜(조직 개편·업무 이관)]
  → 둘을 섞으면 "AI 오답률"이 부풀거나(개편 때문) 줄어든다(묻지 않으면). 답하지 않고 닫으면 "모름"으로 남기고 오답 집계에서 따로 센다.
- 받는 경로 전부: 승인 화면 고치기만이 아니라 지식 수정 창에서 위치 옮기기, VOC 묶음 떼기·합치기, 정책 위험도 수동 변경 — "AI가 정한 칸을 사람이 바꾸면 기록"을
  수정 경로마다 공통 함수로. 기록 없이 바뀌는 경로가 있으면 오답률이 실제보다 좋게 보인다(점검: 해당 칸을 쓰는 UPDATE 전수 grep을 테스트로).

**② 보는 숫자 (운영 리포트)**: 종류별 "AI 틀림" 비율 · **확신으로 자동 반영됐는데 틀림 = 1건이라도 알림 + 자동 반영 기준 자동 상향** ·
확신 없음 → AI안 그대로 승인 비율(사람에게 괜히 넘기나) · 자주 바뀌는 방향(예: 딜리버스 → 팀 공통) · 이유별 건수.

**③ 스스로 리포트 — "왜 틀렸고 어떻게 구조화하면 오르나"**: 정기 점검이 틀림 사례를 이유·신호별로 묶어 가설을 만든다
(예: "틀린 12건 중 9건이 업무 이름 없는 300자 미만 메모 — 글만으로 못 정함 → 출처(넣은 화면·컨플 공간)를 신호로 추가하면?").
**제안은 원장으로 리플레이해서 숫자로 낸다**: 바꾼 규칙/프롬프트로 과거 판단을 다시 돌려 "틀림 n건 중 m건 고침 · 맞았던 것 중 k건 망가짐"을 같이 보여 준다
(k > 0이면 정확도 최우선 원칙에 따라 그대로는 제안 안 함). 사람은 승인만 → 적용 → 다음 주기에 효과 확인. 틀림 사례는 판정 예시 후보로 쌓는다(승인 시 프롬프트 예시).

**④ 어디에 두나 (레이어)**: 원장·집계·리플레이 틀은 코어(신뢰도 레이어 `libs/trustkit` 성격 — 표준 라이브러리, 앱 DB는 어댑터). 판단을 내리는 쪽(지식 등록·
정책 위험도, 나중에 분리될 VOC 에이전트)은 **원장 API(판단 기록·사람 변경 기록)만 호출** — VOC가 별도 에이전트로 떨어져도 같은 원장·같은 리포트를 쓴다(DB 직접 접근 금지).

**⑤ 순서**: E(지식 등록 한 곳 — 첫 생산자)와 함께 원장 + 수정 경로 기록 → 정책 위험도·VOC 묶음 연결(VOC는 레이어 분리 때 API로) → 리포트(운영 리포트 안) → 리플레이 제안.
기존 기록(정정 요청 AI 분석 vs 담당 변경, 정책 검토 기록)에서 되살릴 수 있는 건 E 시작 때 확인해 재사용.
13. **(사용자 10/22, §15-10·11 고침) 고르는 창 = [업무 | 조직] 탭, "다른 파트 관점으로 보기"는 뺀다** — 사이드바에서 업무만 고르면 지식 문서·용어집 화면에서

    **통일 규칙(사용자 10/22)**: 업무 탭과 조직 탭은 같은 정렬·같은 모양 — 1순위 "내 것"(내 파트 / 내 파트 담당 업무) = 보라 배경·테두리·굵은 제목,
