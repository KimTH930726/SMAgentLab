# RAG 거버넌스 개선 — 분류 재검토(레드팀) + WBS (2026-09-22)

> **목적**: `rag-governance-audit.md`(v1·v2) 이후 도출한 "지금 해야 될 것 / 데이터 쌓이며
> 진행 / 안 해도 될 것" 분류를 실행 전에 레드팀 관점으로 한 번 더 찌르고, 그 결과를
> 바로 착수 가능한 WBS로 고정한다. 이 문서 이후엔 각 태스크를 여기 정의된 완료조건대로
> 진행하면 되고, 매번 범위를 재논의하지 않는다.

## 1. 레드팀 재검토 — 지난 분류에서 놓친 것

지난 분류표를 그대로 실행하면 안 되는 이유 4가지를 먼저 짚는다(④는 사용자가 직접
반박하면서 발견됨 — 문서 최초 작성 당시엔 놓쳤던 것).

### ① "정책 최소 승인 절차"는 "저비용"이 하나가 아니라 둘로 쪼개진다

**놓친 것**: 승인 플래그를 스키마에 추가하는 것과, 검색이 그 플래그를 실제로 걸러내게
만드는 것은 완전히 다른 리스크 등급이다. 지금 정책 378건이 **전부** `pending_review`다
— 필터를 곧바로 켜면 정책 검색 결과가 100% 사라진다(이미 v1 감사에서 확인한 함정을
여기서 또 밟을 뻔했다).

**수정된 계획**: 2단계로 쪼갠다.
- **Phase 1(저위험, 지금)**: `policy_item`에 `approved_at`/`approved_by` 실제 기록 연결만
  — 필터링은 아직 안 건다. 오늘 `rag_knowledge.reviewed_at/owner`를 쓴 것과 완전히 같은
  패턴(감사 추적만 먼저 생기게 함).
- **Phase 2(검토 필요, 나중)**: 실제 필터를 켜려면 기존 378건을 언제/어떻게 "승인된 것"
  으로 백필할지부터 정해야 한다(예: 지금까지 문제없이 쓰인 항목은 일괄 승인 처리 기준일
  지정 등) — 이건 코드 문제가 아니라 **업무 판단**이라 Phase 1과 분리해야 한다.

### ② "원자적 활성화"는 한 트랜잭션으로 묶는 게 아니다

지난 세션에서 이미 한 번 걸렀지만 다시 명시: 임베딩에 몇 분 걸리는 대량 job을 통째로
한 트랜잭션에 넣으면 락 경합/타임아웃 위험이 있다. 실제로 필요한 건 **2단계 설계**
(스테이징 상태로 전부 삽입 → job 완료 시 한 번에 status 일괄 전환)이고, 이건 "지금
바로 코드 한 줄"이 아니라 **작은 설계 스파이크가 선행되어야 하는 태스크**다.

### ③ 인젝션 방어 문구는 배포 전 회귀 확인이 완료조건에 들어가야 한다

델리미터/지시문 추가 자체는 저비용이 맞지만, 시스템 프롬프트를 건드리는 모든 변경은
**기존 답변 품질을 건드릴 수 있다** — 특히 운영 문서 중엔 원래 "다음 순서로
진행하세요" 같은 절차형 문장이 정상적으로 존재하는데(정책서 자체가 절차 문서), LLM이
이걸 "명령으로 오인해 거부/이상반응"하게 만들 위험이 있다. **완료조건에 골든셋
89문항 재실행 후 답변 품질 회귀 없음 확인을 반드시 포함**한다 — "코드 배포됨"과
"안전하게 배포됨"을 구분한다.

### ④ "Parent-Child는 데이터 축적형(나중)"이라는 최초 판단이 틀렸다

**놓친 것**: "정책/DB 데이터는 짧고 원자적이라 부모 문맥 안 필요, 컨플루언스는 아직
본격 수집 전이라 급하지 않다"고 판단했는데, 둘 다 근거가 부실했다.
- 정책: 378건 중 125건(33%)이 **이미** 여러 청크로 쪼개져 있고, 실제로 `policy_item
  id=56`("B2C")은 "1. 자사몰만 적용"(적용범위 조건)과 나머지 4개 청크가 분리되어
  있어, 그 조건 없이 "각인옵션이 제공된다"만 단독으로 LLM에 들어가는 게 실측 확인됨.
- 컨플루언스: "아직 본격 수집 안 됨"이 틀렸다 — `외부서비스DB`에 이미 confluence_bulk
  14건이 있고, 그중 2건(배달의민족 섹션 vs 쿠팡이츠 섹션)이 **완전히 동일한 텍스트**
  이면서 어느 채널 얘기인지 구분할 정보가 청크 자체엔 전혀 없었다 — 정책 사례보다
  더 심각한 실례.

**수정된 계획**: "데이터가 쌓이면"이 아니라 **지금 있는 데이터에 이미 문제가 있었다.**
정책 쪽은 원문 전체(`raw_body`)가 이미 검색 시점에 fetch만 되고 안 쓰이고 있어서
즉시 스왑으로 해결(설계 불필요, 오늘 완료). 컨플루언스 쪽은 진짜 계층 구조 저장
컬럼이 없어 일반 해법은 여전히 설계가 필요하지만(`confluence-chunking-spec.md`와
병합 검토), 지금 확인된 것처럼 완전히 모호한 소수 건은 응급 라벨링으로 즉시 완화
가능 — "설계 전엔 아무것도 못 한다"가 아니라 "설계는 별도로 진행하되 이미 보이는
구멍은 지금 막는다"로 구분했다.

## 2. 최종 분류표 (레드팀 반영)

| 버킷 | 항목 | 근거 |
|---|---|---|
| **지금** | 정책 승인 기록(Phase 1, 필터링 없음) | 오늘 rag_knowledge에 쓴 패턴 재사용, 회귀 위험 없음 |
| **지금** | 수집 원자적 활성화 — **설계 스파이크부터** | 실제 재현된 버그, 회귀테스트 기준선 있음(오늘) |
| **지금** | 인젝션 최소 방어 — **골든셋 회귀 확인 포함** | 데이터 불필요하나 배포 전 검증 필수 |
| **데이터 축적형** | 정책 승인 필터 강제(Phase 2) | 기존 378건 백필 기준 결정 필요(업무 판단) |
| **데이터 축적형** | 읽기 ACL 강제 전환 | 로그온리 데이터 1~2주 관찰 필요(오늘 배포함) |
| **데이터 축적형** | ANSWER/CLARIFY/ABSTAIN 실사용 노출 | 적대적 골든셋 보강 필요(no_knowledge 로그에서 후보 추출) |
| **데이터 축적형** | 주장별 근거 검증 | 위 항목과 골든셋 공유, 순서상 뒤따름 |
| **데이터 축적형** | 인젝션 탐지(패턴 기반) | 정상 문서 오탐 방지에 실 샘플 필요(방어=지금, 탐지=나중 — 서로 다름) |
| **데이터 축적형** | 검색 실패 시 1회 재시도(재작성) | ABSTAIN(2-3)이 소비할 "그래도 없으면" 신호가 있어야 의미 있음 — 같은 골든셋/실패로그로 설계 |
| ~~**데이터 축적형**~~ → **정정: 지금(부분 완료)** | Parent-Child 청크 확장 | **2026-09-22 재평가 — 원래 분류가 틀렸음(사용자 지적으로 발견).** "컨플루언스 아직 본격 수집 안 됨"이라고 판단했으나 실제로 `외부서비스DB`에 이미 confluence_bulk 14건이 있었고, 그중 2건(id=12857/12862, "배달의민족" vs "쿠팡이츠" 섹션)이 **토씨 하나 안 다르게 완전히 동일한 텍스트**이면서 어느 채널 얘기인지 구분할 정보가 청크 자체엔 전혀 없는 게 실측 확인됨(정책 사례보다 더 심각). 정책 쪽(policy_item)은 `raw_body`가 이미 fetch만 되고 안 쓰이고 있어서 즉시 스왑으로 해결(아래 3. 오늘 처리분). rag_knowledge/컨플루언스 쪽은 원문이 19페이지 뭉친 대량 청크라 "이 조각의 부모가 정확히 뭔지"를 아는 컬럼 자체가 없어 즉시 해결 불가 — 지금 14건 중 진짜 모호한 2건만 채널명 라벨 삽입으로 응급조치(오늘 완료), **일반 메커니즘(heading 계층 저장 등)은 여전히 설계 필요, `confluence-chunking-spec.md`와 병합해서 다룰 것** |
| **데이터 축적형** | 감사 로그 확장(provider/latency/cost) | 실제 요청 들어온 적 없음 |
| **데이터 축적형** | 모니터링 대시보드 | 감사로그 축적 후 의미 생김 |
| **안 해도 됨** | Tenant 레이어 | 단일조직 내부용, 외부공유 계획 없음 |
| **안 해도 됨** | PostgreSQL RLS | DB 직접 접속 경로가 백엔드 하나뿐 |
| **안 해도 됨** | Provider 데이터등급 자동 라우팅 | 분류체계 자체가 없음, 위험도 낮음 |
| **안 해도 됨** | 진짜 비동기 워커(큐+크래시복구) | 실측 수집 패턴이 상시 반복이 아닌 가끔 대량작업 |
| **안 해도 됨** | Release Manifest | 재현 요구 실제 발생 이력 없음 |
| **안 해도 됨** | LLM Judge | 결정론적 채점이 이미 실측 검증됨(88.8%) |
| **안 해도 됨** | Canary/자동 롤백 | 배포가 사람이 직접 승격하는 소규모 구조 |

## 5. 부록 — 원 감사 스냅샷 (2026-09-23, `rag-governance-audit.md` 통합)

이 문서(§1의 레드팀 재검토)가 아래 원 감사의 우선순위 판단을 대체하므로 별도 파일로 안
두고 여기 요약만 남긴다. 전체 코드 대조 방법론은 실행 시점(2026-09-22) 스냅샷이라 이후
변경분은 반영 안 돼 있음 — 최신 상태는 `docs/architecture.md` 참고.

**한 줄 결론(당시)**: 검색·저장 계층(RRF 하이브리드, PG+pgvector 단일 스토어, INSERT-only
버전관리)은 탄탄했지만, "누가 이 지식을 볼 수 있는가"가 쓰기 경로에만 답이 있고 읽기(채팅)
경로엔 없었다 — 유일한 P0(§2-2로 로그온리 대응 완료).

**정책 충족도(15개 영역, 당시 스냅샷)**: 충족 1(저장구조) · 부분충족 7(문서우선순위·검색
