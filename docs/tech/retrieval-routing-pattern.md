# 검색 전략 라우팅 — 재사용 가능한 설계 원칙 (2026-09-04)

> 목적: "구조화 데이터는 정확 조회, 서술형 데이터는 의미 검색"이라는 원칙이 이 프로젝트에서
> **이미 두 번 독립적으로 재발견됐다** — 그런데 한 번도 그 자체로 문서화된 적이 없다. 다음
> 세 번째 축(예: 다른 데이터 종류를 데이터 허브에 편입할 때)에서 또 처음부터 재발견하지
> 않도록, 지금까지의 두 구현 사례를 근거로 원칙 자체를 이 문서에 뽑아 남긴다.

## 1. 원칙

> **벡터 검색은 "의미가 비슷한 것"을 찾고, 키워드/RDB 조회는 "정확히 일치하는 것"을 찾는다.
> 데이터가 구조화된 값(코드표, 파라미터, 수치)이면 후자가 정답이고, 서술형 문장이면 전자가
> 정답이다 — 벡터화로 통일하면 구조화 데이터에서 "어휘만 겹쳐도 오탐"이 실측으로 반복
> 확인됐다.**

판단 기준은 "이 데이터가 무엇에 쓰이는가"이지 "정량적 값인가"가 아니다(2026-08-28
세션에서 정리된 기준) — 정밀 매칭이 필요한 데이터(장애 원인 분석, 코드값 조회)는 문맥을
보존한 원문/정확 조회가 유리하고, 표현 차이를 넘어 그룹핑해야 하는 데이터(반복 유형 탐지)는
오히려 정규화가 유리하다. "구조화 vs 서술"도 이 상위 기준의 한 사례다.

## 2. 실측 근거 — 이미 두 번 독립적으로 발견됨

| # | 사례 | 문제 | 해결 | 구현 방식 |
|---|---|---|---|---|
| 1 | `rag_knowledge`(v2.49) | `category IN ('DB','공통코드')`가 전체 지식의 88%, 코드표 덤프라 코사인 유사도로 비교하면 무관한 문서와 어휘만 겹쳐도 오탐(실측: "사이렌오더 결제 취소" 문서가 무관한 배송 클러스터와 매칭) | 해당 카테고리는 `search_knowledge()`의 `final_score`에서 벡터 점수를 0으로 만들고 키워드 점수만 사용 | **같은 테이블 안에서 행(row)별로 랭킹 공식을 분기** — `_KEYWORD_ONLY_CATEGORIES` 상수 |
| 2 | 정책서 파이프라인(v1, 2026-09-03) | 정책 본문 안의 파라미터 팩트("일반 배달: 20개")를 서술과 같이 벡터화하면 같은 문제가 재현될 것으로 예상(설계 단계에서 사전 적용) | 애초에 저장 단계에서 파라미터/서술을 분리 — `policy_param`은 RDB `to_tsquery`, `policy_chunk`만 벡터 | **아예 다른 테이블로 분리, 검색도 따로** |

두 사례가 **구현 방식이 다르다**는 점이 중요하다 — 하나는 "한 테이블 안에서 랭킹 공식 분기",
다른 하나는 "테이블 자체를 분리". 원칙은 같은데 구현이 매번 달랐다는 게, 지금까지 이게
재사용 가능한 패턴으로 뽑히지 못했던 이유다.

## 3. 다음 축에 적용할 때 — 결정 체크리스트

새로운 데이터 종류를 시스템에 편입할 때 다음을 먼저 판단한다:

1. **이 데이터의 검색 목적이 "정확한 값 조회"인가 "의미 기반 탐색"인가?**
   - 코드표, 파라미터, 상태값, ID/번호 → 정확 조회 (RDB `to_tsquery` 또는 exact match)
   - 자유서술문, 규칙 설명, Q&A → 의미 검색 (벡터)
2. **한 데이터셋 안에 두 성격이 섞여 있는가?** (섞여 있는 경우가 오히려 흔함 — VOC 본문,
   정책서 본문 모두 그랬다) → **LLM로 segment/행 단위 분류 후 분리 저장**이 필요하다는 신호.
   `service/policy/decompose.py`의 narrative/param 분류가 이 패턴의 최신 구현.
3. **구현 방식 선택**: 기존 테이블에 이미 다른 종류 데이터가 섞여 있고 규모가 작다 → 랭킹
   분기(사례 1 방식, 낮은 마이그레이션 비용). 처음부터 설계하는 신규 데이터 종류다 → 테이블
   분리(사례 2 방식, 더 깨끗하지만 신규 스키마 필요).
4. **과설계 주의**: 지금 당장 통합 검색 프레임워크(예: "무슨 데이터든 넣으면 자동으로 라우팅
   판단하는 범용 모듈")를 만들지 않는다 — 사례가 2개뿐이라 아직 "제3의 변형"이 뭘지 모른다.
   3번째 축이 실제로 생겼을 때, 이 문서의 체크리스트로 판단하고 사례를 추가하는 방식으로
   키운다(YAGNI — `knowledge-lifecycle-design.md`에서 LLM Comparator를 보류했던 것과
   같은 이유).
