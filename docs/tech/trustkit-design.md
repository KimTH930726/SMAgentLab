# trustkit — 신뢰도 레이어 설계 (2026-10-19)

OpsLens는 지식 검색 시스템이지만 본질은 **답을 믿을 수 있게 만드는 신뢰도 레이어** 위에 선 응용이다. 그 레이어(적재 품질·검색 기법·
문맥/답 다듬기·평가)를 프로젝트 밖으로 이식할 수 있는 패키지로 뽑는다 — 팀 자산. 이름은 "신뢰"가 드러나게 `trustkit`(작업 이름,
별도 저장소 이동 전까지 변경 가능). 나중에 영향도·장애 분석 평가에도 쓰일 수 있게 RAG 전용 이름을 피했다.

## 1. 막힌 일
- v2.137~138 기법(BM25 구제·맥락 머리·문서 묶기·목록 범위·조건형 답 구조·오차 범위/짝 비교)이 **정책서 경로에만** 붙어 있다.
  지식(컨플루언스) 경로는 벡터 + ts_rank(IDF 없음) SQL 가중합, 본문만 임베딩 — 같은 기법을 쓰려면 한 벌 더 짜야 한다.
- 기법 코드가 `service/policy/*`, `agents/knowledge_rag/agent.py`, `scripts/eval_*`에 흩어져 있어 "업계 방법론을 레이어로 적용"을 구조로 보여줄 수 없다.
- 적재 품질 검사·청크 불변식(10/7 장애 대응)은 지식 적재 코드 안에만 있다 — 신뢰 레이어의 첫 단계인데 이식 대상에서 빠져 있었다.

## 2. 무엇이 레이어이고 무엇이 응용인가
판단 기준: **DB·데이터 형식과 무관한 순수 계산이면 레이어, 우리 테이블·모델·LLM에 닿으면 응용(어댑터).**

| 단계 | 레이어(trustkit) | 응용(프로젝트에 남음) |
|---|---|---|
| 적재 | 청크 품질 검사(`assess`), 청크 불변식 검사(유실·중복·잘림·제목 매달림) | 청크 분할기·파서, job 기록 SQL |
| 색인 | 맥락 머리 규칙 | 임베딩 모델 호출, 재임베딩 마커 SQL |
| 검색 | 한국어 토큰화(조사·금액), BM25, 문서 단위 묶기, 구제/RRF 합치기 | pgvector·ts_rank SQL, 색인 캐시 |
| 질문 이해 | 질문 유형 판별(탐색·조건) | 분류 목록 찾기(정책 분류 테이블) |
| 문맥·답 | 목록 범위 거르기(`list_scoped`), 유형별 답 구조 지시문 | 문맥 조립 순서, 시스템 프롬프트 |
| 평가 | 오차 범위·짝 비교·카파(`stats`), 전/후 판정(`gate`) | 골든셋 로딩, 답 수집, LLM 채점 호출 |

## 3. 구조
```
backend/libs/trustkit/            ← 표준 라이브러리만. core·service·shared·agents import 금지(테스트로 강제)
├ pyproject.toml                  ← 다른 프로젝트: pip install <경로 또는 git>#subdirectory=backend/libs/trustkit
├ README.md                       ← 단계별 기법·출처·사용 예
├ trustkit/
│  ├ ingest/   quality.py · invariants.py
│  ├ text/     ko.py
│  ├ retrieval/ bm25.py · fusion.py · chunk_header.py
│  ├ query/    intent.py
│  ├ answer/   shaping.py
│  └ eval/     stats.py · gate.py
└ tests/                          ← 패키지만으로 실행(도커·DB 불필요) + 독립성 검사
```
- 이 프로젝트는 `PYTHONPATH`에 `/app/libs/trustkit`을 더해 import(설치 단계 없음 — 폐쇄망·dev 마운트 그대로).
- 기존 위치(`service/policy/keyword_index.py`, `korean_text.py`, `scripts/eval_stats.py`, `ingestion/quality.py`)는 trustkit을 쓰는
  어댑터로 남긴다(DB 조회·캐시만). SQL 함수 `policy_strip_ko`와 같아야 하는 조사 목록은 trustkit이 기준, `korean_text`는 재노출.

## 4. 인터페이스 원칙 (두 번째 사례 전까지 굳히지 않음)
- 입력은 단순 타입(id·텍스트·점수 목록, 키 함수). 우리 dataclass(`NarrativeHit` 등)를 요구하지 않는다.
- **버전 0.x** — 컨플루언스 경로 적용·게이트 통과 전에는 시그니처가 바뀔 수 있다. 별도 Bitbucket 저장소 이동은 그 뒤.

## 5. 진행 순서와 완료 기준
1. **뽑아내기(동작 변화 0)** — 정책 경로·적재 품질·평가 통계가 trustkit을 쓰게. 완료 기준:
   - 검색 측정(결정적) 문항별 결과가 이전과 **완전히 같음**(`eval_out/retr_before_trustkit.jsonl` 대조)
   - 답 수집 `--reuse`에서 176/176 재사용(= LLM 입력 문맥이 바이트 단위로 같음, 게이트웨이 비용 0)
   - 기존 테스트 전체 + 청크 불변식(점검표 C1·C2) 통과, trustkit 단독 테스트 통과
2. **게이트 스크립트** — `trustkit.eval.gate`로 전/후 채점 파일 → 유형별 통과/실패(검색 나빠짐 0, 답 의미 있는 하락 없음).
3. **두 번째 사례 = 컨플루언스 지식 경로** — 맥락 머리(제목 경로) 임베딩 + BM25 구제를 trustkit으로. 평가 문항은 **로컬 LLM이 원문을
   읽어 생성**(Claude 세션은 원문·생성 문항을 읽지 않고 집계만 — 사용자 지침 "Confluence 원문은 로컬 LLM"). 전/후 Recall 측정.
4. 독립 코드 리뷰(작성 맥락 없는 리뷰어) → 반영 → 사용자 확인 후 커밋.
5. 사례 2 통과 뒤: 인터페이스 1.0, 별도 저장소 이동 판단.

## 6. 안 하는 것 · 다시 볼 조건
| 안 하는 것 | 다시 볼 조건 |
|---|---|
| DB·벡터 저장소·임베딩·LLM 호출 추상화 | 다른 팀 프로젝트가 실제로 붙을 때 — 그쪽 저장소 보고 |
| LLM 채점기(루브릭·목록 대조) 이동 | 컨플루언스 답 평가에서 같은 채점기를 실제로 쓸 때 |
| 근거 없음 판정(`should_abstain`) 이동 | 지식 경로에도 같은 판정을 붙일 때(지금 신호 이름이 우리 것) |
| 설정만으로 조립하는 파이프라인 프레임워크 | 데이터 종류 4개 이상 또는 다른 팀 요청 |
| 데이터 넣으면 기법·지표 추천하는 자동 게이트 | 9월 로드맵 그대로 — 사례 2~3개 이후 |

## 7. 진행 결과 (2026-10-19)

### 7-1. 뽑아내기 — 동작 변화 0 확인
- 옮긴 것: 조사·금액 정규화(`text.ko`), BM25(`retrieval.bm25`), 묶기·구제·RRF(`retrieval.fusion`), 맥락 머리(`retrieval.chunk_header`),
  질문 유형(`query.intent`), 목록 범위·조건형 지시문(`answer.shaping`), 적재 품질·청크 불변식(`ingest.quality`·`ingest.invariants`),
  평가 통계(`eval.stats`), 게이트(`eval.gate`, 신규). 기존 모듈은 재노출·DB 어댑터로 남김(import 경로 그대로).
- 검증: 정책 검색 측정 148줄 전부 동일 · 답 수집 `--reuse` 176/176 재사용(LLM 입력 바이트 단위 동일, 게이트웨이 0회) ·
  테스트 전체 + trustkit 단독 10건(컨테이너 밖 호스트 파이썬에서도 통과) · 청크 불변식 테스트가 `check_chunks`로 같은 검사(점검표 C1·C2).
- 게이트(`scripts/eval_gate.py`)를 v2.138 전/후 실제 파일로 돌려 손 계산과 같은 값(탐색형만 "의미 있게 좋아짐").

### 7-2. 두 번째 사례 — 컨플루언스 지식 경로
- 평가 문항: 로컬 LLM이 활성 컨플루언스 조각 53개를 읽어 106문항 생성(`scripts/confluence_synth_questions.py`, 결과는 eval_out/ — 이 세션은
  개수·집계만 봄). 질문 단어 중 원문에 있는 비율 중앙 44%. 원문 묶음 5개.
- 기준선: 문맥 Recall@3 95.3%(101/106), 상위 10 안 100% — dev 데이터가 파트당 25개 안팎이라 여유가 적다.

| 시도 | 결과 | 판정 |
|---|---|---|
| 맥락 머리 임베딩("페이지명 (제목 경로): 조각") | Recall@3 95.3→94.3%, 같은 페이지 조각끼리 유사도 중앙 0.51→0.65, 중복 판정(0.88) 넘는 쌍 13→30 | **안 씀** — 조각이 길고 제목 줄이 이미 있어 같은 머리가 구분력을 깎음(정책 조각은 짧고 주어가 없어 효과) |
| BM25 구제 2자리(문맥 3자리 중) | 95.3→75.5% | 안 씀 — 키워드 단독 1위 정답 59/106, 주 채널이 맞힌 2·3위를 밀어냄 |
| BM25 구제 1자리 | 101→102, 좋아짐 3·나빠짐 2(p=1.0) | **게이트 실패 → 기본 꺼짐**(`KNOWLEDGE_KEYWORD_RESCUE=1`로 켬, 재적재 후 다시 판단) |
| 동점 순서 고정(`ORDER BY final_score DESC, k.id`) | 바뀐 문항 0 | 적용 — 완전 동일 조각 쌍 때문에 실행마다 순위가 뒤바뀌던 것 |

- 레이어에 남은 일반 규칙: **구제 자리 = 문맥 자리의 약 30%**(`default_rescue_slots` — 정책 10→3, 지식 3→1).
- 의미: 같은 부품이 다른 데이터에 인터페이스 변경 없이 붙었고(추가 1개: `default_rescue_slots`), 게이트가 "이 데이터엔 안 맞는다"를
  걸러냈다. 기법을 복붙하지 않고 데이터마다 측정·판정하는 것이 이 레이어의 핵심.
- 답 정확도(`scripts/eval_knowledge_answers.py`, 채팅과 같은 경로로 생성 · 로컬 LLM이 정답 조각과 대조해 채점, 2회 반복): **정답률 92.0%
  (95% 구간 90–94%)**, 212개 중 정답 195·부분 9·오답 5·거절 2. 실패 대부분(13)이 "정답 조각이 문맥에 있는데 답이 부족" — 정책서와 같은 패턴
  (개선 여력은 검색보다 답 생성). 합성 문항이라 조건형 질문이 거의 없어 조건형 답 구조의 효과는 판단 보류. 리뷰 후 규칙을 eval_answers와
  맞춤(게이트웨이 거부·빈 답 = 오류, 채점 서버 장애 = 중단, 정답 조각 없음 = 판정불가 우선) — 저장된 결과에 다시 적용하면 1건 차이(≈91.5%).
- 부수 발견(데이터): 활성 지식 중 유사도 1.000(완전 동일) 조각 쌍이 있다 — 재적재 때 정리 대상(post-demo-backlog).
