## 1. 에이전트 시연 (라이브 데모 스크립트)

### 1.1 사전 준비 체크리스트

- [ ] 시연용 네임스페이스에 결제/쿠폰/배송 등 시나리오와 맞는 지식이 최소 5~10건 등록되어 있는지 확인
- [ ] 시연에 쓸 "지식 공백" 질문 1개를 **의도적으로 비워둠** (없는 지식이라 답 못 하는 모습을 보여주기 위함)
- [ ] Ollama/사내 LLM 연결 상태 정상 확인 (`GET /health` 또는 Admin 헤더 상태등)
- [ ] 브라우저 확대(Zoom) 130~150% — 회의실 스크린 가독성
- [ ] 네트워크 발표장 환경에서 사전 리허설 1회 (사내망 지연으로 스트리밍 체감 속도가 다를 수 있음)
- [ ] 백업 수단: 녹화 영상(2~3분, `03_시스템개요_데모.md` 슬라이드 삽입용과 동일 소스) — 라이브 데모 실패 시 즉시 전환

### 1.2 시나리오 1 — 질문하면 바로 답한다 (기본 흐름)

**보여줄 화면**: Chat 페이지

**입력 질문 예시**: "결제 오류 발생 시 1차 확인 항목은 무엇인가요?"

**보여줄 포인트**:
1. 입력 즉시 단계별 진행 표시(임베딩 → 검색 → LLM) — "블랙박스가 아니라 지금 뭘 하고 있는지 보인다"
2. 답변이 토큰 단위로 실시간 스트리밍되는 모습
3. 답변 하단 **근거 문서 카드** — "이 답변이 어느 문서에서 나왔는지 항상 같이 보여준다"
4. 용어 매핑 배지(있다면) — "뺏어오기"처럼 구어체로 질문해도 "회수"라는 표준 용어로 자동 보강되는 예시가 좋음
5. 👍/👎 피드백 버튼 클릭 → "이 클릭 하나가 뒤에서 검색 가중치를 조정한다" (2.4절에서 상세 설명 연결)

**발표 멘트**: "질문 입력부터 답변까지 사람이 검색하고 문서를 뒤지는 과정이 없습니다. 그리고 중요한 건 답변만 던지는 게 아니라 '어느 문서를 근거로 했는지'를 항상 같이 보여준다는 겁니다."

### 1.3 시나리오 2 — 몰랐던 질문은 "모른다"고 답하고 기록한다

**입력 질문 예시**: 사전에 지식이 없는 걸 확인해 둔 질문 (예: 아직 등록 안 한 신규 기능 관련 질문)

**보여줄 포인트**:
- LLM이 "관련 지식을 찾지 못했습니다" 계열 답변을 함 (환각으로 아무 말이나 지어내지 않음)
- Admin 대시보드로 전환 → 방금 질문이 **지식 공백(주황 카드)** 에 즉시 집계된 것 확인
- 카드 클릭 → 미해결 질문 목록 → 질문 클릭 → 지식 등록 폼이 질문 원문을 채운 채로 팝업

**발표 멘트**: "모르는 걸 아는 척 지어내지 않고, 대신 '몰랐다'는 사실 자체를 기록으로 남깁니다. 이게 다음 슬라이드에서 말씀드릴 선순환 구조의 시작점입니다."

### 1.4 시나리오 3 — 지식 등록 (Human-in-the-loop)

**보여줄 화면**: Admin → 지식베이스 → 파일 업로드 (또는 방금 지식 공백에서 넘어온 등록 폼)

**보여줄 포인트**:
1. PDF/Excel/텍스트 등 업로드 → **등록 전 청크 미리보기** 화면
2. "자동으로 다 등록되는 게 아니라 관리자가 청크 단위로 확인 후 확정" — Human-in-the-loop 강조
3. 등록 확정 → 곧바로 Chat으로 돌아가 방금 등록한 내용으로 같은 질문 재입력 → 이번엔 답이 나오는 모습

**발표 멘트**: "등록에서 검색 반영까지 재시작이나 재색인 같은 배치 작업이 없습니다. 등록하는 순간 바로 검색 가능합니다."

## 2. 주요 기술구조 상세 설명

> 아래는 청중의 기술적 질문에 답할 때 참고하는 상세 설명이다. 다이어그램·수식 원문은 `architecture.md`, `flow.md` 참조.

### 2.1 전체 구성

```
Frontend(React+nginx :8501) ─REST/SSE─▶ Backend(FastAPI :8000) ─▶ PostgreSQL+pgvector(:5432)
                                              │                  ▲
                                              ├─▶ Redis(시맨틱 캐시)
                                              └─▶ 사내 LLM(DevX Gateway) 또는 Ollama(온프레미스, exaone3.5)
```

- 4개 컨테이너(frontend/backend/postgres/redis)로 Docker Compose 단일 서버 구동 (`infra-brief.md`)
- **폐쇄망 전제**: 운영 중 인터넷 아웃바운드 0건. 임베딩 모델은 이미지 빌드 시 동봉, LLM 호출만 사내망 내 DevX Gateway로 나감
- LLM은 `LLM_PROVIDER` 환경변수 하나로 `ollama`(로컬) ↔ `inhouse`(사내 게이트웨이) 전환 — 재시작 없이 Admin 화면에서도 런타임 전환 가능

### 2.2 질문 처리 파이프라인 (핵심 중의 핵심)

```
질문 → [Semantic Cache 조회] → [멀티턴 검색 보강] → [용어집 매핑] → [하이브리드 검색] → [LLM 답변 생성]
```

1. **Semantic Cache**: Redis에 질문 벡터로 스캔, 코사인 유사도 0.97 이상이면 저장된 답변 즉시 반환 (LLM 호출 스킵). 에이전트별로 캐시가 분리되어 KnowledgeRAG 답변이 다른 에이전트로 새지 않음
2. **멀티턴 검색 보강**: 직전 Q+A를 현재 질문에 결합해 검색 — "그 쿼리 알려줘" 같은 짧은 후속 질문도 맥락을 유지한 채 검색됨. 추가 LLM 호출 없이 DB 조회 1회로 처리
3. **용어집(Glossary) 매핑**: 질문 임베딩과 용어집 설명 임베딩을 비교해 유사도 0.5 이상이면 표준 용어를 질문에 덧붙여 검색어를 강화 — 회사 고유 표현("뺏어오기")과 시스템 용어("회수") 간 간극을 메움
4. **가중 하이브리드 검색**:
   ```
   final_score = (w_vector × 벡터유사도 + w_keyword × 키워드점수) × (1 + base_weight)
   ```
   - 벡터 검색(HNSW 인덱스, 의미 유사도) + 키워드 검색(GIN 인덱스, BM25류 `ts_rank`) 결합
   - 비중(`w_vector`/`w_keyword`)은 사용자가 슬라이더로 실시간 조정 가능 (기본 0.7 : 0.3)
   - `base_weight`는 문서별 가중치로, 피드백에 따라 자동 조정됨 (2.4절)
5. **LLM 답변 생성**: Few-shot(유사 질문 사례) + 검색된 문서 + 대화 이력을 프롬프트로 구성해 SSE로 토큰 스트리밍

### 2.3 대화 메모리 — ConversationSummaryBuffer + Semantic Recall

- 대화가 4회 교환될 때마다 오래된 교환을 LLM이 요약해 벡터로 저장(백그라운드, 답변 지연 없음)
- 새 질문이 들어오면 "최근 2회 원문 교환"은 항상 포함하고, 그 이전 대화는 현재 질문과 벡터 유사도 0.45 이상인 것만 골라 리콜
- 효과: 대화가 아무리 길어져도 LLM 컨텍스트 창을 넘기지 않으면서, 관련 없는 옛날 맥락(다른 주제로 전환된 대화)은 자동으로 걸러짐

### 2.4 선순환 구조 (피드백 → 품질 개선)

```
👍 피드백 → 근거 문서 base_weight +0.1, few-shot 후보로 저장
👎 피드백(단순 건너뛰기) → base_weight -0.1
👎 + 지식 재등록으로 교정 → 오답 원인 지식은 페널티, 새 지식과 연결(resolved_knowledge_id)
검색 결과 없음/LLM이 "모른다" 계열 답변 → no_knowledge로 기록
```

- 사람이 별도로 "이 문서 순위를 올려라"라고 관리하지 않아도, 실제 사용 흐름에서 나오는 피드백만으로 품질이 스스로 조정됨
- 지식 공백(no_knowledge) 기록은 Admin 대시보드에 KPI 카드로 집계되어 "다음에 뭘 등록해야 하는지"를 알려줌

### 2.5 에이전트 확장 구조 — AgentRegistry 패턴

- `AgentBase`를 상속한 에이전트(KnowledgeRAG / MCP Tool / …)를 `AgentRegistry`에 등록해두고, 채팅 라우터는 `agent_type`만 보고 위임
- 인증/세션/피드백 같은 **플랫폼 공통 기능**과 **에이전트별 파이프라인**을 분리한 구조라, 새 에이전트를 추가할 때 기존 코드를 건드리지 않고 `agents/` 아래에 모듈만 추가하면 됨
- 발표 포인트: "지금 KnowledgeRAG를 보여드렸지만, 같은 플랫폼 위에 MCP 도구 연동 에이전트가 이미 같은 구조로 얹혀 있고, VOC 메일링 같은 다음 확장도 이 구조를 그대로 재사용합니다." (Text-to-SQL 에이전트는 현재 과업 범위가 아니라 dev_0/main에서 제외돼 있음 — 필요 시 archive/with-text2sql 브랜치에서 같은 구조로 존재했음을 언급 가능)

### 2.6 데이터 격리 및 권한 (보안 질의 대비)

- **네임스페이스 기반 격리**: 모든 지식/대화/로그가 `namespace_id`로 구분됨
- **부서(owner_part) 기반 권한**: 네임스페이스 소유 부서만 해당 데이터 CRUD 가능, 타 부서는 읽기 전용. `owner_part`가 없는 공통 네임스페이스는 전원 CRUD 가능
- **암호화**: 사용자별 LLM API Key, Confluence PAT은 Fernet 대칭 암호화로 저장, 비밀번호는 bcrypt 해시
- **인증**: JWT Access Token(30분) + Refresh Token(7일), 라우터 단위 `Depends` 보호
- **감사 로그**: MCP 도구 호출에 대해 별도 감사 로그 테이블 존재

### 2.7 인프라·운영 관점

- 폐쇄망 리눅스 서버 1대, Docker Compose로 4개 컨테이너 (`infra-brief.md` 참조)
- 최소 사양(10~30명 동시): 4 vCore / 8GB RAM / 80GB SSD, x86_64 필수
- 코드 수정 시 이미지 재빌드 없이 컨테이너 재시작만으로 반영 가능(dev 소스 마운트) — 운영 환경은 이미지 태그 기반 배포
- 임베딩 모델(`paraphrase-multilingual-mpnet-base-v2`, 768차원, 한국어 지원)은 빌드 시 이미지에 포함 — 운영 중 외부 모델 다운로드 없음

## 3. 질의응답 및 토론

### 3.1 기술 관련 예상 질문

**Q. LLM이 틀린 답을 만들어내면(환각) 어떻게 하나?**
검색된 근거 문서를 항상 답변과 함께 노출해 사용자가 직접 확인할 수 있게 한다. 또한 관련 지식이 없으면 "모른다"로 답하도록 설계했고(no_knowledge 판정), 아무 근거 없이 그럴듯한 답을 지어내는 상황 자체를 최소화하는 방향으로 설계했다. 다만 100% 환각 방지를 보장하는 장치는 아니며, 근거 문서 대조가 최종 안전판이다.

**Q. 검색이 부정확하면(관련 없는 문서가 뜨면) 어떻게 개선하나?**
세 가지 레버가 있다 — ① 지식 자체를 더 세분화해서 재등록, ② 용어집으로 표현 차이를 메움, ③ 벡터/키워드 비중 슬라이더 조정. 그리고 👍/👎 피드백이 쌓일수록 `base_weight`가 자동 조정되어 시간이 지날수록 검색 품질이 스스로 좋아진다.

**Q. 청킹(문서를 자르는 단위) 전략은 어떻게 정하나?**
현재 section/paragraph/fixed/auto 등 여러 전략을 지원하고 LLM Analyzer가 문서 유형에 맞는 전략을 자동 추천하지만, 운영 데이터에 최적화된 정량적 기준은 아직 계속 다듬는 중이다 (`05_구축과정_교훈.md` 참고 — 진행 중인 과제로 솔직히 공유하는 편이 신뢰를 준다).

**Q. 사용자가 몇 명까지 감당 가능한가?**
권장 사양 기준 8 vCore/16GB RAM에서 동시 사용자 50~100명. 벡터 인덱스(HNSW)를 쓰기 때문에 지식이 수만 건으로 늘어나도 검색 속도는 거의 유지된다. 다만 LLM 응답 속도는 사내 LLM 게이트웨이/Ollama 쪽 처리 능력에 의존한다.

**Q. 다른 LLM으로 교체 가능한가? 특정 벤더에 종속되나?**
`LLMProvider` 추상 클래스만 구현하면 신규 LLM을 팩토리에 등록하는 것만으로 교체 가능하고, 실제로 Ollama(온프레미스)와 사내 DevX Gateway(멀티모델) 두 가지가 이미 공존한다. 특정 벤더 종속 없이 환경변수/Admin 설정으로 전환된다.

### 3.2 보안/거버넌스 관련 예상 질문 (보안팀 검토 대비)

**Q. 데이터가 외부로 나가나?**
운영 중 인터넷 아웃바운드는 0건이다. 유일한 외부 호출은 사내망 내부의 DevX LLM Gateway로 가는 HTTPS 호출뿐이고, 임베딩 모델은 이미지에 내장되어 있어 외부 모델 서버를 호출하지 않는다.

**Q. 누가 어떤 데이터에 접근할 수 있나?**
네임스페이스(업무 영역) 단위로 데이터가 격리되고, 각 네임스페이스는 소유 부서만 쓰기 권한을 가진다(타 부서는 읽기 전용, 공통 네임스페이스는 전원 쓰기 가능). 관리자(Admin) 계정은 전체 권한을 가지며 별도로 관리된다.

**Q. 비밀번호·API 키 같은 민감정보는 어떻게 저장되나?**
비밀번호는 bcrypt 해시, LLM API Key와 Confluence PAT 같은 자격증명은 Fernet 대칭 암호화로 저장한다. VOC 메일링 확장 기능도 동일한 패턴(Fernet 암호화 + Admin 응답에서 시크릿 값 자체는 절대 노출하지 않음)을 재사용하고 있다.

**Q. (VOC 메일링 로드맵 관련) M365/Graph API 연동 시 권한 범위는?**
특정 공용 VOC 메일함만 대상으로, 최소 권한(RBAC 스코프 제한 — Mail.Read를 전체 테넌트가 아닌 지정 메일함으로 제한)으로 앱 등록하는 방식을 사전 설계했다. 자격증명은 발급 즉시 Admin 화면에 입력만 하면 되고 코드/로그에 하드코딩되지 않는다. 상세는 `email-analysis-channel-plan.md`, 진행 일정은 별도 WBS 참조.

**Q. 감사(audit)는 어떻게 남기나?**
MCP 도구 호출, VOC 메일 분석/알림 발송 결과 모두 별도 로그 테이블에 남는다. 어드민 화면에서 조회 가능하다.

**Q. 장애/오류가 나면 서비스 전체가 죽나?**
LLM 연결이 끊겨도 검색 결과 자체는 정상 반환되고 안내 메시지만 나오는 Graceful Degradation 구조다(LLM 없이도 근거 문서는 확인 가능). Redis(캐시)가 죽어도 캐시 단계만 건너뛰고 정상 동작한다.

### 3.3 운영/비용/조직 관련 예상 질문

**Q. 이 시스템을 유지보수하는 데 누가 필요한가?**
현재는 소수 인원이 개발·운영 중이다. 지식 "등록"은 각 부서 담당자가 직접 하는 구조로 설계되어 있어(등록 UI 자체가 부서 담당자용), 중앙 운영팀이 모든 지식을 대신 입력할 필요는 없다.

**Q. 도입 효과를 어떻게 측정하나?**
Admin 대시보드의 해결/대기/미해결/지식공백 KPI, 그리고 피드백(👍/👎) 비율로 실사용 품질을 추적할 수 있다. 반복 문의가 줄어드는 정성적 효과(온보딩 비용 절감)는 `06_기대효과와_다음단계.md` 참조.

**Q. 다음 단계(지식 현행화 자동화, VOC 메일링)는 언제쯤 되나?**
VOC 메일링은 Track A(구현 가능한 기술 부분)는 이미 완료되어 dev/main에 배포됐고, Track B(M365 보안성 검토, API 제공 등 조직 승인 절차)가 남아 있다 — 이 부분은 보안팀 검토 일정에 달려 있어 별도 WBS로 공유 중이다. 지식 현행화 자동화는 아직 설계 문서(`knowledge-refresh-automation-plan.md`) 단계로, 구현 착수 전이다.

### 3.4 아직 결론 나지 않은 열린 토론 주제

발표 자리에서 "답이 정해진 것처럼" 말하기보다 **함께 고민할 지점**으로 던지는 것이 신뢰도 면에서 유리하다 (`05_구축과정_교훈.md`의 톤과 동일):

1. **청킹 전략 표준화** — 운영 문서 특성에 맞는 정량적 분할 기준이 아직 없음. 부서별 문서 스타일이 다른데 하나의 표준으로 통일할지, 문서 유형별로 다르게 갈지가 열려 있음
2. **지식 현행화 자동화의 범위** — Confluence Webhook 등으로 자동 재수집까지는 설계했지만, "자동으로 갱신 vs 사람이 검토 후 반영"의 균형을 어디에 둘지는 조직 성향에 따라 달라질 문제
3. **최소 개입 원칙** — 자동화 수준을 높일수록 사람이 개입할 지점이 줄어드는데, 어느 선까지 자동화하고 어디서부터는 반드시 사람이 확인하게 할지 (특히 VOC 메일 자동 알림처럼 외부 채널로 나가는 액션)
4. **MCP·에이전틱 확장 시 거버넌스** — 에이전트가 외부 시스템에 직접 액션(API 호출 등)을 취하는 범위가 넓어질수록, 승인 절차와 감사 로그를 얼마나 촘촘히 둘지에 대한 조직적 합의가 필요
