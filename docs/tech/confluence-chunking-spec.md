# Confluence 지식 청킹 규격 (2026-09-16)

> 2026-09-11 팀 피드백 1번("컨플 등 보관 지식의 청킹 전략을 먼저 실험 → 정해진 규격으로
> 리팩토링 가이드") 착수분. `data-storage-philosophy.md` §3 방법론(구조 분석 → 포맷 결정 →
> 결정론 파서 → LLM은 의미만)을 실제 Confluence 소스에 적용한 결과.

## 0. 방법 — 왜 실제 데이터부터 봤는가

"LLM이 문서를 보고 그때그때 청킹 전략을 추천"하는 대신, 이미 시스템에 들어와 있는 실제
Confluence 소스 문서(`rag_knowledge.source_type='confluence_bulk'`, 현재 서로 다른 원본
페이지 4건 — id 68/69/70/5831·5832쌍, 5834/5835는 5831/5832 중복 업로드)를 전부 직접
읽고 실측했다. 표본이 4건뿐이라 통계적 일반화엔 부족하지만, §3의 "산문 → Markdown"이라는
치트시트 한 줄로는 못 잡는 **산문 안의 하위 모양 차이**가 이미 분명히 보였다 — 앞으로
Confluence 축이 늘어날 때 이 문서에 사례를 계속 추가해 규격을 다듬는다.

## 1. 구조 분석 — 실제로 확인된 3가지 모양

> 원문은 사내 Confluence 소스라 이 세션이 직접 읽지 않고 로컬 LLM(`ask_internal.py
> --target local`)에 위임해 구조만 익명화 요약받았다(`feedback_internal_llm_routing`
> 메모리 참고). 아래 표는 그 요약 기반 — 실제 제품명/API명/조직명은 없음.

| id | 원본 성격(일반화) | 헤딩 구조 | 제목 유형 | 대략 길이 |
|---|---|---|---|---|
| 68 | 리포트형 (기능 개발 보고서) | 1단계 제목 + 2단계 3개 대분류 + 3단계 3개 소분류 | 짧은 명사구 | ~1700자 |
| 69 | 짧은 이슈 메모 | 1단계 제목 + 2단계 3개("관리현황/개발현황/수정요청"류) | 완결 문장형 | ~300자 |
| 70 | 한 줄 코멘트 | 헤딩 사실상 없음(제목+본문 1개) | — | ~100자 |
| 5831 | 체크리스트/런북형 (배포 절차) | 1단계 제목 + 2~3단계 다수(10개 이상) | 완결된 문장/절차 단계 | ~1600자 |
| 5832 | 체크리스트/런북형 (개발-리뷰 절차) | 1단계 제목 + 2단계 7개(번호순) | 완결된 문장/절차 단계 | ~600자 |

**관찰된 3가지 겉모습** (표본 4건 기준 — 아래 §3에서 실측해보니 청킹 규칙까지 나눌
필요는 없었다. 겉모습 구분 자체는 유효하지만 "규칙"은 겉모습과 무관하게 하나로 단순화됨):
1. **리포트형** — 섹션마다 다른 주제(개요/DB/API처럼). 제목이 짧은 명사구. (표본 1건)
2. **체크리스트/런북형** — 섹션마다 앞뒤로 이어지는 절차 한 단계. 제목 자체가 완결된
   문장인 경우가 많음 — Confluence에서 숫자 목록을 헤딩처럼 렌더링해서 생기는 모양으로
   추정. (표본 2건, 같은 업로드 배치에서 나온 페이지들이라 독립 표본이 아닐 수 있음)
3. **짧은 메모형** — 헤딩 없음, 전체가 300자 미만. (표본 2건)

## 2. 발견한 버그 — id=5831 콘텐츠 중복(청킹 이전 단계, 추출 단계)

> 아래는 실제 원문이 아니라 패턴만 보여주는 **가상 예시**(원문은 §1과 같은 이유로
> 직접 인용하지 않음). 로컬 LLM에 같은 원문을 구조 분석시켰을 때는 이 패턴을 못
> 잡았다 — 이 발견 자체는 이 세션이 원문을 직접 읽고 확인한 것.

id=5831의 실제 저장된 내용을 보면, **한 섹션의 본문이 그대로 다음 섹션의 제목으로
복제**돼 있다(가상 예시로 패턴만 재현):
```
## 1단계: A 확인
B 작업을 먼저 진행한다...

## B 작업을 먼저 진행한다...   ← 방금 본문이 그대로 다음 제목이 됨
C 작업을 이어서 진행한다 (...)
```
이 패턴이 문서 전체(9개 이상 섹션)에 걸쳐 일관되게 나타난다 — `chunker.py`의 병합 로직
버그가 아니라 **`web_crawler.py`의 `_extract_heading_sections()`가 Confluence storage
HTML을 섹션(제목/본문)으로 나누는 단계에서 한 칸씩 밀려 읽은 것**으로 보인다(원본
Confluence HTML을 실제로 열어보지 않고는 100% 단정은 못 함 — 이 세션에 Confluence
API 토큰이 없어 재현 확인 불가).

**영향 범위 확인**: 전체 confluence_bulk 4개 원본 페이지 중 **1건만** 이 패턴을 보임
(5831, 중복 업로드본 5834 포함 2 rows). 같은 배치의 5832는 정상(제목이 전부 고유하고
내용과 안 겹침) — 페이지별 원본 HTML 구조 차이에 따라 갈리는 것으로 보임, 파서 전체가
깨진 건 아님. **내용 손실은 없다**(모든 텍스트가 어딘가엔 남아있음, 라벨이 꼬였을
뿐) — 2026-09-10 DB/공통코드 3040건 오염(청크 자체가 깨져 내용이 유실됨)과는 심각도가
다르다. 규모도 작아(영향받는 고유 페이지 1건) 별도 soft-delete/재적재 캠페인은
과함 — 재현 확인 전까지는 **그대로 둔다**. 근본 원인은 실 Confluence API 접근이 가능한
세션에서 원본 storage HTML을 직접 떠서 재현 확인 후 고칠 것.

## 3. 실측 — 병합(1청크) vs 섹션별 분리

`nlpai-lab/KURE-v1`(운영 중인 실제 임베딩 모델)로 직접 재현: 리포트형(id=68)과
체크리스트형(id=5832) 각각을 "지금처럼 통째로 1청크"와 "`## ` 헤딩 기준 섹션별 분리"
두 버전으로 임베딩하고, 그 문서 내용을 실제로 겨냥한 질문들을 활성 지식(다른 23건)과
함께 코사인 유사도로 채점했다.

**리포트형(id=68, 5개 섹션)**

| 질문 | 병합 유사도(순위) | 분리 유사도(순위) |
|---|---|---|
| (§2.1 아키텍처 하위 항목) 특정 파라미터의 기능은? | 0.619 (24건 중 1위) | 0.664 (29건 중 1위) |
| (§2.2 DB Schema 하위 항목) 특정 함수 이름은? | 0.580 (1위) | 0.688 (1위) |
| (§2.3 API 하위 항목) 특정 엔드포인트의 변경 내용은? | 0.534 (1위) | 0.573 (1위) |
| (§1 개요 하위 항목) 관련 이슈 트래커 번호는? | 0.407 (**6위**) | 0.479 (**1위**) |

마지막 질문이 결정적 — 병합 상태에선 무관한 다른 문서 5개한테 밀려서, 운영 중인 top_k
(3~5)로는 **검색 결과에 아예 안 뜰 뻔했다.** 분리하면 1위.

**체크리스트형(id=5832, 7단계) — 가설이 틀렸다.** "절차형은 쪼개면 앞뒤 맥락이
사라져 손해"라고 예상했는데, 실측은 반대다:

| 질문 | 병합 유사도(순위) | 분리 유사도(순위) |
|---|---|---|
| 설계리뷰 요청은 누구에게? | 0.643 (1위) | 0.659 (1위) |
| 코드리뷰는 배포 며칠 전에? | 0.694 (1위) | **0.813** (1위) |
| 운영 배포용 branch는 어떻게? | 0.582 (1위) | 0.667 (2위로 근소 하락) |

체크리스트형도 단계별 질문엔 분리가 더 좋거나 비슷했다 — 유의미하게 손해 본 경우는
없었다.

**결론(정정)**: 리포트형/체크리스트형을 다른 규칙으로 나눌 필요가 없다. **결정론 규칙은
하나로 단순화된다: 섹션이 2개 이상이면 무조건 섹션당 1청크로 분리한다.** 기존
`_chunk_by_sections()`의 "합쳐도 max_chars(2000자) 이하면 병합" 로직이 두 아키타입
모두에서 손해였다.

**단, 검증 못 한 것 하나**: 이번 질문은 전부 "특정 섹션/단계를 콕 집는" 질문이었다 —
"전체 배포 프로세스가 어떻게 되나요?" 같은 **통합형 질문**은 테스트하지 않았다. 체크리스트
분리 시 걱정했던 "맥락 손실"은 이런 통합 질문에서 나타날 수 있다 — 분리해도 검색 자체가
top_k개를 함께 반환하니(§5 챗봇 답변 생성은 top_k 전체를 LLM에 넣는 "풀컨텍스트 주입"
구조, `PolicyLab.tsx`의 METRIC_INFO 참고) 실제 피해는 제한적일 가능성이 높지만, 확정하려면
통합형 질문으로 한 번 더 실측해야 한다.

## 4. LLM 역할

위 결정론 규칙(섹션 ≥2개 → 섹션당 분리)이 못 잡는 예외(예: 섹션 제목은 있는데 내용이
표뿐인 경우, HTML 구조가 깨져 섹션 추출 자체가 실패한 경우)만 LLM한테 넘긴다 — 청크
경계 자체를 LLM에 맡기지 않는다(§3 원칙 그대로, data-storage-philosophy.md).

## 5. 적용 범위 및 다음 단계

- **아직 코드 변경 안 함** — 규칙은 실측으로 확정됐지만(§3), `_chunk_by_sections()`는
  Confluence 전용이 아니라 txt/md/web/pdf 등 섹션 기반 청킹을 쓰는 모든 소스가 공유하는
  함수라, "병합 안 함" 규칙을 전역으로 바꾸면 다른 소스 타입(txt 등, 섹션이 원래 작고
  많아서 병합이 필요했을 수 있음)에 부작용이 있을 수 있다 — 전역 변경 전 다른 소스
  타입 샘플도 확인 필요.
- 통합형 질문("전체 프로세스는?") 테스트는 아직 안 함 — §3 마지막 문단 참고.
- 표본이 4건뿐이므로, Confluence 문서가 더 들어올 때(대량 업로드나 새 축 편입 시)마다
  이 규칙("섹션 ≥2개 → 분리")이 계속 유효한지 재검증할 것.
- id=5831 중복 버그는 재현 확인(Confluence API 접근 가능할 때) 후 고칠 것 — 지금은
  방치.
