# Confluence 지식 청킹 규격 (2026-09-16)

> 2026-09-11 팀 피드백 1번("컨플 등 보관 지식의 청킹 전략을 먼저 실험 → 정해진 규격으로
> 리팩토링 가이드") 착수분. `data-storage-philosophy.md` §3 방법론(구조 분석 → 포맷 결정 →
> 결정론 파서 → LLM은 의미만)을 실제 Confluence 소스에 적용한 결과.

## 0. 방법 — 왜 실제 데이터부터 봤는가

"LLM이 문서를 보고 그때그때 청킹 전략을 추천"하는 대신, 이미 시스템에 들어와 있는 실제
Confluence 소스 문서(`rag_knowledge.source_type='confluence_bulk'`, 현재 서로 다른 원본
페이지 4건 — id 68/69/70/5831·5832쌍, 5834/5835는 5831/5832 중복 업로드)를 전부 직접
읽고 실측했다. 표본이 4건뿐이라 통계적 일반화엔 부족하지만, §3의 "산문 → Markdown"이라는
치트시트 한 줄로는 못 잡는 **산문 안의 하위 모양 차이**가 이미 분명히 보였다 — 앞으로
Confluence 축이 늘어날 때 이 문서에 사례를 계속 추가해 규격을 다듬는다.

## 1. 구조 분석 — 실제로 확인된 3가지 모양

| id | 원본 성격 | 길이 | 구조 |
|---|---|---|---|
| 68 | 리포트형 (판매 제어 고도화 보고서) | 1761자 | `## 개요/변경사항/DB Schema/API/참고자료` — 5개 섹션, 서로 다른 독립 주제 |
| 69 | 짧은 이슈 메모 | 239자 | 헤딩 없음, 문단 4~5개 |
| 70 | 한 줄 코멘트 | 92자 | 헤딩 없음, 문장 1개 |
| 5831 | 체크리스트/런북형 (배포 일정) | 1566자 | `## 스텝1 / ## 스텝2 ...` — 순차 절차, 각 제목이 짧은 라벨이 아니라 문장 |
| 5832 | 체크리스트/런북형 (설계리뷰 프로세스) | 586자 | `## 1. .../## 2. ...` — 동일 패턴, 7단계 |

**세 가지 아키타입**:
1. **리포트형** — 섹션마다 다른 주제(개요/DB/API처럼). 제목이 짧은 명사구.
2. **체크리스트/런북형** — 섹션마다 앞뒤로 이어지는 절차 한 단계. 제목 자체가 완결된
   문장(평균 20자 이상, "~한다"/"~진행" 등으로 끝남)인 경우가 많음 — Confluence에서
   숫자 목록을 헤딩처럼 렌더링해서 생기는 모양으로 추정.
3. **짧은 메모형** — 헤딩 없음, 전체가 300자 미만.

## 2. 발견한 버그 — id=5831 콘텐츠 중복(청킹 이전 단계, 추출 단계)

id=5831의 실제 저장된 내용을 보면, **한 섹션의 본문이 그대로 다음 섹션의 제목으로
복제**돼 있다:
```
## 배포 일정 컨플 확인
개발 건 분석/설계 후 연동규격서 업데이트...

## 개발 건 분석/설계 후 연동규격서 업데이트...   ← 방금 본문이 그대로 다음 제목이 됨
개발 건 개발 진행 (...)
```
이 패턴이 문서 전체(9개 섹션)에 걸쳐 일관되게 나타난다 — `chunker.py`의 병합 로직
버그가 아니라 **`web_crawler.py`의 `_extract_heading_sections()`가 Confluence storage
HTML을 섹션(제목/본문)으로 나누는 단계에서 한 칸씩 밀려 읽은 것**으로 보인다(원본
Confluence HTML을 실제로 열어보지 않고는 100% 단정은 못 함 — 이 세션에 Confluence
API 토큰이 없어 재현 확인 불가).

**영향 범위 확인**: 전체 confluence_bulk 4개 원본 페이지 중 **1건만** 이 패턴을 보임
(5831, 중복 업로드본 5834 포함 2 rows). 같은 배치의 5832는 정상(제목이 전부 고유하고
내용과 안 겹침) — 페이지별 원본 HTML 구조 차이에 따라 갈리는 것으로 보임, 파서 전체가
깨진 건 아님. **내용 손실은 없다**(모든 텍스트가 어딘가엔 남아있음, 라벨이 꼬였을
뿐) — 2026-09-10 DB/공통코드 3040건 오염(청크 자체가 깨져 내용이 유실됨)과는 심각도가
다르다. 규모도 작아(영향받는 고유 페이지 1건) 별도 soft-delete/재적재 캠페인은
과함 — 재현 확인 전까지는 **그대로 둔다**. 근본 원인은 실 Confluence API 접근이 가능한
세션에서 원본 storage HTML을 직접 떠서 재현 확인 후 고칠 것.

## 3. 포맷/청킹 규칙 (결정론, LLM 불필요)

기존 `chunker.py`의 `_chunk_by_sections()`는 "합쳐도 max_chars(2000자) 안 넘으면
무조건 병합"이라, 리포트형(id=68)처럼 섹션이 여러 개여도 전체가 짧으면 통째로 한
청크가 돼버린다 — 이러면 "API 얘기만 궁금한 질문"도 DB 스키마·일정까지 섞인 청크와
비교당해 검색 정밀도가 떨어진다. 반대로 체크리스트형은 단계별로 쪼개면 "3단계가 2단계
결과에 이어진다"는 절차 맥락이 사라져서 오히려 손해다 — **두 아키타입은 반대 방향의
규칙이 필요**하다.

| 아키타입 판별 (결정론) | 청킹 규칙 |
|---|---|
| 섹션 ≥2개, 제목 평균 길이 **짧음**(20자 미만, 명사구) | **섹션당 1청크 — max_chars 이하로 합쳐도 병합 금지.** 각 제목·본문이 독립 주제라 합치면 검색 정밀도가 떨어짐. |
| 섹션 ≥2개, 제목 평균 길이 **김**(20자 이상, 완결된 문장/"~한다"류) | **문서 전체를 1청크로 유지**(단, max_chars 초과 시에만 그때 섹션 경계로 분할). 순차 절차라 쪼개면 앞뒤 맥락 유실. |
| 섹션 0~1개, 전체 300자 미만 | 그대로 1청크(현재 paragraph 폴백이 이미 정확 — 수정 불필요). |

판별 기준(섹션 수, 제목 평균 길이)은 `doc.sections`에서 바로 계산 가능한 값이라 LLM
없이 결정론 규칙만으로 분기할 수 있다.

## 4. LLM 역할

위 3개 아키타입 어디에도 안 맞는 경우(예: 섹션 제목 길이가 애매하게 걸치는 문서, 표가
본문에 섞인 경우 등)만 예외로 LLM에 "이 문서, 리포트형이야 체크리스트형이야?" 하나만
묻는다 — 청크 경계 자체를 LLM에 맡기지 않는다(§3 원칙 그대로).

## 5. 적용 범위 및 다음 단계

- **아직 코드 변경 안 함** — `_chunk_by_sections()`는 Confluence 전용이 아니라 txt/md/
  web/pdf 등 섹션 기반 청킹을 쓰는 모든 소스가 공유하는 함수라, 여기 반영하려면 다른
  소스 타입에 부작용이 없는지 먼저 확인 필요(규모 있는 변경이라 별도 확인 후 착수).
- 표본이 4건뿐이라, Confluence 문서가 더 들어올 때(대량 업로드나 새 축 편입 시)마다
  §1 표에 사례를 추가하고 아키타입 판별 기준(20자 임계값 등)을 재검증할 것.
- id=5831 중복 버그는 재현 확인(Confluence API 접근 가능할 때) 후 고칠 것 — 지금은
  방치.
