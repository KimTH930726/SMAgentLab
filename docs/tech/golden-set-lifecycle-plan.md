# 골든셋 관리 사이클 — 생성 → 사람 검토 → 버전 고정 → 실행 → 정확도 (계획, 2026-10-08)

> 상태: **계획**(시연 후 착수, 과설계 지양 기준으로 범위 축소 10/08). 사용자 요청: "지금은 즉석 질의만 있다 — 골든셋 생성과 애매한 부분 사람 검토(정책서 검토처럼)까지
> 관리 사이클을 제공하고, 그렇게 만든 세트로 실행 → 정확도로 가는 흐름". 관련: 백로그 §2-2(구분별 평가 화면), 원문 원장(§0).

## 1. 지금 상태 — 무엇이 손으로 돌고 있나

| 단계 | 지금 | 문제 |
|---|---|---|
| 생성 | 정책 골든 88문항은 손으로 만든 JSONL 파일. 검증 후보는 `scripts/gen_holdout_questions.py`(LLM) → md 파일, 컨플루언스 질문은 `scripts/gen_confluence_questions.py`(로컬 LLM) → JSONL | 화면 없음, 구분(정책서·컨플루언스·공통코드…)마다 따로, 개발자만 만들 수 있음 |
| 사람 검토 | `holdout_v1_review.md`를 사람이 읽고 거름, 채점기 표본은 로컬 HTML(`review-html`) | 검토 결과가 시스템에 안 남음(누가·언제·왜), 애매한 문항을 골라 주는 장치 없음 |
| 버전 | 파일 이름(v1)뿐 | 10/07 컨플루언스 재분할 때 질문 세트가 청크 id 기준이라 깨져 **전후 비교 불가**였다 |
| 실행 | 평가 게이트 "골든셋 실행"(정책서 축만, 검색 지표), 답변 정확도는 스크립트(`eval_answers.py`) | 구분별로 못 봄, 답변 정확도는 화면에서 실행 불가 |
| 결과 → 다음 세트 | 없음 | 신고("답변 틀림")·지식 공백·실패 문항이 세트로 돌아오지 않음 |
| 화면 | 평가 게이트의 **즉석 질의**만 사람이 직접 씀 | 즉석 질의는 일회성 — 쌓이지도 비교되지도 않음 |

## 2. 업계 표준 사이클 (조사 요약)

업계 도구들은 대체로 같은 고리를 돈다: **후보 생성(합성 + 실제 트래픽) → 사람(SME) 검토 → 버전 고정된 세트 → 실행(오프라인 평가)
→ 실패를 다시 후보로**. 채점기(LLM-as-judge)는 사람 판정과 맞춰 보정한다.

- **합성 생성**: Ragas는 문서에서 지식 그래프(개체·주제·요약)를 만들어 단일·다중 홉·추상 질문을 페르소나별로 생성. Databricks Mosaic AI
  Agent Evaluation도 문서에서 평가 세트를 자동 생성해 "SME를 부르기 전에" 커버리지를 확보.
- **사람 검토**: LangSmith 주석 큐(annotation queue) — 검토할 실행을 큐로 묶어 사람이 기준(rubric)대로 판정, 판정을 지정한 데이터셋으로
  바로 보냄. Databricks 리뷰 앱 — SME가 라벨링하면 평가 세트에 동기화되고 다시 평가.
- **버전**: LangSmith는 편집마다 자동 버전 + 태그로 "그 시점 세트"를 고정해 평가 — 세트가 바뀌어도 비교 가능.
- **실제 트래픽에서 성장**: Langfuse 등 — 골든셋은 "실제 실패에서 자라야" 한다(사용자 신고·사람 정정·이관·기각된 답이 후보).
  크기는 용도별(빠른 게이트는 수십, 전체 회귀는 수백~천), 알려진 실패 유형을 덮도록.
- **채점기 보정**: 체크리스트의 필수 항목 — LLM 채점이 사람과 얼마나 맞는지 주기적으로 잰다.

## 3. 우리 쪽 매핑 — 이미 있는 부품

| 업계 단계 | 우리에게 이미 있는 것 |
|---|---|
| 합성 생성 | `gen_holdout_questions.py`(정책), `gen_confluence_questions.py`(컨플루언스, 원문은 로컬 LLM만) |
| 실제 트래픽 후보 | 질의 기록(지식 공백·반복 공백 `glossary_mining`), 정정 신고 원장(`ops_improvement_item` "답변 틀림"), 실제 질문 사람 라벨(10/07 103개) |
| 사람 검토 UX | **정책 검토 큐**(위험도 분류 → 높음은 사람, 낮음은 자동 통과 + 표본 → 표본 반려 시 규칙 정지, 이력 `policy_review_log`) |
| 실행 | 평가 게이트 골든셋 실행(`track2`), `eval_answers.py`(collect → 로컬 LLM judge → report, 이력 #70) |
| 채점기 보정 | `eval_answers.py review-html / review-apply`(사람 표본 일치율) |
| 원문 기준 정답 | 정책은 식별키(파트·분류 경로·정책명), 지식은 원문 원장(예정) |

→ 새로 만들 것은 "세트·문항·검토·버전"의 **원장과 화면**이고, 생성기·채점기·실행기는 있는 걸 연결한다.

## 4. 설계 — 지금 실제로 막힌 것만 (과설계 지양, 사용자 10/08)

판단 기준: **우리 규모(구분별 수십~수백 문항)와 지금 실제로 막힌 일**. 업계 도구의 기능(위험도 자동 분류·자동 승인·트래픽 자동 수집)은
대규모 세트를 전제로 한 것 — 우리는 사람이 전부 보는 게 더 빠르고 정확하다. 실제로 막혀 있는 건 셋뿐:

1. **LLM이 만든 후보를 사람이 거를 화면이 없다** — 검증 후보 40문항을 md 파일로 읽고 거름, 결과가 시스템에 안 남음.
2. **세트가 바뀌면 전후 비교가 안 된다** — 10/07 컨플루언스 재분할 때 실제로 겪음(질문이 청크 id 기준).
3. **구분별로 실행·결과를 못 본다** — 정책서 축만, 답변 정확도는 스크립트(백로그 §2-2).

### 4-1. 하는 것 (MVP)
- **문항 원장** `eval_item` 한 테이블: 구분, 질문, 기대 답, 정답 근거(원문 위치 — 정책 식별키 / 원장 문서 + 섹션 경로, 청크 id 아님),
  질문 유형, 출처(LLM 생성·사람 작성·정정 신고), 상태(후보·승인·반려), 검토자·사유·시각. 별도 이력 테이블·버전 테이블은 만들지 않는다.
- **버전 = 실행 시점 승인 문항 목록 스냅샷**: 실행 기록에 그때 쓴 문항 id 목록을 같이 저장 → 같은 문항끼리 전후 비교(테이블 추가 없이).
- **검토 화면 하나**: 후보 목록 → 질문·기대 답·정답 근거 원문을 나란히 보고 승인 / 고쳐서 승인 / 반려(사유). 정책 검토 화면의 모양을
  재사용하되 위험도 분류·자동 승인은 넣지 않는다(전부 사람).
- **후보 넣기**: 기존 스크립트(`gen_holdout_questions.py`, `gen_confluence_questions.py`) 출력을 후보로 올리는 것만. 생성기 화면 연동은 안 함.
- **실행·결과**: 평가 게이트에서 구분 + 승인 문항으로 실행(검색 지표 + 답변 정확도), 결과는 구분별(§2-2와 한 화면). 같은 문항·같은 문맥이면
  이전 답 재사용(사내 LLM 토큰 지적 10/07 — 바뀐 문항만 호출).

### 4-2. 안 하는 것 (보류 — 실제로 필요해지면)
| 업계 기능 | 보류 이유 / 다시 볼 조건 |
|---|---|
| 위험도 자동 분류·자동 승인·표본 검토 | 문항 수백 개 이하면 전부 사람이 보는 게 빠름. 후보가 한 번에 수백 개씩 들어오기 시작하면 |
| 정정 신고·반복 공백·실패 문항 자동 수집 | 수동으로 몇 건 옮겨 본 뒤 효과가 확인되면(체계화는 수동 1회 이후 원칙) |
| 생성기 화면 연동·지식 그래프 기반 다중 홉 생성 | 스크립트로 충분. 개발자 아닌 담당자가 직접 만들어야 할 때 |
| 세트 용도 분리(게이트용/회귀용)·태그·별도 버전 테이블 | 실행 시점 문항 목록 스냅샷으로 비교가 되는 동안은 불필요 |
| 채점기 보정 주기 자동화 | 지금은 `review-html`로 수동 표본. 채점 결과를 두고 다툼이 생기면 |

## 5. 단계

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1 | `eval_item` + 기존 자산 이관(정책 골든 88·검증 후보 40·컨플루언스 56, 정답 근거를 원문 위치로) + 검토 화면 | 이관 전후 정책 골든 검색 결과 문항별 동일, 검증 후보 40을 화면에서 사람이 걸러 승인 수가 남음 |
| 2 | 평가 게이트에서 구분별 실행·결과(검색 + 답변 정확도), 실행 시점 문항 스냅샷, 같은 문맥 답 재사용 | 같은 문항 두 번 실행 비교가 화면에 나옴, 재실행 시 사내 LLM 호출이 바뀐 문항 수만큼 |

규모: 1단계 1~2일, 2단계 1~2일. 정답 근거(원문 위치)는 원문 원장(§0)과 같이 정한다 — 그래야 재적재에 안 깨진다.

## 6. 정해야 할 것
- 검토 담당: 파트별 누가 승인하나(정책 검토처럼 파트 권한 기준이면 추가 설정 없음).
- 채점 기준: 목록형 "목록 + 요약"을 정답으로 볼지(백로그 §2 탐색형 부분 13건과 연결).
