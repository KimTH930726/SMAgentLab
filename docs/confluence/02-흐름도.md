# 핵심 처리 흐름

> 1차 소스: `docs/flow.md`(질문 처리/pgvector/메모리/통계/SSE 등 9개 흐름 상세). 이 문서는 팀
> 공유용으로 핵심 흐름 4가지(채팅 검색, VOC 파이프라인, 정책서 파이프라인, 지식 생명주기)를
> 정리했다.

## 1. 채팅 질문 처리 흐름 (KnowledgeRAG)

```
사용자 질문 ("쿠폰 뺏어오기 실패한 건 어떻게 확인해?")
    │
    ▼
[0-A] Semantic Cache 조회 (Redis)
    │  코사인 유사도 ≥ 0.97 히트 → 저장된 답변 즉시 반환(파이프라인 스킵)
    │  미스 → 다음 단계
    ▼
[0-B] 멀티턴 검색 보강 (2턴 이상 대화일 때)
    │  직전 Q+A(각 80자)를 현재 질문에 결합해 검색용 텍스트 구성
    │  → 짧은 후속 질문("그 쿼리 알려줘")도 맥락 반영, 추가 LLM 호출 없음
    ▼
[1] 용어집(Glossary) 매핑
    │  질문 임베딩 → rag_glossary 벡터 유사도 검색 → 매핑된 용어를 질문에 덧붙임
    │  예: "쿠폰 뺏어오기" → "회수"라는 사내 용어로 보강
    ▼
[2] 하이브리드 검색 (rag_knowledge)
    │  벡터 검색(코사인 유사도) + 키워드 검색(ts_rank) 동시 실행
    │  final_score = (w_vector·v_score + w_keyword·k_score) × (1 + base_weight)
    │  DB/공통코드 카테고리는 벡터 점수를 0으로 만들고 키워드만 사용(구조화 데이터 오탐 방지)
    ▼
[2-1] 정책 데이터 병행 검색 (정책서가 있는 네임스페이스만)
    │  policy_param(RDB 정확조회) + policy_chunk(벡터 서술검색) 최대 10건
    │  LLM 프롬프트에는 재현율 유지를 위해 10건 그대로 포함
    ▼
[3] LLM 답변 생성
    │  few-shot 사례 + 검색된 지식 + 정책 컨텍스트 + 대화 이력을 프롬프트로 구성
    │  스트리밍(SSE)으로 토큰 단위 응답
    ▼
[2-2] 정책 근거 카드 역추적 (답변 생성 "이후")
    │  최종 답변 텍스트와 정책 후보 10건의 원문(raw_body)이 토큰 단위로 얼마나
    │  겹치는지 계산 → 가장 많이 겹치는 1건만 화면에 "정책 근거" 카드로 노출
    │  (겹치는 게 없으면 근거 없음 처리 — 억지로 아무거나 보여주지 않음)
    ▼
화면: AI 답변(Markdown) + 검색된 지식 카드 + 정책 근거 카드 + 👍/👎 피드백 버튼
```

**설계 포인트**
- 정책 인용 카드는 `results`(지식 인용) 배열과 **의도적으로 분리**돼 있다 — 프론트의 피드백
  컴포넌트가 `results[0].id`를 "이 답변이 참조한 rag_knowledge id"로 써서 지식 수정 흐름에
  연결하는데, 여기에 다른 테이블(policy_param/policy_chunk)의 id가 섞이면 오인식 위험이
  있기 때문.
- 근거 카드를 "검색 직후 1위"가 아니라 "답변 생성 후 역추적"으로 고른 이유: 검색 1위로
  LLM 컨텍스트까지 줄였다가, 그 1위가 실제로 무관해서 정답이 컨텍스트에서 빠지는 사고가
  실측으로 확인됐다. 그래서 LLM 컨텍스트(재현율)와 화면 노출(근거 압축)을 분리했다.

## 2. VOC 이메일 분석 파이프라인

```
파트별 공용 메일함 (Microsoft Graph API 폴링, 백그라운드 스케줄러)
    │
    ▼
[관련지식 사전 필터] check_relevance()
    │  등록된 지식과의 최고 유사도가 임계치(기본 0.35) 미만이면
    │  LLM 호출/Teams 발송 없이 skipped_relevance로만 기록(스팸/무관 메일 비용 절감)
    ▼
[LLM 분석] analyze_email()
    │  기존 하이브리드 검색 파이프라인 재사용 — 분류/심각도/오배치 여부 판정
    │  민감정보(IP/이메일/전화번호)는 LLM 프롬프트 직전에만 마스킹(DB/알림은 원본 유지)
    │  issue_signature(정규화된 짧은 이슈 요약)도 함께 생성
    ▼
[반복 패턴 탐지] detect_and_update_cluster()
    │  issue_signature 임베딩을 클러스터 centroid와 비교(코사인 유사도, LLM 호출 없음)
    │  같은 이슈가 7일 내 3건 이상 쌓이면 "반복 패턴"으로 확정
    │  해결방안 존재 여부(get_cluster_coverage)는 코사인 1차 필터(≥0.70) +
    │  LLM 재검증으로 판정(순수 유사도만으로는 무관 문서 오탐 발생 확인됨)
    ▼
[Teams 알림] 담당 파트 채널로 발송
    │  개별 VOC 카드에 "🔁 반복 패턴 — N건째 발생" 한 줄 + 해결방안(있으면) 얹어서 발송
    │  반복이 아닌 단독 VOC는 발송하지 않음(노이즈 최소화 원칙)
```

**설계 포인트**: 이 파이프라인이 팀 내에서 유일하게 "결심 없이도" 계속 도는 자발적 루프다 —
사람이 이미 하던 일(메일 확인)에 자동으로 얹혀 있어서 별도로 챙길 필요가 없다. 반면 채팅
피드백/지식 등록처럼 사람이 일부러 행동해야 하는 루프는 사용률이 낮게 관찰된다.

## 3. 정책서 데이터화 파이프라인

정책 엑셀 한 row를 3층 구조로 분해해 적재한다.

```
엑셀 업로드 (POST /api/policy/import)
    │
    ▼
[시트 판별 + 헤더 퍼지매핑] excel_parser.py
    │  용어정의 시트 / 정책 시트 자동 구분, 팀마다 다른 대/중/소분류 깊이를
    │  category_path TEXT[]로 흡수(고정 컬럼 대신)
    ▼
[LLM 3분류 분해] decompose.py
    │  각 정책 row를 narrative(서술) / param(파라미터 팩트) / unresolved(미해결) 로 분해
    │  완전 자동화 대신 "자동 처리 비율 최대화 + 실패 사유 캡처"가 목표
    ▼
[적재] service.py
    ├─ policy_item    (원문 + 메타, 버전 관리: UPDATE 대신 새 row INSERT)
    ├─ policy_param    (구조화 파라미터, RDB tsquery로 정확 조회)
    └─ policy_chunk    (서술 청크, 벡터로 의미 검색)
```

검색은 파라미터(RDB 정확조회) + 서술(벡터) **항상 둘 다** 실행한다. 이 "구조화=키워드,
서술=벡터" 하이브리드 방식이 지식-only(rag_knowledge에 원문 통째로 저장) 방식보다 나은지는
골든셋 89건(§실측)으로 검증했고, 4개 질문 유형 전부에서 하이브리드가 우세함을 확인한 뒤
채팅에 편입했다.

**부가 화면**
- **미분류(unresolved) 리포트**: LLM이 서술/파라미터 어느 쪽으로도 분류 못한 항목을 팀별로
  집계해서 보여준다(원문은 보존만 되고 유실되지 않음).
- **항목 브라우저**: 쿼리 없이 전체 정책 항목을 훑어보며 각 항목에 param/chunk가 어떻게
  달려있는지 확인.
- **저장소 실험실**: A(지식-only)/B(하이브리드) 저장 방식의 정답률을 골든셋으로 실측
  비교하는 화면 — 관리자가 버튼으로 재실행 가능.

## 4. 지식 생명주기 관리

```
지식 등록
    │
    ▼
[중복탐지] 청크 단위로 기존 활성 지식과 유사도 비교(임계치 0.88)
    │  임계값 이상이면 status='pending_review'로 저장(검색에서 숨김)
    ▼
[관리자 검토] 승인 / 반려 / 병합(merge) 중 선택
    │  병합 시 대상 지식을 덮어쓰기 전에 rag_knowledge_history에
    │  기존 content/embedding을 먼저 보존(v2.68 — 과거엔 이력 없이 소실됐음)
    ▼
지식 검색·응답에 사용
    │
    ▼
[피드백 루프]
    ├─ 👍 → 해당 지식 base_weight +0.1, few-shot 후보 등록
    ├─ 👎 → 프론트가 지목한 지식 1건 base_weight -0.1
    └─ 👎 + message_id 있음 → 그 답변이 실제로 참조한 지식 전체를
       rag_knowledge_review_flag에 리뷰 후보로 적재(자동 감점 아님, 사람이 볼 큐)
    ▼
[삭제 시] status='deleted'로 소프트 삭제(v2.68 — 과거엔 하드 DELETE라 복구 불가)
```

**현재 진행 중인 논의**: 이 루프들 중 "사람이 결심해서 행동해야 하는" 것들(피드백, 리뷰 큐
확인, 지식 등록)은 실사용률이 낮게 관찰돼, VOC 파이프라인처럼 기존 업무 흐름에 자연스럽게
얹는 방향으로 재설계를 검토 중이다(상세: `docs/tech/knowledge-lifecycle-design.md`).
