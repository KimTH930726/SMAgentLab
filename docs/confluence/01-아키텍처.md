## 레이어 구조

Ops-Navigator는 **에이전트 레이어**와 **플랫폼 공통 레이어**를 분리한 DDD(도메인 주도 설계)
구조를 쓴다.

```
backend/
├── main.py              # 앱 진입점 — DB풀/임베딩/LLM/에이전트 초기화, 마이그레이션 실행
├── agents/               # 에이전트 레이어 (AgentBase + AgentRegistry 패턴)
│   └── knowledge_rag/    #   현재 유일하게 운영 중인 에이전트
│       ├── agent.py      #   하이브리드 검색 + LLM 스트리밍 오케스트레이션
│       ├── knowledge/    #   지식/용어집 CRUD + 검색(retrieval.py)
│       └── ingestion/    #   문서 인제스천 파이프라인(파싱→청킹→태깅→Q&A생성)
├── service/               # 플랫폼 공통 레이어
│   ├── auth/              #   인증(JWT/bcrypt/Fernet)
│   ├── chat/               #   채팅 라우터·메모리(AgentRegistry로 위임)
│   ├── feedback/           #   피드백 기록 + 지식 가중치 조정
│   ├── admin/              #   네임스페이스·통계·LLM 설정
│   ├── llm/                #   LLM Provider 추상화(ollama/inhouse)
│   ├── email_voc/          #   VOC 이메일 분석 채널
│   └── policy/             #   정책서 데이터화 파이프라인
├── core/                  # config, database, security, dependencies(공통 인프라)
└── shared/                # embedding, cache(Semantic Cache), http_client(아웃바운드 HTTP)
```

**핵심 설계 원칙**

- **AgentRegistry 패턴**: 채팅 요청이 들어오면 `AgentRegistry.get(agent_type).stream_chat()`로
  위임한다. 새 에이전트를 추가할 때 `agents/` 하위에 모듈만 추가하고 레지스트리에 등록하면
  끝나는 구조 — Text2SQL/MCP 도구 에이전트를 깔끔하게 제거할 수 있었던 것도 이 구조 덕분이다
  (다른 에이전트가 서로를 import하는 역방향 의존이 없었음).
- **비동기 전용**: `asyncpg` + `httpx` async로 블로킹 I/O 없이 동작.
- **임베딩 싱글톤**: 앱 시작 시 임베딩 모델을 1회 로드하고 이후 스레드 executor로 재사용.
- **LLM Provider 패턴**: 환경변수 하나로 `ollama`(로컬 테스트) / `inhouse`(사내 LLM 게이트웨이)
  전환 가능.
- **Graceful Degradation**: LLM 연결이 끊겨도 검색 결과는 정상 반환하고 안내 메시지만 붙인다.

## 인증/인가

- **JWT 기반**: Access Token(30분) + Refresh Token(7일). `core/dependencies.py`의
  `get_current_user`/`get_current_admin`이 FastAPI `Depends`로 라우터 단위 보호.
- **네임스페이스 소유 파트 기반 권한**: 네임스페이스마다 `owner_part`가 있고, 같은 부서
  구성원만 그 네임스페이스의 데이터를 쓸 수 있다. `owner_part`가 NULL이면 전 부서 공통.
  Admin은 모든 권한 보유.
- **비밀번호/키 암호화**: bcrypt(비밀번호), Fernet 대칭암호화(사용자별 LLM API Key, Confluence
  PAT).
- **팀 SSO(Azure AD) 연동 착수**: `ops_user`에 `auth_provider`/`external_id`/`email` 컬럼을
  선반영해뒀고(로컬 계정 소수인 지금이 스키마 확장 비용이 제일 싼 시점이라는 판단), 실제
  OIDC 로그인 흐름은 Azure AD 앱 등록 승인 이후 구현 예정.

## 데이터베이스 (PostgreSQL 16 + pgvector)

테이블은 접두어로 도메인을 구분한다.

| 접두어 | 도메인 | 대표 테이블 |
|---|---|---|
| `ops_*` | 플랫폼 공통 | `ops_user`, `ops_namespace`, `ops_conversation`, `ops_message`, `ops_feedback`, `ops_query_log`, `ops_system_config` |
| `rag_*` | KnowledgeRAG 지식 | `rag_knowledge`, `rag_glossary`, `rag_fewshot`, `rag_conv_summary`, `rag_knowledge_history`(병합 이력), `rag_knowledge_review_flag`(피드백 리뷰 큐) |
| `ops_voc_*` / `ops_email_*` | VOC 이메일 채널 | `ops_voc_routing`, `ops_email_analysis`, `ops_voc_cluster`(반복 패턴) |
| `policy_*` | 정책서 파이프라인 | `policy_item`, `policy_param`, `policy_chunk` |
| `sql_*` | (제거됨) Text-to-SQL | `archive/with-text2sql` 브랜치 참고 |

- **HNSW 인덱스**(`vector_cosine_ops`): 벡터 근사 최근접 이웃 검색에 사용.
- **GIN 인덱스**(`to_tsvector('simple', content)`): 전문 검색(키워드).
- 모든 도메인 테이블이 `namespace_id`(INT FK)로 격리된다.

전체 컬럼 단위 정의는 `docs/table-definition.md` 참고.

## 임베딩 모델

| 항목 | 값 |
|---|---|
| 모델 | `paraphrase-multilingual-mpnet-base-v2` (Sentence-Transformers) |
| 벡터 차원 | 768 |
| 실행 위치 | Backend 컨테이너 내부(CPU) |
| 선택 배경 | 로컬(Mac) 개발 환경 제약 하에서 선택된 값 — 서버 인프라 확보 후 KURE-v1/BGE-M3 등과 벤치마크 비교 예정(`docs/tech/embedding-reranker-upgrade-plan.md`) |

같은 텍스트라도 용도에 따라 다른 임베딩을 쓰는 경우가 있다 — VOC는 지식 검색(RAG)엔 원문
임베딩을, 반복 유형 클러스터링엔 LLM이 뽑은 정규화 요약(`issue_signature`)의 임베딩을 쓴다
(정밀 매칭은 문맥 보존이 유리하고, 표현 차이를 넘어선 그룹핑은 정규화가 유리하다는 기준).

## 배포 토폴로지

- **개발**: `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build` —
  `./backend:/app` 소스 마운트로 코드 수정 후 `restart backend`만으로 반영.
- **운영(폐쇄망)**: `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build`
  — 사전 `docker load`로 이미지 반입 필요(`docs/deployment-closed-network.md`).
- **이미지 버전**: `.env`의 `IMAGE_TAG`로 관리(예: `v2.68`).
- **LLM 추론(Ollama)**: 컨테이너 밖 호스트에서 직접 실행 — Backend가
  `host.docker.internal:11434`로 접근. 모델은 `exaone3.5:2.4b`.
