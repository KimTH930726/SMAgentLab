# 개발 규율 (Development Conventions)

> 이 문서는 이론이 아니라, 이 프로젝트에서 **실제로 일어난 사고/지적을 근거로** 정리된 것이다.
> 각 항목에 "왜"가 붙어있는 이유가 그것 — 실제 사례 없이 지어낸 규칙은 여기 없다.
> 새 팀원, 다른 AI 세션, 그리고 향후의 자신을 위한 문서. `CLAUDE.md`가 매 세션 자동으로
> 로드되므로, 거기 요약 체크리스트 + 이 문서 링크를 둬서 실제로 지켜지게 한다.

## 0. 완료 기준 (Definition of Done)

"다 됐다"고 말하기 전에 아래를 전부 통과해야 한다 — 하나라도 빠지면 미완성으로 취급.

1. 코드 작성 — 기존 코드의 패턴(네이밍, 에러 처리 방식, 인증/권한 체크)을 먼저 확인하고 따름
2. 신규/변경 로직을 검증하는 테스트 추가 (§1 검증 원칙대로 — 200 확인이 아니라 결과값 비교)
3. 기존 회귀 테스트 스위트 전체 재실행 — 회귀 없음 확인
4. 프론트 변경 시 `npx tsc --noEmit` + `npm run build` 통과
5. 부작용 있는 변경은 실제 서버/DB로 시나리오 재현 검증 (§1-1, §1-2)
6. 변경분 자가 리뷰(diff 재검토) — 의도치 않은 파일/라인 안 섞였는지, 죽은 코드 안 남았는지
7. 아키텍처 변경이면 `docs/` 4종 동기화 (§4)
8. 위 전부 통과 후에만 커밋(§2) — 그 전엔 "구현 중"이지 "완료"가 아님

## 1. 검증 원칙

### 1-1. "200 응답"은 검증이 아니다
상태 전이·가중치 변경·FK로 다른 레코드를 연결하는 등 **부작용이 있는 로직**은, 엔드포인트가
200을 반환하는지만 보고 끝내면 안 된다. 실제 시나리오를 테스트 케이스로 구성해 **전(before)/후
(after) 값**까지 비교해야 한다.

> 실 사고: 나빠요 피드백 후 정정 지식을 등록하는 플로우에서 `is_positive: true`가 그대로
> 흘러가 오답 원인 지식의 검색 가중치가 오히려 **올라가는** 버그가 있었다. API는 항상 200,
> 화면도 정상적으로 다음 상태로 넘어갔다 — "눌러보고 에러 안 나면 OK" 수준으로는 절대 안 걸림.

### 1-2. `docker compose exec`로 재import한 것은 "떠 있는 서버"가 아니다
백엔드 변경 후 "검증 완료"라고 말하기 전에, 최소 한 번은 실제 떠 있는 서버 프로세스에 curl로
진짜 요청을 보내 상태코드·응답 바디를 확인한다. `exec`는 컨테이너 안에서 새 파이썬 프로세스로
디스크의 최신 코드를 재import하는 것뿐이라 "코드가 논리적으로 맞는지"는 검증돼도 "지금 요청을
받는 실제 프로세스가 그 코드로 동작 중인지"는 전혀 보증 못 한다.

> 실 사고: backend 컨테이너가 dev 마운트 없이 재생성돼 `/api/email-voc/*`가 전부 404를 내고
> 있었는데도, `exec` 기반 검증은 매번 "정상"으로 나왔다(그 순간 디스크 코드를 바로 재import
> 했으므로). 관리자가 화면에서 직접 클릭해보고서야 발견됨.

### 1-3. 리팩터링 시 기존 가드의 "전제"도 같이 재검토
로직 구조를 바꿀 때, 그 안의 가드/조건문(예: "1회만 표시", "재발송 방지")은 **그 리팩터링으로
전제 자체가 사라졌을 수 있다.** 코드는 "의도대로" 정확히 동작하고 테스트도 통과하지만, 그
의도 자체가 낡은 상태로 배포될 수 있다.

> 실 사고: VOC 반복 패턴 알림이 "별도 메시지"에서 "기존 카드에 통합"으로 바뀌었는데 "1회만
> 표시" 가드를 그대로 남겨둬서, 21건짜리 클러스터에서 3건째만 표시되고 나머지 18건은
> 안내 없이 나갔다. 유닛테스트는 완벽히 통과했다 — "무엇을 검증할지조차 인지 못한" 케이스.

## 2. 커밋 · 브랜치 워크플로우

- **테스트 완료 후 커밋+푸시를 한 번에** — 중간 커밋 금지. 코드 변경 → 빌드/타입체크 →
  (필요시) 사용자 확인 → 그다음 커밋+푸시.
- **관련 없는 변경을 한 커밋에 묶지 않는다** — `git add -A`처럼 넓은 스테이징은 의도치 않은
  파일을 같이 묶기 쉽다(실사고: 무관한 프레젠테이션 파일이 기능 커밋에 섞여 들어간 적 있음).
  경로를 명시해서 스테이징.
- **규모 있는 신규 기능은 dev_0에서 완전 검증 후에만 main 병합.** main은 실서비스 취급 —
  검증 안 된 대규모 기능이 섞이지 않게 한다. main → dev_0 방향 동기화는 수시로 하되, 반대
  방향(dev_0 전용 신규 기능 → main)은 완전 검증 후에만.
- **force-push는 매번 명시적 승인이 필요** — 한 번 허용받았다고 이후 계속 유효한 게 아니다.

## 3. 클린코드 · 리팩토링 판단 기준

### 3-1. 실측 근거 없이 미리 추상화하지 않는다 (YAGNI)
"나중에 재사용할 것 같다"는 예측만으로 범용 모듈/자동 판단 로직을 먼저 만들지 않는다.
**실 사례가 최소 2~3개 쌓인 뒤**, 그 사례들을 근거로 공통 패턴을 뽑는다.

> 실 사례: 지식 중복탐지에 LLM 자동 재검증(Comparator)을 처음엔 상위 우선순위로 뒀으나,
> 실측(발동 이력 7건, 전부 초기 3일 안에 몰림, 이후 재발동 0)을 확인하고 후순위로 내림.
> "지식화 실험실"의 표현계층/평가지표 자동 추천 게이트도 같은 이유로 보류(실 사례 1개뿐).

### 3-2. 안 쓰이는 기능은 새 화면을 늘리지 않는다
관리자 설정 화면에 새 토글/옵션을 추가하기 전에, 기존의 비슷한 설정 표면이 실제로 쓰이고
있는지부터 확인한다 — 안 쓰이는 admin 설정이 늘어나는 것 자체가 유지비용이다.

### 3-3. 집계·리포트 API만으로는 미완성
통계/집계 기능은 "API까지"가 완료 기준이 아니다 — 사람이 보고 다시 행동할 최소 읽기 전용
화면까지 한 묶음이다(쓰기 동작이 있는 무거운 UI는 별도 범위로 분리해도 정당함).

> 실 사고: 정책서 unresolved 집계 API만 만들고 "v1 범위 밖"이라며 UI를 미루려 했으나, 이건
> 데이터는 쌓이는데 아무도 안 보는 상태를 반복하는 것 — 과거 실제로 이 상태에서 데이터
> 유실 버그가 "우연히 발표 준비 중" 발견된 전례가 있음.

### 3-4. 자동화 도구(감사 에이전트 등)의 결과도 검증 후 반영
정적 분석/자동 감사가 낸 결과를 바로 실행하지 말고, 실제 코드·DB를 다시 확인한 뒤 반영한다.

> 실 사례(2026-09-09): 전체 코드베이스 클린코드 감사에서 나온 3개 우선 항목 중 2개
> (`rag_knowledge` 인덱스 없음, 특정 라이트모드 CSS 버그)가 재검증 결과 오탐으로 확인됨 —
> 인덱스는 별도 초기화 SQL 파일에 이미 있었고, CSS 패턴은 실제로는 올바른 패턴이었음.

## 4. 문서 동기화

아키텍처가 바뀌면 `docs/architecture.md` / `docs/flow.md` / `docs/table-definition.md` /
`docs/api-specification.md` 4종을 함께 갱신한다. `architecture.md`는 버전 번호를 올리고
변경 이력을 한 항목으로 남긴다(무엇을·왜·실측 결과까지). "결정 근거가 대화에만 남으면
인수인계 시/시간이 지나면 소실된다"는 게 이 프로젝트가 반복 확인한 원칙.

## 5. 관리자 화면(UI/UX)

- **문구는 짧고 직관적으로** — 개발자가 아는 배경지식을 화면에 장문으로 풀어쓰지 않는다.
  상시 노출 설명은 한 줄 이내로, "왜/언제만 해당"류 예외 설명은 `title` 툴팁으로 옮긴다.
  비슷한 개념(예: "화면 갱신 주기" vs "실제 폴링 주기")은 이름 자체를 다르게 지어 혼동을
  원천 차단한다.
- **라이트/다크 모드 색상**: 이 프로젝트는 `slate` 팔레트만 CSS 변수(`--slate-*`)로 테마별
  자동 반전된다(`[data-theme]` 기준). **slate 계열은 `dark:` 접두사 없이 단일 클래스로 쓴다**
  — `dark:`를 붙이면 오히려 이중 반전으로 깨진다(예: `text-slate-800 dark:text-slate-200`가
  라이트 모드에서 흰 배경에 흰 글씨가 됨). **slate가 아닌 accent 색상(indigo/amber/emerald
  등)은 반대로 `dark:` 쌍을 직접 명시**해야 한다 — 이 색상들은 자동 반전 대상이 아니라서
  안 붙이면 한쪽 테마에서 대비가 깨진다.
- **useMutation은 항상 onError를 갖는다** — 실패해도 화면에 아무 것도 안 뜨면 사용자가
  성공한 줄 알고 넘어간다. 폼 컨텍스트가 있으면 기존 에러 상태 슬롯을 재사용, 없으면
  `alert(err.message)` 최소 패턴이라도 넣는다(이 프로젝트 관례).

## 6. 인프라 관련

- 이 저장소에서 `docker compose` 명령은 **항상**
  `docker compose -f docker-compose.yml -f docker-compose.dev.yml <subcommand>`로 실행한다.
  `-f` 없이 특정 서비스만 지정해도, Compose가 의존 서비스(backend)까지 "설정 변경"으로
  인식해 재생성하면서 dev 바인드 마운트가 조용히 사라질 수 있다(frontend만 건드리는
  명령에서도 발생 가능).
- 조회만 하는 `docker compose ps`/`logs`는 `-f` 없이도 무방 — 문제는 컨테이너 상태를
  바꾸는 명령.

## 7. 보안 기본 원칙

- **시크릿은 항상 암호화 저장, 로그엔 절대 노출 금지.** 이 프로젝트는 Fernet 대칭암호화로
  LLM API Key/Confluence PAT/Graph API 자격증명/Teams 웹훅 URL을 저장한다(`core/security.py`).
  상태 조회 엔드포인트는 `configured: true/false`만 반환하고 복호화된 값을 절대 돌려주지
  않는다 — 새 자격증명을 추가할 때 이 패턴을 그대로 따른다.
- **모든 쿼리는 파라미터화** — 문자열 조합으로 SQL을 만들지 않는다(`asyncpg`의 `$1,$2...`
  플레이스홀더 사용). 동적 컬럼/함수명이 필요하면 f-string 삽입 대신 `CASE` 분기로 우회한
  전례가 있음(`feedback/router.py`의 가중치 갱신 쿼리).
- **모든 쓰기 API는 소유권을 검사한다** — `check_namespace_ownership()` 패턴(요청자 부서가
  리소스의 `owner_part`와 일치하는지)을 새 엔드포인트에도 동일하게 적용. admin은 예외.
- **admin 전용 엔드포인트는 `get_current_admin`으로 명시적으로 막는다** — 일반 인증
  (`get_current_user`)과 관리자 권한을 혼동하지 않는다.

## 8. 로깅 · 관측성

- **실패를 삼킬 때도 로그는 남긴다.** "best-effort" 보조 기능(자동 태깅, LLM 분해 실패 시
  unresolved 처리 등)은 요청을 실패시키지 않고 넘어가는 게 맞지만, **로그 한 줄도 없이
  넘어가면 안 된다.** 그러면 "게이트웨이가 죽어서 전부 실패"와 "내용이 진짜 애매해서
  실패"를 운영 중에 구분할 방법이 없어진다.
- `except Exception: pass`는 이 코드베이스에서 금지 패턴이다 — 최소 `logger.warning(...)`을
  붙인다. 사용자에게 실패를 숨기지 않는 것(§5)과는 다른 축이다 — 이건 **운영자가 나중에
  로그로 원인을 추적할 수 있는가**의 문제.

## 9. 성능 기준선

- **namespace 없이 전체 테이블을 반환하는 `list_*` 엔드포인트를 새로 만들지 않는다** —
  최소 namespace 스코프, 이상적으로는 페이지네이션. 데이터가 계속 쌓이는 테이블(지식,
  용어집, 로그류)일수록 우선순위 높음.
- **루프 안에서 DB 쿼리 하나씩 날리지 않는다** — 배치 쿼리(`WHERE id = ANY($1::int[])`)로
  묶거나, 불가피하면 최소한 `asyncio.gather`로 병렬화하고 커넥션 풀 크기 대비 동시 요청
  수를 계산해본다.
- **동기/CPU-bound 작업(엑셀·PDF 파싱 등)을 async 핸들러 안에서 그냥 부르지 않는다** —
  이벤트 루프를 블로킹한다. `run_in_executor`/`asyncio.to_thread`로 감싼다(임베딩 서비스가
  이미 이 패턴, 새 동기 파싱 코드도 동일하게).
- **새 테이블에 자주 필터링되는 컬럼(특히 `namespace_id`)은 처음부터 인덱스를 만든다** —
  나중에 추가하는 것보다 처음에 하는 게 항상 싸다(§3-1과 같은 논리).

## 10. AI 페어 개발(Claude Code) 특유의 원칙

- **애매한 긍정("웅", "좋다")을 실행 승인으로 확대해석하지 않는다.** 직전 메시지가 명확한
  액션 제안("~할까요?")이었을 때만 그 실행으로 간주한다 — 순수 정보/상태 확인 질문에 대한
  대답을 다음 실행의 승인으로 잘못 이어 붙이지 않는다.

  > 실사고(2026-09-09): "RDB랑 벡터 중 뭐가 찾아내는 거야?"라는 상태 질문에 "이거 마저
  > 나눠서 볼까요?"라고 제안까지 곁들였고, 뒤이은 "웅"을 그 제안(구현)의 승인으로 받아
  > 코드를 짰다. 사용자는 "현황을 물었는데 수정을 해버렸다"고 지적 — 실행이 아직 커밋
  > 전이라 되돌리기는 쉬웠지만, 애초에 확인 없이 앞서갔던 게 문제였음.

- **큰 작업 전엔 탐색→계획→실행→검증 순서를 지킨다.** 범위가 불확실하거나 여러 접근이
  가능한 작업은 Plan 모드로 먼저 설계를 사용자에게 확인받고 실행한다.
- **여러 독립 영역을 병렬 서브에이전트로 조사/감사할 수 있지만, 그 결과도 §3-4대로 검증
  후 반영한다** — 서브에이전트 결과라고 자동으로 신뢰하지 않는다(실사례: 오늘 감사 결과
  3개 중 2개가 재검증에서 오탐으로 걸러짐).
- **결정 근거는 코드 문서 + 메모리 양쪽에 남긴다.** 세션 메모리는 다음 세션의 나에게만
  보이고 팀에겐 안 보인다 — 팀이 봐야 할 근거는 반드시 이 저장소의 문서로 옮긴다(§4의
  근거이기도 함).
