## 1. 요약

컨플루언스에서 일괄 등록한 지식의 **청크 경계가 잘못 잘려**, 같은 섹션이 앞뒤 두 청크에 중복되고 다음 상위 제목이 앞 청크 끝에
매달린 채 저장됐다. 같은 원인 계열로 붙여넣기 등록은 "섹션 기준"을 골라도 실제로는 단락으로 잘리고 상위 맥락(heading_path)이
저장되지 않았으며, 컨플루언스 HTML 추출에서는 코드 블록·h5/h6 제목·표 구조가 사라지고 있었다.
기존 테스트·골든셋 평가·E2E가 모두 통과한 상태로 2주간 운영됐다 — **검증 체계가 "있어야 할 것이 있나"만 보고 "없어야 할
것(중복·유실)이 없나"는 보지 않았던 것**이 근본 원인이다.

- 같은 내용 청크가 검색 상위 슬롯을 두 번 차지해 다른 근거가 밀려날 수 있었다.
- 형제 섹션 내용이 다른 섹션 청크에 섞여(예: 1.2.1.1 내용이 1.2.1.2 청크에) 근거 카드·정정 검토 대상이 엉뚱하게 잡힐 수 있었다.

- 정책 골든셋 검색 지표(Recall@10 88.6%)는 결함 전후 동일 — 정책 답변 경로는 영향 없음.

## 4. 원인

### 4-1. 직접 원인 (코드)
1. **짧은 도입부 재부착이 레벨을 보지 않음** (`chunker._chunk_by_sections`): "짧은 상위 도입부를 하위 섹션 앞에 붙인다"가
   의도였지만 다음 섹션이 하위인지 확인하지 않아 형제·상위 섹션에도 붙었다. v2.99 이후 섹션 분리 모드에서는 그 도입부가
   자기 청크로도 한 번 더 저장돼 **같은 내용이 두 청크에**, 다음 상위 제목이 앞 청크 끝에 매달렸다.
2. **붙여넣기 "섹션 기준"이 조용히 단락 분할로 대체**: 코드 주석에만 "붙여넣은 텍스트엔 제목 구조가 없어 단락으로 대체"라고
   적혀 있고 화면·테스트에는 드러나지 않았다. 상위 맥락은 컨플루언스 일괄 등록 경로에서만 저장됐다.
3. **경로마다 다른 제목 인식기**: PDF 패턴은 "3.5kg"을 "## 3 / 5kg"로 잘라 본문을 바꾸고 제목엔 번호만 남겼다. md는 코드 블록 안
   `# 주석`을 제목으로 봤다.
4. **HTML 추출 누락**: 코드 매크로(CDATA)의 SQL이 섹션·원문 양쪽에서 사라짐, h5/h6 제목 유실(본문 줄로 섞임), 표가 칸마다 한
   줄로 풀림, dt/dd·div 직속 글자 누락.
5. **버전 교체 빈틈**: 재등록 시 옛 버전의 승인 대기 행이 남았다가 승인되면 옛 내용이 되살아남. 병합 대상 상태 미확인.

### 4-2. 근본 원인 (왜 2주간 못 찾았나)
| # | 원인 | 설명 |

## 5. 조치 (완료)

### 5-1. 코드 (v2.129)
- 청크 분할 재작성: 다음 섹션 레벨을 보고 짧은 상위 도입부·제목뿐인 상위는 **하위 청크 앞에 한 번만**, 본문 있는 짧은 섹션은
  유지(최소 길이 필터는 본문 없는 청크만), 연결 표현 병합은 크기 상한 안에서, 큰 섹션 재분할 조각마다 자기 제목.
- 제목 인식기 단일화(txt·md·PDF·붙여넣기 공통): `#` 제목 / 두 단계 이상 번호. "1." 한 단계·"3.5kg"·날짜·"~다" 문장·코드 블록은
  제목 아님. 붙여넣기도 같은 인식기 + 같은 청크 함수 + 상위 맥락 저장, 제목이 실제로 있으면 LLM 추측보다 구조 우선.
- HTML 추출 재작성: 문서 순서대로 한 번 순회, 표는 행 단위(칸 안 줄바꿈·"|" 처리, 제목을 품은 배치용 표는 안쪽 그대로), 코드는
  코드 블록, h1~h6. 일괄 등록 상위 맥락 = [페이지 제목, 페이지 안 조상](형제 페이지로 부모 확장이 번지지 않게).
- 빈 줄 없는 큰 섹션은 줄 경계에서 나눔(문장 중간 절단·부분 겹침 제거), 재분할 조각은 제목 머리말 포함 상한 이내.
- 파일·단일 URL 등록도 상위 맥락을 미리보기→확정까지 전달.
- 버전 교체 시 옛 승인 대기 행도 폐기. 병합은 같은 파트의 활성 지식에만(예전엔 다른 파트 지식을 덮어쓸 수 있었음 — 리뷰에서 발견).
- 지식 상세 "문서 구조": 분할 방식별로 다르게 — 섹션 구조는 상위 경로 + 검색 때 함께 붙는 이웃(검색 코드와 같은 규칙) + 앞뒤,
  단락·고정 길이는 같은 문서의 앞뒤 조각, 직접 입력은 단건. 파트 권한 검사.

## 7. 원문 원장(SoT) 점검 — "다시 자를 원본이 있는가"

이번 보정은 원문이 아니라 **저장된 청크에서 원문을 복원**해 다시 잘랐다(겹친 부분 한 번만). 이번엔 결함이 "중복"이라 복원이
가능했지만, 결함이 "유실"(예: 코드 매크로 SQL이 추출 단계에서 사라짐)이면 청크로는 되살릴 수 없다. 원장이 있어야 재처리가 된다.

| 데이터 | 원장 | 재처리 가능성 | 현황(활성 기준) |
|---|---|---|---|
| 정책서(엑셀·JSON) | **있음** — 정책 항목 행마다 원문(raw_body) + 파일·시트·행 | 가능(행 → 서술 조각 재생성) | 377/377 추적 가능 |
| 컨플루언스 지식 | **없음** — 청크만 저장. 외부 원본(컨플루언스 페이지)이 사실상 SoT인데 연결 정보도 9/28 이후 등록분만 | 페이지 ID가 있으면 재수집 가능, 없으면 불가 | 56청크 중 페이지 ID 보유 **0** — 원본 위치는 "Confluence 18개 페이지" 같은 묶음 이름뿐 |
| 파일·붙여넣기 지식 | **없음** — 원본 파일·붙여넣은 원문을 저장하지 않음 | 불가(청크가 유일 사본) | 붙여넣기 1청크 |
| 직접 입력 지식 | 지식 자체가 원문 | 해당 없음 | 18건 |

판단: 지식 쪽은 **청크가 원장 역할을 겸하고 있어** 파이프라인 결함이 데이터에 그대로 굳는 구조다. 정책서처럼 원문 원장을 두고
청크는 거기서 다시 만들 수 있는 파생물로 두는 게 맞다.

결정(2026-10-07): **업계 표준 방식으로 진행** — 아래 제안의 권장 기본값 그대로, 구현은 시연 후(dev_0 완전 검증 후 main).

설계:
- `rag_source_document`(원문 원장): 등록 단위 1건 = 원문 스냅샷(컨플루언스는 storage HTML + 페이지 ID·버전, 파일은 파일명·해시·추출 텍스트,
  붙여넣기는 원문) + 내용 해시 + 파서 버전 + 등록자·시각. 청크는 `source_document_id`로 연결.
- 등록 흐름: 원문 저장 → 파싱·분할(파생) → 품질 검사. 결함이 나면 "원장에서 다시 분할" 한 번으로 재처리(파서 버전 비교).
- 컨플루언스는 외부 원본이 바뀌거나 지워져도 재현할 수 있게 스냅샷을 남기되, 원본 버전이 바뀌면 재수집(버전 교체 v2.115 경로).
- 저장 위치는 지금 청크와 같은 DB(새로운 외부 노출 없음). 보존 기간·용량은 검토 필요.

## 8. 남은 위험·확인 필요
- 컨플루언스 원본의 코드 매크로 SQL은 옛 추출기에서 이미 사라진 채 저장돼, 저장 데이터 보정만으로는 복구되지 않는다 — 해당 페이지가
  코드 블록을 포함하는지는 원본 재수집 시 확인.
- 원본 문서의 번호 중복(1.2.1.2가 개점·폐점 두 곳)은 컨플루언스에서 수정 필요.
- 컨플루언스 검색 평가 질문 세트는 청크 id 기준이라 재분할로 무효 — 로컬 LLM으로 재생성 후 재측정 필요. 답변 정확도 88문항 재측정 예정.
- 동시 일괄 등록 잠금 부재(코드 추적만, 미재현), 단일 페이지 등록이 일괄 등록과 다른 분할 전략을 고를 수 있음 — 백로그.

## 9. 교훈
1. 변환·적재 로직의 테스트는 **사례가 아니라 성질**로 쓴다. "들어있다"는 "중복·유실이 없다"를 보증하지 않는다.
2. 데이터 품질은 데이터에서 직접 잰다. 검색·답변 지표는 중복을 오히려 보상할 수 있다.
3. 모드·전제를 바꾸는 변경은 기존 가드의 전제를 같이 점검한다.
4. 대체 처리(fallback)는 보이게 한다. 주석에만 있는 대체는 결함이 된다.
