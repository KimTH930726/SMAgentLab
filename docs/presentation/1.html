백엔드 레이어 구조 — Agent / Service / Core

agents/

파이프라인 레이어. AgentBase 추상 클래스 + AgentRegistry 싱글톤. 새 에이전트 = 모듈 추가 + 레지스트리 등록만으로 완결.

service/

플랫폼 공통 레이어(인증/채팅/피드백/정책/VOC 등). DDD식으로 도메인별 schemas/service/router 응집.

core/ · shared/

DB 풀, JWT/Fernet 보안, 임베딩 싱글톤, 시맨틱 캐시 — 전 에이전트가 공유하는 인프라.

설계 원칙: 플랫폼(인증·세션·피드백)과 에이전트(실제 파이프라인)를 분리한다 — 채팅 라우터는 AgentRegistry.get(agent_type).stream_chat()으로 위임만 하고, 검색/생성 로직은 전혀 모른다. Text-to-SQL 에이전트를 v2.51에서 통째로 걷어냈을 때 이 경계 덕분에 플랫폼 코드는 한 줄도 안 건드렸다(코드는 archive/with-text2sql 브랜치에 보존).

2기술 스택 — 왜 이걸 골랐나

왜 PostgreSQL + pgvector인가 핵심 결정

별도 벡터 DB(Pinecone/Milvus/Weaviate 등)를 두지 않고, 정형 데이터와 벡터를 한 DB에 둔다. pgvector 확장 하나로 VECTOR(768) 컬럼 + HNSW 인덱스를 기존 테이블에 그대로 추가할 수 있다.
  • 구조화 데이터와 벡터가 같은 트랜잭션 안에 있다 — 지식 등록 시 content와 embedding이 같은 INSERT로 원자적으로 들어간다. 별도 벡터 DB였으면 이중 쓰기·정합성 문제가 생긴다.
  • 정형 조회(SQL)와 의미 검색(코사인 유사도)을 한 쿼리에 섞을 수 있다 — WHERE namespace_id=$1 AND status!='deprecated' ORDER BY embedding <=> $2처럼 필터+벡터 정렬이 그냥 SQL이다.
  • 벡터는 파생물, pg는 source of truth — 임베딩 모델을 바꾸면 재인덱싱은 당연한 일이다. 비싸고 비가역인 작업(엑셀 파싱+LLM 분해+사람 검수)은 pg에 원문(raw_body)으로 남아 pg_dump로 그대로 이관되고, 벡터는 언제든 원문에서 재생성 가능하다는 전제로 설계했다.
  • 운영 비용 — 전용 벡터 DB 클러스터를 별도로 운영할 필요가 없다. 폐쇄망 배포(docs/deployment-closed-network.md)에서도 이미 쓰던 Postgres 인프라를 그대로 확장하면 된다.

인덱스 두 종류를 같이 쓴다: HNSW(vector_cosine_ops, 근사 최근접 이웃)로 벡터 검색을, GIN(to_tsvector)으로 전문 검색(FTS)을 각각 최적화한다 — 하이브리드 검색(§3-5)의 기반.

왜 Redis 시맨틱 캐시인가

완전히 같은 질문이 반복되는 게 아니라 의미가 비슷한 질문이 반복된다(오탈자, 존댓말 차이, 어순 차이). 그래서 캐시 키를 문자열 해시가 아니라 질문 임베딩의 코사인 유사도로 잡았다 — 임계값 이상이면 검색+LLM 생성을 전부 건너뛰고 즉시 응답한다. Redis가 죽어도 캐시만 비활성화되고 서비스는 정상 동작한다(graceful degradation).

왜 로컬 임베딩(sentence-transformers)인가

paraphrase-multilingual-mpnet-base-v2(768차원, 다국어)를 백엔드 컨테이너 안에서 직접 구동한다. 외부 임베딩 API를 안 쓰는 이유: ①사내 문서/질문이 외부로 나가지 않음(데이터 경계) ②API 비용·레이턴시 없음 ③오프라인(폐쇄망) 배포 가능. Docker 빌드 시 이미지에 모델을 미리 받아둬서 컨테이너 기동 지연도 없다.

왜 LLM Provider를 추상화했나

LLMProvider 추상 클래스 뒤에 OllamaProvider(로컬, exaone3.5)와 InHouseLLMProvider(사내 DevX 게이트웨이, GPT/Claude/Gemini 선택 가능)를 둔다. 환경변수 하나로 전환되고, 관리자 화면에서 재시작 없이 런타임 전환도 가능하다 — 온프레미스 vs 클라우드 LLM 어느 쪽이든 같은 파이프라인 코드로 돈다.

왜 React + Zustand + TanStack Query인가

Redux 같은 무거운 상태관리 대신 Zustand(전역 스트림/인증 상태)와 TanStack Query(서버 상태 캐싱)를 분리했다 — SSE 스트리밍처럼 자주 바뀌는 상태(토큰 누적)와 REST로 가져오는 상태(대화 목록, 지식 목록)의 갱신 주기가 다르기 때문. TailwindCSS로 커스텀 CSS 없이 일관된 디자인 토큰(bg #0F172A / accent #6366F1)을 유지한다.

3채팅 파이프라인 상세

한 번의 질문이 답변으로 나오기까지 실제로 거치는 7단계. 각 단계가 "왜 필요한가"를 중심으로 본다.

3-2. 시맨틱 캐시 레이어 semantic layer

완전 일치가 아니라 의미 유사도로 캐시 히트를 판정한다. 질문을 정규화(공백·자모 간격·대소문자 정리)한 뒤 임베딩하고, Redis에 저장된 최근 캐시 엔트리(최대 200개 후보)와 코사인 유사도를 비교한다.

키 설계

semcache:{namespace}:{agent_type}:* — 에이전트 타입으로 분리해 KnowledgeRAG와 MCP 도구 캐시가 서로 새지 않게 한다.

파라미터 (관리자 조정 가능)

유사도 임계값 기본 0.88(한국어 단문 최적값으로 튜닝), 현재 운영값 0.92 · TTL 1800초(30분) · Redis 미연결 시 캐시 없이 정상 동작(graceful degradation)

캐시 payload에는 답변뿐 아니라 mapped_term, results, policy_citations까지 통째로 저장한다 — 캐시 히트 시에도 화면에 똑같은 근거·인용이 재생되도록.

3-3. 멀티턴 검색 보강 multi-turn

"그 쿼리 알려줘" 같은 후속 질문은 그 자체로는 검색이 안 된다. 그래서 DB에서 직전 Q+A를 조회해(각 80자로 자름) 현재 질문 앞에 붙여 검색용 문장을 만든다 — LLM을 한 번 더 부르지 않고 DB 조회 1회(1ms 미만)로 끝낸다. 단, 이 결합 문장은 검색에만 쓰고 LLM에 전달하는 실제 질문(query)은 원본 그대로 유지한다.

search_question = f"{prev_Q[:80]} {prev_A[:80]} {현재_질문}"
→ 이 문장으로 임베딩·용어매핑·하이브리드검색 수행
→ query_vec은 이후 정책 검색(§8)에서도 재사용해 중복 임베딩 방지

3-4. 대화 메모리 — ConversationSummaryBuffer + Semantic Recall context maintenance

대화가 길어져도 LLM 컨텍스트 윈도우를 넘기지 않으면서 관련 맥락을 유지하는 전략. 핵심은 "최근 것은 그대로, 오래된 것은 요약해서 필요할 때만"이다.

교환 1~4가 쌓이면(4회 = SUMMARY_INTERVAL) → 오래된 교환(1~2)을 LLM으로 요약
  → 요약을 임베딩해 rag_conv_summary에 저장 (백그라운드, 응답 지연 없음)

새 질문이 들어오면:
  ├─ 최근 2회 raw 교환(working memory) → 항상 그대로 포함
  └─ 현재 질문 벡터로 과거 요약 검색(유사도 ≥ 0.45, 최대 2개) → Semantic Recall
        관련 없는 과거 주제는 자동으로 컨텍스트에서 빠짐

예: 10번째 교환에서 "아까 쿠폰 관련 쿼리 다시 알려줘"라고 물으면, 1~2번째 교환 요약이 유사도 0.72로 리콜되어 몇 턴 전 얘기도 정확히 이어받는다.

3-5. Weighted Hybrid Search top_k / w_vector / w_keyword

final_score = (w_vector × v_score + w_keyword × k_score) × (1 + base_weight)
기호의미기본값비고
v_score코사인 유사도 (HNSW 인덱스)0~1의미가 유사할수록 ↑
k_scorets_rank (GIN 인덱스, BM25 계열)0~0.1대정확한 단어 일치일수록 ↑
w_vector / w_keyword가중치 비율0.7 / 0.3사이드바 슬라이더로 개인화(로컬 저장, DB 미저장)
base_weight문서 자체 가중치1.0👍 시 +0.1 / 👎 시 −0.1 자동 조정(§4)
top_k반환 개수5슬라이더로 조정, 리랭커 활성 시 후보를 더 넓게 가져와 CrossEncoder로 재정렬

왜 벡터+키워드를 섞나: 벡터만 쓰면 표형식 데이터(공통코드, 파라미터표)에서 어휘만 겹쳐도 오탐이 난다는 걸 실측으로 확인했다(§7 라우팅 원칙). 그래서 특정 카테고리(DB/공통코드)는 벡터 점수를 0으로 만들고 키워드만 쓰도록 랭킹 공식 자체를 분기한다(_KEYWORD_ONLY_CATEGORIES).

3-6. SSE 스트리밍 — asyncio.Task + Queue 디커플링

LLM 생성이 HTTP 연결 수명과 완전히 분리된다. 사용자가 탭을 닫아도 백엔드 워커는 끝까지 실행해 DB에 저장한다 — 재접속 시 status='generating'을 감지해 폴링으로 자동 이어받는다.

type: status  → 단계별 진행 표시 (embedding/context/search/llm)
type: meta    → ①0.02초 내 conversation_id/message_id ②검색 완료 후 결과 카드
type: token   → LLM 토큰마다, 20토큰 단위로 DB 부분 저장
type: done    → 완료, 피드백 버튼 활성화

3-7. 파이프라인 디버그 단계 debug

POST /api/chat/debug는 LLM을 호출하지 않고 검색 파이프라인 전 구간의 중간값을 그대로 반환한다 — 관리자 화면 "디버그 패널"에서 왜 이 문서가 검색됐는지 단계별로 확인 가능하다.

enriched_query(용어 보강 후 질의) · glossary_match(매핑된 용어+유사도) · 문서별 v_score/k_score/final_score · fewshots(유사 Q&A 전체, 임계값 미달분도 포함해 어디서 필터링되는지 확인 가능) · context_preview(실제 LLM에 들어갈 프롬프트 텍스트 미리보기)

이건 "검색이 왜 이렇게 나왔는지"를 블랙박스로 안 남기겠다는 설계 원칙의 실현이다 — 결과(답변)뿐 아니라 과정(점수)까지 투명하게 보여준다.

4지식 관리 · 선순환 구조

등록 경로 4종
  • 파일 업로드 (PDF/Excel/CSV/MD/TXT)
  • URL / Confluence 수집 (PAT 인증, BFS 트리 탐색)
  • 직접 입력 (단건)
  • 대량 텍스트 붙여넣기 (자동 분할)
등록만으론 안 끝난다
  • 용어집 — "DS"→"Discount Service" 같은 사내 약어를 정식 용어로 매핑, 검색 전 질문에 보강
  • Few-shot — 정답 예시를 등록해 답변 톤·형식까지 제어

피드백 선순환

👍 → base_weight +0.1, status='resolved', few-shot 후보 자동 생성
👎 (단순 스킵) → base_weight -0.1, status='unresolved'
👎 + 지식 등록 교정 → 오답 원인 지식 페널티(-0.1) + resolved_knowledge_id 연결
검색 결과 없음 / "관련 지식을 찾지 못했습니다" → status='no_knowledge' (지식 공백 신호)

사용자는 평소처럼 질문하고 피드백 버튼만 누르면 된다 — 그 행동 하나하나가 검색 가중치를 조정하는 신호가 되고, "몰라서 답 못 한 질문"은 no_knowledge로 자동 기록돼 관리자 대시보드에서 "지식 공백" 카드로 드러난다. 클릭 한 번으로 등록 폼까지 이어진다 — 발견→등록→즉시 반영의 관리 사이클.

6저장소 전략 실험실 — Track 2

"이 데이터는 벡터가 나은가, RDB가 나은가, 하이브리드가 나은가"를 감으로 정하지 않고 골든셋으로 수치화하는 재사용 프레임워크.

가설이 실측으로 뒤집힌 과정

1차 측정: "하이브리드가 무조건 낫다"는 가설이 기각됐다 — param 유형에서 A(지식-only)가 크게 앞섬(73.9% vs 34.8%). 원인: item의 36%가 파라미터로만 분해돼 벡터 청크가 하나도 없어서, 자연어 질문이 짧은 필드와 어휘가 안 겹치면 못 찾았다. 같은 날 수정: 모든 item에 최소 1개 벡터 폴백 청크를 보장 → 재측정하니 4개 유형 전부 하이브리드 우세로 반전.

교훈: 검색 전략을 배타적으로 나누지 말고 "정확 조회 + 벡터 폴백"을 겹쳐야 한다 — 이 교훈은 retrieval-routing-pattern.md에 반영됐다.

POST /api/policy/track2/run로 API화되어 관리자가 버튼 하나로 재실행 가능(1~2분), 결과가 수동 스크립트와 정확히 동일함을 실측 확인했다. 두 가지 모드로 쓰인다: 탐색(새 데이터 유형 편입 전 저장 전략 결정) / 게이트(스키마·프롬프트·골든셋 변경 시 회귀 판정).

7검색 전략 라우팅 — 재사용 원칙

벡터 검색은 "의미가 비슷한 것"을, 키워드/RDB 조회는 "정확히 일치하는 것"을 찾는다. 데이터가 구조화된 값(코드표·파라미터·수치)이면 후자, 서술형 문장이면 전자가 정답.

이 원칙이 프로젝트에서 두 번 독립적으로 재발견됐다 — 구현 방식은 매번 달랐다:

#사례문제구현
1rag_knowledge(v2.49)공통코드 카테고리(전체 88%)가 코사인 유사도로 무관한 문서와 오탐같은 테이블 안에서 랭킹 공식 분기(_KEYWORD_ONLY_CATEGORIES)
2정책서 파이프라인파라미터를 서술과 같이 벡터화하면 같은 문제 예상(설계 단계 사전 적용)아예 다른 테이블로 분리(policy_param vs policy_chunk)
경계 사례가 2개뿐이라 범용 자동 라우팅 모듈은 만들지 않는다 — 제3의 변형이 뭘지 아직 모른다(과설계 금지, YAGNI). 다음 축이 실제로 생기면 이 문서의 체크리스트로 판단하고 사례를 추가하는 방식으로 키운다.

8정책 검색의 메인 채팅 편입 — "게이트가 편입을 판정한다"

실험실(§6)이 하이브리드 우세를 수치로 확정해준 뒤에야 실제 채팅에 편입했다 — 판단 순서 자체가 핵심.

1단계 (텍스트 컨텍스트 병합)

agent.py:stream_chat()이 rag_knowledge 검색과 병행해 정책 검색을 호출, 결과를 LLM 프롬프트에 텍스트로 더한다. has_policy_data(namespace)로 정책 없는 네임스페이스는 매 턴 쿼리를 스킵하고, 이미 계산된 질문 임베딩을 재사용해 중복 임베딩을 방지한다.

2단계 (정책 근거 인용 카드) → 1건 압축

"정책에서 온 답인지 기준정보에서 온 답인지 구분이 안 된다, 원문도 보여달라"는 피드백으로 근거 카드 UI를 추가했는데, 처음엔 최대 10건(param 5 + narrative 5)이 그대로 노출돼 "근거가 너무 많다"는 재피드백을 받았다.

1차 시도 폐기 검색 직후 벡터 점수 1위 후보 하나로 LLM 컨텍스트까지 줄였더니, 그 1위가 실제로 무관한 후보였고 정답이 컨텍스트에서 통째로 빠져 LLM이 "관련 지식을 찾지 못했습니다"로 답변 자체에 실패하는 걸 실 E2E로 확인 — 즉시 되돌림.
최종 설계: LLM 컨텍스트는 원래대로 다중 후보(top_k 5×2)를 유지해 재현율을 지키고, 화면에 보여줄 근거 카드만 답변이 다 나온 뒤에 최종 답변 텍스트와 원문의 토큰 겹침을 계산해 가장 많이 겹치는 1건을 역추적한다. "화면 표시 개수"와 "검색 재현율"은 서로 다른 축이라는 게 이번에 실측으로 확인된 교훈.

9VOC 이메일 분석 채널

같은 지식베이스·같은 검색 로직·같은 피드백 구조를 메일 채널에 그대로 이식한 사례 — "관련 없는 메일은 애초에 LLM까지 안 보낸다"는 새 통제 지점이 추가됐다.

수집 → 필터 → 분석 → 클러스터링 → 발송

Graph API 폴링 → check_relevance() 사전 필터(임계값 미만이면 LLM 호출 없이 스킵)
  → 기존 하이브리드 파이프라인 재사용해 분류(system_error/user_mistake/uncertain)·심각도 판정
  → 반복 유형 클러스터링(issue_signature 임베딩 비교, LLM 호출 없음)
  → 발송 게이트: 클러스터 최소 건수 넘을 때만, 그 이후는 배수(3/6/9건째)에서만 알림

IP/이메일/전화번호는 LLM에 넣기 직전 마스킹(사내 LLM 게이트웨이가 이런 패턴 포함 시 응답을 거부하는 정책 대응). 30일 고정 보관정책으로 ops_email_analysis/ops_email_poll_cycle이 자동 정리된다.

10인증 · 권한 모델

JWT(Access 30분 + Refresh 7일) + 네임스페이스 소유 부서(owner_part) 기반 권한. 소유 부서 구성원만 CRUD, 타 부서는 읽기 전용. owner_part=NULL(공통 네임스페이스)은 모든 사용자가 CRUD 가능. 사용자별 LLM API Key·Confluence PAT는 Fernet 대칭 암호화로 저장한다.

11사내 LLM 라우팅 브리지

SMAgentLab이 아니라 ~/.claude/ 공통 레이어 — 모든 세션에서 재사용하는 인터랙티브 모델 라우팅 도구.

분기대상용도
기본(아무 말 없음)프론티어 Claude이 세션이 직접 처리
"데브엑스로"사내 DevX Gateway사내 게이트웨이 LLM(플레이그라운드)
"로컬로"폐쇄망 로컬 Qwen3-Coder-30B완전 온프레미스 — 가장 민감한 데이터도 가능, 코드·구조 분석에 강함

민감 원문은 --context-file로만 전달하고 명령어·출력에 리터럴로 안 넣는다 — Claude(오케스트레이터)는 판단만 하고, 민감 데이터 접촉은 사내 LLM이 전담한다는 역할 분리가 목적이다.

실측: 라우팅의 목적은 토큰 절약이 아니다 — 로컬 출력을 다시 Claude 컨텍스트로 끌어와 검증·반복하면 토큰은 오히려 늘어난다. 절약은 "안 읽고 파일로만 받거나(--out) 대용량 입력이 로컬에서만 소화될 때"뿐 — 진짜 목적은 데이터 경계 + 비용·역할 분리다.

12설계 철학 — 경계한 것들

과설계 금지

사례 2개뿐인데 범용 라우팅 모듈을 만들지 않음(§7). 한 번 본 사례로 스키마를 미리 늘리지 않음(상태전이 규칙 → 전용 테이블 대신 unresolved 캡처만).

완전 자동화를 목표로 안 잡음

팀별 정책서 비표준화를 실측 확인 후, "자동 처리 비율 최대화 + 실패 사유 구조화 캡처"로 목표 재정의(§5).

DRM 우회 안 함

실 정책서가 IRM 암호화라 못 열렸을 때 화면 캡처+수동 재구성으로 우회 없이 검증.

"만들었지만 방치되는 기능" 경계

unresolved 데이터를 그냥 쌓아만 두지 않고 집계 리포트+읽기전용 UI로 "사람이 보게" 만듦 — API만으론 루프가 안 닫힌다는 판단.

전면 평가 프레임워크 조기 도입 안 함

Recall@K/nDCG류는 지금 규모(정책서 골든셋 89건)엔 과함 — 대상에 맞는 소형 골든셋으로 충분.

검증 안 된 것을 공유 경로에 먼저 안 섞음

정책 검색을 전용 엔드포인트로 분리해두고, 실험실 수치가 확정된 뒤에야 메인 채팅에 편입(§8).
